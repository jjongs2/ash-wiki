# 도메인 문서

엔지니어링 스킬이 코드베이스를 살펴볼 때 이 저장소의 도메인 문서를 어떻게 쓰는지 정리한 문서다.

## 작업 전에 읽을 문서

- 저장소 루트의 **`GLOSSARY.md`**
- **`docs/adr/`**: [ADR 색인](../adr/README.md)에서 작업할 영역과 관련된 ADR을 찾아 읽는다. 현행 규칙과의 관계는 [ADR과 운영 문서](#adr과-운영-문서)를 따른다.
- **`docs/decision-log.md`**: 규칙을 바꾸기 전에 [결정 로그](../decision-log.md)에서 그 규칙의 파일 경로를 찾아, 그 규칙을 고른 항목을 읽는다.

## ADR과 운영 문서

- ADR은 아래 세 기준을 모두 갖춘 결정과 그 까닭의 기록이다. 현행 규칙의 정본은 운영 문서이고, ADR이 운영 문서를 가리키면 그 문서를 따른다.
  - 되돌리기 어렵다.
  - 맥락 없이는 의아하다.
  - 실제 대안 사이에서 골랐다.
- 규칙을 바꿀 때는 운영 문서를 그 자리에서 고친다. 세 기준을 모두 갖춘 결정일 때만 바뀐 부분과 까닭, 고려한 대안을 적은 짧은 ADR을 더하고 [색인](../adr/README.md)에 한 줄을 넣는다.
- 그 밖의 규칙 변경은 ADR 없이, 규칙만 보고는 의아할 때만 그 규칙 곁에 까닭을 한 문장으로 두고, 실제 대안 사이에서 골랐으면 [결정 로그](#결정-로그)에 항목을 쓴다. 대안과 경위는 운영 문서에 적지 않는다. 기존 ADR을 가리키는 "까닭은 [ADR …]에" 꼴의 문장은 그대로 둔다.
- 기존 ADR 가운데 이 기준에 못 미치는 세부 규약의 기록은 새 ADR을 쓸 선례가 아니다.
- 규칙을 함께 담은 ADR(예: [ADR 0001](../adr/0001-isolation-boundary.md) 격리 경계)은 처음 개정할 때 운영 문서로 나눈다.

## 결정 로그

[결정 로그](../decision-log.md)는 세 기준에 못 미치는 결정과 버린 대안을 한 항목씩 남긴다. 항목의 꼴은 결정 로그 머리에 있다.

- 항목을 쓰는 것: 실제 대안 사이에서 고른 규칙 변경(콘텐츠 규칙 포함), [하네스 조사](../research/README.md) 질문 하나의 판정.
- 쓰지 않는 것: 대안 없는 고침, 표기 결정([용어 표기 결정](../wiki-terms.md)이 맡는다), 세 기준을 갖춘 결정(ADR이 맡고 로그에 따로 두지 않는다).
- **원래 까닭 찾기**: ADR이나 항목이 없는 규칙을 바꾸며 항목을 쓸 때는 `git blame`으로 그 규칙을 들인 PR을 찾는다. 찾으면 까닭 필드에 `원래 까닭: … (#n)`으로, 못 찾으면 `원래 까닭: 근거 불명`으로 적는다. 항목을 쓰지 않는 고침에는 걸지 않는다.

`npm run check:trace`가 두 가지를 본다.

- 결정 로그 안: ID 겹침, 빠진 필드, 대체 짝
- `content/` 밖 Markdown의 상대 링크: 가리키는 파일과 절(앵커)이 있는지. 코드 블록과 인라인 코드 안, 테스트 픽스처는 보지 않는다.

## 용어집의 용어 사용하기

결과물에서 도메인 개념을 언급할 때(이슈 제목, 리팩터링 제안, 가설, 테스트 이름 등)는 `GLOSSARY.md`에 정의된 용어를 쓴다. 용어집에서 쓰지 않기로 한 유의어로 바꿔 쓰지 않는다.

`GLOSSARY.md`에는 용어의 정의만 둔다. 무엇을 해야 하는지나 무엇이 1층인지는 [ADR과 운영 문서](#adr과-운영-문서)가 말하는 정본에 두고, 용어집은 필요하면 그 문서를 가리킨다.

필요한 개념이 용어집에 아직 없다면 둘 중 하나다. 프로젝트에서 쓰지 않는 용어를 새로 만들고 있는 것일 수 있으니 다시 생각해 보거나, 실제로 빠진 용어라면 `/domain-modeling`에서 다룰 수 있도록 기록해 둔다.
