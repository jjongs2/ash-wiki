# 결정 로그

ADR의 세 기준에 못 미치는 결정과 버린 대안을 한 항목씩 남긴다. 무엇을 쓰는지는 도메인 문서의 [결정 로그](agents/domain.md#결정-로그)가 정한다. 꼴은 `npm run check:trace`가 검사한다.

## 꼴

항목 하나가 `###` 제목 하나와 그 아래 필드 불릿이다. 새 항목은 끝에 더하고, 지우지 않는다. 표로 두지 않는다. prettier가 열 너비를 맞추며 모든 행을 다시 써서 나란한 PR끼리 충돌하기 때문이다.

```markdown
### D12 <이름>

- 채택: <고른 것>
- 기각: <버린 것>
- 까닭: <고른 까닭>
- 규칙: [<절>](<경로>#<앵커>)
- 근거: #<PR이나 이슈>, [<조사 기록>](경로)
```

| 필드           | 쓰는 것                                                                                                                                                                    |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 제목           | `D<n>`과 결정을 가리키는 짧은 이름. ID는 `D1`부터 매기고, 겹치면 나중에 머지하는 쪽이 고친다                                                                               |
| 채택·보류·기각 | 고른 것, 미룬 것, 버린 대안. 하나 이상 쓰고, 채택에는 기각이나 보류가 따른다                                                                                               |
| 까닭           | 고른 까닭. 보류는 다시 볼 조건을 적는다. ADR이나 항목이 없던 규칙을 바꾸면 [원래 까닭](agents/domain.md#결정-로그)을 함께 적는다                                           |
| 규칙           | 바꾸거나 확인한 규칙의 절 링크. 없으면 `없음`                                                                                                                              |
| 근거           | PR, 이슈, 조사 기록 가운데 하나 이상                                                                                                                                       |
| 대체           | 이 항목이 대체한 항목. `대체: D<n>`으로 쓰고, 대체된 항목의 제목에 `(D<m>이 대체)`를 단다. ADR이 항목을 대체하면 `(ADR <n>이 대체)`를 단다. ADR을 뒤집는 결정은 ADR로 쓴다 |

필드는 불릿 머리에 `<필드>: `로 한 번씩 쓰고, 값이 길면 들여 쓴 줄로 잇는다. 대체된 항목의 표시는 ID 바로 뒤에 둔다. 예: `### D3 (D12이 대체) <이름>`

## 항목

### D1 ADR 문턱 유지와 결정 로그 도입

- 채택: ADR의 꼴, 현행 규칙의 정본을 운영 문서에 두는 분리, 세 기준을 그대로 두고, 세 기준에 못 미치는 결정은 결정 로그에 둔다
- 기각: ADR 문턱을 "실제 대안 사이에서 골랐다" 하나로 낮추기
- 까닭: 하네스 결정은 문턱과 상관없이 ADR로 오지 않았다. 기록할 대상은 문턱을 낮춰도 같고, 결정마다 ADR 파일을 두면 엔지니어링 스킬이 매번 읽는 색인이 불어난다.
- 규칙: [ADR과 운영 문서](agents/domain.md#adr과-운영-문서), [결정 로그](agents/domain.md#결정-로그)
- 근거: #714, [ADR이 이 저장소의 하네스 결정에 맞는가](research/adr-fit-for-harness-decisions.md)

### D2 ADR 대체 처리 유지

- 채택: ADR의 대체 처리를 그대로 둔다
- 기각: 0001\~0006에 정본 줄, 부분 변경 칸, `deprecated` 상태 두기
- 까닭: 0002·0005·0006은 #191이 그대로 두었고, 0001·0003·0004는 #470이 범위 밖에 두었다. 이 길로 들어오는 독자가 적고, 부분 변경 표시에 누락이 없다.
- 규칙: [대체됨](adr/README.md#대체됨)
- 근거: #714, [대체되거나 폐기된 결정](research/superseded-decisions-and-canonical-docs.md)

### D3 규칙 변경의 대안 기록

- 채택: 실제 대안 사이에서 고른 규칙 변경은 결정 로그에 남긴다
- 기각: squash 메시지에 대안 옮기기
- 까닭: #609 뒤 머지된 docs·feat PR 23건(#710 포함)의 본문에 대안이 없다. 커밋 메시지는 이력이라 찾으러 가야 보이고 검사할 링크가 없다.
- 규칙: [ADR과 운영 문서](agents/domain.md#adr과-운영-문서), [결정 로그](agents/domain.md#결정-로그)
- 근거: #714, [작은 결정과 그 대안](research/minor-decisions-and-alternatives.md)

### D4 결정 로그와 링크 검사

- 채택: 결정 로그 안의 검사와, `content/` 밖 Markdown의 상대 링크·앵커 존재 검사를 `npm run check`에 둔다
- 기각: `검사 <id>` 표지 짝 검사, PR 본문의 `결정 로그:` 줄을 CI로 보는 검사
- 까닭: 조사 기록의 인용 셀에서 깨진 상대 링크 3곳이 나왔다. 표지 13종은 검사 id와 모두 맞는다. 본문 검사는 `CONTRIBUTING.md`의 "PR 제목·본문 검사는 두지 않습니다"와 부딪치고, 규칙 파일을 고치는 content PR과 Dependabot PR을 막으므로 그 줄은 리뷰가 본다.
- 규칙: [결정 로그](agents/domain.md#결정-로그)
- 근거: #714, [결정, 규칙, 근거를 잇는 추적성](research/decision-rule-traceability.md)

- 까닭: 산문 사본은 결정적으로 잡지 못하고, 조사가 든 줄 사본의 어긋남은 #451 직전의 것이다.
- 규칙: [원칙](../CONTRIBUTING.md#원칙)

### D7 조사 기록의 공개 저장소 배치

- 채택: 하네스 조사의 조사 기록과 출처 목록은 공개 저장소의 `docs/research/`에 둔다
- 기각: 저장소 밖의 비공개 자리에 두기
- 까닭: 독자는 규칙을 고치려는 사람과 에이전트라, 결정 로그와 규칙이 링크로 가리키고 검사기가 볼 수 있는 자리여야 한다. 들일 수 있는 것은 데이터 경계가 정한다.
- 규칙: [데이터 경계](research/README.md#데이터-경계)
- 근거: #711, #710

### D8 기존 규칙의 소급 없음

- 채택: 기존 규칙에 결정 기록을 미리 소급하지 않는다. 항목을 쓰는 변경이 ADR이나 항목이 없는 규칙을 바꿀 때만 `git blame`으로 원래 까닭을 찾아 적는다
- 기각: 기존 규칙의 일괄 소급
- 까닭: 까닭은 규칙을 바꿀 때 필요하고, 바꾸지 않는 규칙의 까닭은 읽힐 일이 없다. 대안 없는 문구 고침에는 찾은 까닭을 적을 자리가 없어 원래 까닭 찾기를 걸지 않는다.
- 규칙: [결정 로그](agents/domain.md#결정-로그)
- 근거: #711, #714

### D9 모든 규칙 변경에 쓰는 결정 로그

- 채택: 결정 로그, 원래 까닭 찾기, 추적성 검사는 콘텐츠 규칙을 포함한 모든 규칙 변경에 쓴다. 표기 결정은 [용어 표기 결정](wiki-terms.md)이 그대로 맡는다
- 기각: 하네스 규칙에만 쓰기
- 까닭: 콘텐츠 규칙도 실제 대안 사이에서 고르고, 세 기준에 못 미치면 하네스 규칙과 같이 대안이 남지 않는다. 분야마다 기록 자리를 따로 두면 규칙을 바꾸는 사람이 어디를 볼지 갈린다.
- 규칙: [결정 로그](agents/domain.md#결정-로그)
- 근거: #711

### D10 출처 밖 결론과 사유 없는 인용 키

- 채택: 인용한 사실을 엮어 출처에 없는 결론을 내지 않는다는 줄, 사유를 적지 못한 인용 키는 빼라는 줄
- 기각: 값싼 자동 대조
- 까닭: STORM 글의 주된 오류는 출처를 넘어선 추론이었는데 이것을 따로 막는 줄이 없어, 검증자가 통과시키면 드러나지 않는다. 검증자가 키마다 사유를 이미 내므로 키 처리는 한 줄로 닫힌다. 자동 대조는 하네스 밖에서 돌려야 하고, 추론 연결은 함의 판정으로 잡히지 않는다. 사람의 표본 대조는 D13이 정한다.
- 규칙: [판정](wiki-verification.md#판정), [`source-verifier`](../.claude/agents/source-verifier.md), [`note-verifier`](../.claude/agents/note-verifier.md)
- 근거: #725, [검증 단계](research/llm-wiki-verification-stages.md)

### D11 미검증 주장 처리의 현행 유지

- 채택: 현행 유지
- 기각: 닫힌 이슈의 미검증 항목 이어받기, 사유에 따라 다시 시도할 때 두기, 표시하고 게시하기
- 보류: 유료 원문을 근거로 인정하기
- 까닭: 보강이 지도 자료로 페이지에 없는 주장을 스스로 찾으므로 중요한 주장은 다시 잡히고, 옛 미검증 기록은 이미 떨어진 출처와 노트 표현을 끌고 온다. 다시 시도로 열릴 `접근 실패`는 10개뿐이다. 표시하고 게시하기는 "게시되는 것은 검증 완료뿐"과 유료 출처 규칙을 뒤집고, 위키백과는 이 꼴의 대가로 밀린 일을 진다. 유료 원문은 ADR 0005와 출처 위계의 유료 출처 절을 뒤집는 콘텐츠 규칙이라, 관문 3에서 콘텐츠 규칙으로 넓힐 때 다시 본다.
- 규칙: [판정](wiki-verification.md#판정), [미검증 사유](wiki-verification.md#미검증-사유)
- 근거: #725, [미검증 주장](research/unverified-claim-handling.md)

### D12 `verified` 만료 검사 빼기

- 채택: `verified` 만료 검사 빼기(`verified` 필드는 기록으로 남긴다), 검증 규칙이나 검증 에이전트의 결함을 고치는 PR이 그 결함이 닿았을 페이지를 다시 볼지 정해 본문에 적기
- 기각: 인용할 때 보관 사본 남기기, 날짜 붙은 상태 문장 모으기
- 보류: 논문 철회 통로
- 까닭: 만료 FAIL은 2027-03-26부터 3\~5월에 421쪽에 찍히지만 받는 흐름이 없다. 낡음은 월간 판 확인, 보강의 정정 항목, 상태 문장의 확인한 달이 맡는다. 원래 까닭: 근거 불명(#1, #15). 결함 아래 게시한 글은 다시 볼 계기가 없고, 이 줄은 결함을 고칠 때만 비용이 든다. 논문 철회는 #729가 DOI 있는 엔트리 76개를 대조해 걸린 것이 없었다. 걸린 것이 나오면 다시 본다. 죽은 링크는 린트가 잡아 Wayback으로 바꾸고, 상태 문장의 날짜는 독자에게 보인다.
- 규칙: [출처 상태](wiki-verification.md#출처-상태), [결함을 고칠 때](wiki-verification.md#결함을-고칠-때)
- 근거: #725, [게시한 주장의 재검증](research/published-claim-reverification.md)

### D13 사유 먼저 내기와 사람 표본

- 채택: 검증자 반환에서 사유를 판정보다 먼저 내기, 검증 완료의 사유를 인용 위치의 원문 구절 한두 문장으로 시작하기, 사람 표본으로 검증자 판정의 일치율을 한 번 재기
- 기각: 공개 벤치마크로 재기
- 보류: 심은 오류로 놓침 재기
- 까닭: 검증자 판정을 사람과 견준 적이 없어, 판정자 연구의 수치가 이 검증자에 들어맞는지 모른다. 사유 먼저는 점수 전 추론과 근거 먼저 보정의 꼴이고, 옮긴 구절이 있으면 사람 표본이 원문을 다시 열지 않고 대조된다. 원래 까닭: 필드 순서는 근거 불명(#1, #15). "자기 말로"는 출처의 이용 조건이 번역과 수정을 허락하지 않아서이므로(#15, #194), 옮긴 구절은 페이지와 이슈에 들이지 않는다. 표본은 상시 단계가 아니라 한 번이고(#728), 계속할지는 결과로 정한다. 심은 오류는 표본에서 놓친 판정이 나오면 다시 본다. 공개 벤치마크는 출처의 분야와 길이가 이 저장소와 다르다.
- 규칙: [판정](wiki-verification.md#판정), [`source-verifier`](../.claude/agents/source-verifier.md), [`note-verifier`](../.claude/agents/note-verifier.md), [인제스트의 반환 확인](../.claude/skills/wiki-ingest/SKILL.md#3-반환-확인)
- 근거: #725, [LLM 판정자의 신뢰도](research/llm-judge-reliability.md)

### D14 판정하는 모델 나누기의 기각

- 기각: 쓰는 쪽과 판정하는 쪽의 모델을 다르게 두기, 다른 계열 판정자를 표본에 두기, 전용 사실 확인 모델, 판정 전에 추론하게 하기
- 보류: 인제스트에도 독립 판정 하나 더
- 까닭: 같은 계열 안에서는 얻는 것이 작다. 다른 계열과 전용 모델은 하네스 밖 실행과 키가 들고, 긴 원문 대조에서 잰 적이 없다. 판정 전 추론은 agent 파일로 정할 수 없고, 사유 먼저(D13)가 지시로 같은 일을 한다. 독립 판정은 판정 호출이 두 배라, 사람 표본에서 놓친 판정이 나오면 다시 본다.
- 규칙: 없음
- 근거: #725, [같은 모델끼리 검증하는 한계](research/same-model-verification-limits.md)

### D15 긴 문서 머리의 절 찾기 줄

- 채택: 위키 검증 문서와 매체 목록의 머리에 맡은 절을 절 제목으로 찾아 읽으라는 줄
- 기각: 큰 참고 파일에 목차, 파일 쪼개기, 단계별 읽기를 다섯 스킬로 넓히기
- 보류: 스킬 머리에 늘 지킬 규칙, 5,000토큰을 넘는 스킬을 단계별 파일로 나누기
- 까닭: 두 파일은 Read 한 번에 첫 쪽만 오는데 브리프는 첫 쪽 밖의 절(미검증 사유, 봇 차단 호스트, 검색 질의)을 정해, 첫 쪽에서 멈춘 에이전트는 드러나지 않게 그 절을 빠뜨린다. 머리의 줄은 첫 쪽에 늘 보이고 제목과 어긋날 것이 없다. 목차는 브리프가 준 절 이름을 되풀이할 뿐이고 새 절이 빠져도 검사가 잡지 못한다. 100줄 넘는 나머지 10개는 한 번에 다 읽힌다. 쪼개기는 위키 검증 문서를 적어도 셋으로 나누고 이를 가리키는 53개 파일의 링크와 표를 읽는 코드를 고쳐야 한다. 단계별 읽기가 줄이는 비용은 잰 적이 없다. 스킬 머리 규칙은 compaction 뒤 스킬 앞 5,000토큰만 다시 붙는 것을 겨누지만 #347이 잰 세션은 압축에 걸리지 않았고, 스킬 나누기는 명세의 5,000토큰 권고를 따르지만 넘는 스킬이 있는지 재지 않았다. 두 보류는 D17의 조건에서 다시 본다.
- 규칙: [위키 검증](wiki-verification.md#위키-검증), [매체 목록과 검색 질의](../.claude/skills/wiki-news/outlets.md#매체-목록과-검색-질의)
- 근거: #726, [스킬과 지시 문서의 짜임](research/skill-and-instruction-doc-structure.md)

### D18 브리프에 넘기지 않을 것

### D21 결정 로그 항목의 꼴

- 채택: 항목마다 `###` 제목에 ID와 짧은 이름을 두고, 필드를 불릿 한 줄씩 쓴다. 결정은 채택·보류·기각 필드로 나눈다
- 기각: 한 불릿 안에서 필드만 하위 불릿으로 나누기
- 까닭: 한 불릿에 필드를 이어 쓰면 GitHub가 목록 안의 줄바꿈을 공백으로 렌더해, 항목 하나가 한 문단으로 붙는다. 제목은 GitHub의 목차에 항목을 늘어놓고 항목마다 앵커를 준다. 하위 불릿은 필드는 나누지만 항목을 찾으려면 훑어야 한다. 원래 까닭: 한 불릿 꼴은 표가 나란한 PR끼리 충돌해서 골랐고(#721), 제목과 필드 불릿도 표가 아니라 그 까닭은 그대로 선다.
- 규칙: [꼴](#꼴)
- 근거: #727

### D22 PR 본문의 꼴

- 채택: PR 본문은 PR-body 스킬의 꼴(Summary, Evidence, Merge Danger)을 따르고, 저장소는 `Closes #N` 줄과 `## Open Questions` 절만 더한다. 절 이름은 모두 영어로 쓴다. 흐름의 본문 항목은 절 이름 없이 적고, PR 템플릿은 지운다
- 기각: 저장소만의 꼴(`## Changes`, `## Verification`) 두기, 템플릿에 새 꼴의 예시 본문 두기
- 까닭: 두 꼴은 하는 일이 거의 같고, 스킬의 꼴은 머지 위험을 따로 묻는다. 항목마다 절을 정하면 이름이 바뀔 때마다 여러 파일을 고치고, 어느 절에 둘지는 스킬의 절 설명으로 갈린다. 템플릿은 스킬 꼴의 사본이다. 예시(#665)는 옛 꼴에서 본문을 줄였지만 새 꼴에서는 재 본 적이 없어, 지우고 본문 길이를 지켜본다. 원래 까닭: 근거 불명. 두 절은 저장소 기반을 놓은 #10이 까닭 없이 들였다.
- 규칙: [PR 본문](../CONTRIBUTING.md#pr-본문)
- 근거: #745

### D23 두 축 리뷰를 걸지 않는 곳

- 채택: 두 축 리뷰는 그대로 두고, 다른 단계가 대신하는 조사 기록 PR(사실 확인 에이전트)과 Dependabot PR(CI만)을 예외로 적는다
- 기각: 다른 검토와 겹치는 흐름에서 두 축 리뷰 빼기
- 까닭: 두 축 리뷰는 다른 검토 사이에서 빠진 것을 잡았다. #736에서 2회차 Standards가 UN R100 두 문장의 중복을 잡았고, #669에서 Standards 지적 8건 가운데 4건을 고쳤고, #693과 #668에서 Spec이 링크를 고쳤고, #704에서 구현 Stage가 Standards 지적 3건을 반영했다. 조사 기록 PR(#715, #716)은 사실 확인 에이전트가 대신했고 그 브리프에 질문 범위와 README 규칙을 넣었으나 문서에 없었다. 원래 까닭: 두 축 리뷰는 #10이 모든 PR에 들였고, 루틴이 이 리뷰를 건너뛴 사이 `outlets.md` 버그가 main에 들어가 검토는 이 리뷰를 대신하지 않는다고 정했다(#599).
- 규칙: [리뷰](../CONTRIBUTING.md#리뷰), [머지까지](research/README.md#머지까지)
- 근거: #745

### D24 `결정 로그:` 줄 폐지

- 채택: PR 본문의 `결정 로그:` 줄과 그 적용 범위를 정하던 규칙 파일 문단을 없앤다. 항목을 쓸지는 도메인 문서의 결정 로그 절이 정하고, 항목은 `근거`로 PR을 가리킨다
- 기각: 줄을 그대로 두기
- 까닭: 두 축 리뷰는 PR 본문을 쓰기 전에 돌고 본문을 받지 않아, 이 줄은 아무 검사도 받지 않았다. D4가 이 줄의 CI 검사를 기각하며 든 "그 줄은 리뷰가 본다"는 맞지 않았다. D4가 채택한 검사는 그대로 선다. 원래 까닭: 규칙 파일을 고친 PR이 결정 로그 항목을 가리키게 하고 그 줄을 리뷰의 Standards 축이 보게 하려고 들였다(#721).
- 규칙: [PR 본문](../CONTRIBUTING.md#pr-본문), [결정 로그](agents/domain.md#결정-로그)
- 근거: #745

### D25 보드 draft와 새 이슈로 티켓 내기

- 채택: triage 전의 규약 검토, 용어 표기, 보강의 후속(재조사의 `범위 밖` 포함)을 공개 보드의 draft로 두고, 발견 하나가 draft 하나다. triage는 티켓을 새 이슈로 내고, 흡수한 draft에 그 이슈의 URL과 상태를 쓴다. 용어 표기의 소유자 결정은 그 티켓에 적는다
- 기각: draft를 이슈로 바꾸기, Reader Testing B 이슈·린트 이슈·판 확인 모음도 보드로 옮기기, 모음 이슈를 그대로 두기
- 까닭: 모음 이슈는 항목 여럿을 본문과 코멘트에 쌓아, 항목마다 처리됐는지는 닫을 때 손으로 만드는 짝 표에만 남았다. 보강의 후속 이슈(#433, #662, #680, #686)는 열린 채 triage를 기다렸다. draft는 항목마다 상태를 갖고, `Inbox` 뷰가 흐름별로 묶어 처리한 것을 저절로 뺀다. draft를 이슈로 바꾸면 본문을 agent brief로 다시 써야 하고, draft 여럿을 티켓 하나로 합치지 못한다. B 이슈와 린트 이슈는 이미 걸러진 티켓 입력이라 이슈로 둔다. B 이슈(#553)는 #564 하나로, 린트 이슈(#440)는 #444 하나로 닫혔다. 판 확인 모음은 월간 workflow가 쓰는데, 저장소 토큰으로는 사용자 보드에 쓰지 못하고 그러려면 계정 전체에 닿는 토큰을 새 시크릿으로 둬야 한다. 원래 까닭: 규약 검토 모음은 #172에서 이슈로 시작했고, 열 때마다 닫힌 이슈의 본문을 복사하지 않으려고 템플릿을 두었다(#190). 모음을 이슈로 둔 까닭은 근거 불명이다. `term:` 이슈는 위키 규약을 들인 #13이 까닭 없이 들였고, 결정을 댓글로 남긴 것은 본문의 질문과 추천을 결정의 맥락으로 남기려는 것이었다(#305). 그 맥락은 이제 draft와 티켓이 나눠 갖는다. 보강의 후속은 티켓이 닫히면 본문의 지시가 추적되지 않아 이슈로 냈고(#414), 재조사의 `범위 밖` 이슈는 재조사 스킬(#210)이 까닭 없이 들였다. 추적은 draft가 이어받는다.
- 규칙: [보드](agents/issue-tracker.md#보드), [이슈](../CONTRIBUTING.md#이슈), [용어](wiki-conventions.md#용어)
- 근거: #747

### D26 재조사 일괄 실행

- 채택: 재조사 한 번이 열린 `verify:` 이슈 여럿을 맡아 PR 하나로 닫는다. 이슈는 주제 계획이나 보강마다 하나로 두고, blocked-by 확인, 본문 다시 쓰기, 형제 묶음 링크는 이슈마다 돈다. 게시할 것도 걸 링크도 없는 이슈는 그 실행에서 PR 없이 닫는다
- 기각: `verify:` 이슈를 여럿 합쳐 하나로 두기, 이슈 하나마다 PR 하나를 그대로 두기
- 까닭: 재조사는 2026-10-22(#506) 뒤로 돌지 않았고, 그사이 열린 `verify:` 이슈가 여섯(#658, #666, #673, #677, #681, #741)이 됐다. 인제스트가 끝난 다섯(#658, #666, #673, #677, #681)의 항목은 4, 0, 1, 11, 4개이고, 빈 이슈도 나왔다(#429, #666). 이슈마다 PR을 내면 항목 몇 개마다 검토와 두 축 리뷰를 따로 치른다. 이슈를 합치지 않는 것은 인제스트 티켓의 blocked-by와 형제 묶음이 이슈마다 다르기 때문이다. 원래 까닭: "이슈 하나가 PR 하나"는 재조사 스킬(#210)이 지난 네 번의 재조사(#59, #171, #173, #200)를 옮기며 까닭 없이 정했다.
