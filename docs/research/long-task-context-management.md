# 한 세션에 들지 않는 긴 작업에서 컨텍스트를 어떻게 관리하는가

티켓: #720

## 답

범위: Anthropic의 context engineering 글과 긴 작업 하네스 글 둘, 다중 에이전트 조사 시스템 글, Manus와 Cognition의 글, Claude Code의 컨텍스트와 compaction 문서를 이 저장소의 파이프라인 규약, 스킬의 작업 파일 규칙, #347과 견줬다. 서브에이전트로 나누는 것은 [서브에이전트 나누기와 브리프](subagent-split-and-brief.md)가 다룬다.

**바깥의 세 수단.** Anthropic은 긴 작업의 수단으로 compaction, 구조화된 메모, 서브에이전트를 꼽는다(C1). 오가는 대화가 많은 일에는 compaction, 단계가 분명한 반복 개발에는 메모, 나란히 훑는 조사에는 서브에이전트가 맞는다고 한다(C35).

- **요약(compaction)**: 대화를 요약해 새 컨텍스트에서 잇는다. 가장 가벼운 꼴은 지난 도구 결과를 지우는 것이다(C36). 너무 줄이면 나중에야 중요해질 것을 잃고(C2, C3), 대화 앞쪽의 자세한 지시는 사라질 수 있다(C18). Claude Code는 compaction 뒤에 루트 `CLAUDE.md`, auto memory, 계획, git 상태, 스킬 설명을 디스크에서 다시 넣고, 최근 파일 다섯과 스킬 본문의 앞부분을 다시 붙인다(C19, C21, C34). 무엇을 남길지는 `CLAUDE.md`의 Compact Instructions 절이나 `/compact`의 초점으로 이끌고(C22), `compact`에 맞춘 SessionStart hook으로 출력을 그대로 다시 넣을 수 있다(C34).
- **작업 파일**: 컨텍스트 밖 파일에 메모를 남기고 나중에 다시 읽는다(C4). Anthropic의 하네스는 진행 파일과 git 기록을 두고, 세션마다 그것을 먼저 읽는다(C7, C8, C10). 기능 목록은 Markdown보다 덜 고쳐지는 JSON으로 둔다(C9). Manus는 URL이나 경로만 남기고 본문을 덜어, 되찾을 수 있게 줄인다(C15). 할 일 목록을 다시 써 목표를 컨텍스트 끝에 되새기기도 한다(C16).
- **세션 나누기**: 새 세션은 앞의 기억 없이 시작하므로 세션 사이를 잇는 것이 문제다(C5). Anthropic의 첫 하네스는 compaction만으로 모자라 세션마다 기능 하나만 맡기고, 컨텍스트를 비울 때 구조화된 인계를 넘겼다(C6, C8, C11, C37). 다중 에이전트 조사 시스템도 끝낸 단계를 외부 메모리에 적고 새 서브에이전트에게 넘긴다(C14). Cognition은 기록을 요약하는 모델을 따로 두는 길을 든다(C17).

수단은 모델에 따라 바뀐다. Anthropic의 다음 하네스는 Opus 4.5에서 컨텍스트 비우기를 빼고 자동 compaction에 맡겼지만, 계획·생성·평가 에이전트는 파일로 주고받으며 나눠 두었다(C12, C38). 하네스의 부품마다 가정이 있으니 새 모델마다 다시 보라고 한다(C13). Claude Code 문서도 컨텍스트가 모자라는 일은 드물다고 하면서 일 사이의 `/clear`는 권한다(C23). 반대로 Anthropic은 창이 커져도 컨텍스트 오염은 남는다고 본다(C39).

**이 저장소.** 세션을 나누고, 세션 안에서 싣는 것을 줄이고, 작업 파일을 둔다. compaction은 다루지 않는다.

- **세션 나누기**: 티켓 하나를 한 세션 크기로 두고, ticket-runner는 목적 하나마다 Stage 세션 하나를 띄운다(C24). Stage가 커밋하면 브랜치를 push하고, 이어 갈 티켓의 상태는 원격 브랜치에 남긴다(C25, C40). 인제스트의 아홉 단계는 한 세션 안에서 잇는다(C46).
- **세션 안에서 줄이기**: 메인 세션은 출처를 열지 않고, 규칙은 단계마다 그 절만 읽는다(C41). 검사 출력은 파일로 받아 끝 줄만 본다(C42). #347이 이렇게 메인 세션이 싣는 것을 줄였다(C33).
- **작업 파일**: 인제스트는 브리프, 사본, 로그를 재시작에도 남는 `.work/`에 둔다(C26). Reader Testing은 scratchpad가 재시작에 비므로 `.work/`를 쓴다(C27). 흐름의 상태 일부는 이미 파일에 있다. 브리프의 기준 커밋, 현행판 표, 사본 목록(C43), 계획 파일의 시작 커밋(C28), 재조사 이슈 본문의 항목별 라벨과 메모(C44)다. 출처를 다시 볼 때는 사본에서 필요한 구간만 연다(C29). Manus의 꼴(C15)과 같다.
- **compaction**: 다루는 줄은 없다(C30). 단계마다 "완료:" 줄은 있지만(C31), 스킬 단계 안의 진행을 파일에 적으라는 규칙은 없다(C32). #347이 잰 세션 11개는 압축에 걸리지 않았지만, 출처 경로는 50만\~69만 토큰까지 갔다(C33).

**선택지(결정은 뒤 티켓).**

- **현행 유지**: 세션 나누기와 작업 파일은 바깥 관행과 같은 꼴이다(C7, C11, C24, C26). #347이 잰 세션은 압축에 걸리지 않았고(C33), 모델이 나아지며 compaction에 덜 기대도 된다는 쪽(C12, C23)과 오염은 남는다는 쪽(C39)이 함께 있다.
- **흐름마다 진행 기록을 둔다**: "완료:"를 넘을 때마다 `.work/`의 진행 파일에 한 줄을 적고, 재시작하면 그 파일부터 읽게 한다(C10, C16, C31). 바깥은 단계가 분명한 일에 메모를 권한다(C35). 브리프, 계획 파일, 이슈 본문이 이미 상태 일부를 실으므로(C43, C28, C44), 더할 것은 지금 어느 단계인지다. 바꿀 파일은 각 `SKILL.md`의 준비 문단이나 `CONTRIBUTING.md`의 스킬과 에이전트 절이다. 재시작으로 일을 잃은 기록은 찾지 못했다.
- **compaction 뒤에 다시 넣을 것을 정한다**: 요약을 이끄는 Compact Instructions 절(C22)과, 출력을 그대로 다시 넣는 SessionStart hook(C34)이 있다. 다시 넣을 것은 흐름의 `.work/` 파일 경로다. 바꿀 파일은 `CLAUDE.md`나 프로젝트 `.claude/settings.json`이고, 뒤의 것은 fd6c175에 없다(C45).
- **스킬 머리에 늘 지킬 규칙을 둔다**: compaction 뒤에 다시 붙는 것은 스킬의 앞부분이다(C20, C21). [스킬과 지시 문서의 짜임](skill-and-instruction-doc-structure.md)의 같은 선택지와 겹친다.
