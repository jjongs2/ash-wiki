# 에이전트가 읽는 문서의 일관성은 공개된 프로젝트와 도구에서 어떻게 관리하는가

티켓: #713

## 답

범위: 에이전트 도구의 문서(agents.md, Codex, Claude Code, Gemini CLI, GitHub Copilot, Cursor), 스킬 명세와 작성 지침, 지시 파일 배포 도구(Ruler, rulesync), 린터(skills-ref, agnix, skillsaw), 공개 저장소 두 곳(Ruff, agentskills)을 봤다. cclint라는 이름의 프로젝트는 여럿이라 보지 않았다.

에이전트 지시 파일은 형식이 정해지지 않은 Markdown이다(C1). 하위 폴더의 파일을 어떻게 합치는지는 도구마다 다르다(C2, C4, C5). 다만 여러 도구가 AGENTS.md를 직접 읽거나 읽도록 설정할 수 있어(C7, C12, C24), 한 파일을 함께 쓰기가 쉬워졌다.

**여러 파일에 같은 지시를 두는 관행.**

| 관행                                   | 하는 일                                                               | 기계 검사                                                  | 근거          |
| -------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------- | ------------- |
| 한 파일 + 심볼릭 링크                  | 정본 파일 하나를 두고 다른 이름은 링크로 둔다                         | 없다. 사본이 없다                                          | C3, C25       |
| 한 파일 + import                       | 다른 이름의 파일이 `@AGENTS.md`로 정본을 끌어온다                     | 없다. 사본이 없다                                          | C19, C20, C26 |
| 중앙 원본 + 생성, 생성 파일 커밋 안 함 | 한 폴더의 규칙을 도구별 파일로 생성해 배포하고 저장소에는 두지 않는다 | 저장소에 사본이 없다                                       | C16, C17      |
| 중앙 원본 + 생성, 생성 파일 커밋       | 생성한 파일을 커밋한다                                                | Ruler는 CI 예시로 diff를 보고, rulesync는 `--check`를 둔다 | C18, C27      |

**import와 참조는 비용이 다르다.** import는 파일을 펼쳐 넣는다(C6). 컨텍스트 비용은 줄지 않고(C8), 중첩은 네 단계까지다(C28). Codex처럼 이어 붙이는 도구에는 크기 상한이 있다(C5). 참조는 파일을 넣지 않고 에이전트가 필요할 때 읽는다(C29). 그 대신 참조한 파일이 다시 다른 파일을 참조하면 일부만 읽힐 수 있어, 참조를 한 단계로 두라는 권고가 명세와 작성 지침 양쪽에 있다(C14, C30). 이 저장소는 import를 쓰지 않으므로 C8은 해당하지 않는다(C41).

도구 문서는 사본 대신 정본을 가리키라고 권한다(C13, C26, C31).

**기계 검사.** 자유 글 지시 사이의 모순을 결정적으로 판정하는 검사는 찾지 못했다. 찾은 것은 셋이다.

- 규칙으로 보는 것: 명세의 참조 검사기 skills-ref는 frontmatter와 이름만 본다(C21, C32). agnix는 여러 도구의 지시 파일을 761개 규칙으로 보고 GitHub Action을 둔다(C33). 그 규칙에는 파일 사이의 빌드·테스트 명령과 도구 목록 충돌, 없는 import 경로, 너무 깊은 참조 사슬이 있다(C34). 정형 항목, import 경로, 참조 깊이까지가 규칙의 몫이다.
- 휴리스틱으로 보는 것: skillsaw는 키워드 쌍으로 모순을 짐작하고(C35), 비슷하지만 같지 않은 절을 파일 사이에서 찾고(C36), 대상 파일이 없는 Markdown 링크를 잡는다(C37).
- LLM으로 보는 것: Claude Code의 prompt audit은 지시가 모순되는 파일과 없는 파일 참조를 찾아 고칠 안을 보고만 한다(C9, C10).

같은 낱말을 한결같이 쓰라는 것은 작성 지침이다(C15).

**이 저장소에 주는 함의(선택지와 비용, 결정은 #714).**

- 위 공유 관행은 여러 에이전트에 같은 지시를 나눠 주는 문제를 푼다. 이 저장소에서는 스킬과 프롬프트가 운영 문서의 규칙을 다시 적어 갈라질 위험이 있었다(C22, C23). 줄 단위 사본의 꼴은 [같은 규칙의 사본](rule-copy-drift.md)에서 다룬다. 공유 관행은 이 꼴을 검사하지 않는다.
- **참조 깊이**: 스킬과 에이전트 문서가 위키 검증 문서를 101번 부르고(C38), 그 문서는 다른 문서의 절로 36번 링크한다(C39). 스킬에서 위키 검증 문서를 거쳐 다른 문서의 절로 가는 사슬이 있다. 이번 조사에서 깊이 때문에 규칙을 놓친 사례는 찾지 못했다(C40). 검사를 둔다면 agnix의 참조 깊이 규칙(C34)이 선례다.
- **존재 검사의 범위**: 스킬과 에이전트 문서가 운영 문서를 부르는 자리는 Markdown 링크 14곳, 백틱 경로 154곳이다(C42). 절은 글로 이름을 댄다(C43). 링크만 보는 검사기(C37)로는 대부분을 놓친다. 선택지는 백틱 경로와 절 이름까지 읽는 검사를 만들거나, 운영 문서를 부를 때 링크로 쓰게 하는 규칙을 두는 것이다. 앞의 것은 파서 비용이, 뒤의 것은 기존 154곳을 바꾸는 비용이 든다.
- **모순 찾기**: 휴리스틱(C35, C36)과 LLM 감사(C10)는 오탐을 낼 수 있고 보고만 한다. CI에서 실패시키는 단계보다 리뷰 단계의 도구에 가깝다.
