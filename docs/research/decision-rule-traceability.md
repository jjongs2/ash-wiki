# 결정, 규칙, 근거를 잇는 추적성 관행은 무엇인가

티켓: #713

## 답

추적성은 앞뒤 두 방향으로 따라갈 수 있어야 하고(C1), 문제의 대부분은 규칙이 정해지기 전의 내력, 곧 근거 쪽 추적이 모자라서 생긴다(C2). 이 저장소에 옮기면 "규칙 → 결정 → 조사"의 거꾸로 가는 링크가 그 몫이다.

**링크의 방향.** 요구사항 도구는 아래 항목이 위 항목의 ID를 적는다(C3, C7). 반대 방향은 적지 않고 계산하는 도구도 있다(C10). ADR과 PEP는 대체 관계를 링크로 남긴다. Nygard는 옛 결정에 새 결정을 가리키는 링크만 두고(C13), adr-tools와 PEP 1은 양쪽에 적는다(C14, C15). 양쪽에 적으면 둘이 어긋날 수 있다. PEP 검사기도 값의 꼴만 보고 짝이 맞는지는 보지 않는다(C16).

**기계로 검사하는 것.** 세 층으로 나뉜다.

| 층   | 검사하는 것                                            | 예                                                                    | 근거                   |
| ---- | ------------------------------------------------------ | --------------------------------------------------------------------- | ---------------------- |
| 존재 | 링크의 대상(ID, 파일, 절)이 있다                       | Doorstop의 모르는 UID, Sphinx nitpicky, remark-validate-links, lychee | C5, C17, C18, C19, C20 |
| 덮음 | 위 항목마다 그것을 가리키는 아래 항목이 하나 이상 있다 | OFT, Doorstop의 링크 없는 항목, Sphinx-Needs `back_links`             | C6, C7, C11            |
| 낡음 | 링크가 적어 둔 대상의 판·지문과 지금 대상이 같다       | Doorstop의 suspect link, OFT의 revision                               | C4, C8, C9, C27        |

덮음과 낡음 검사는 항목마다 고정된 ID를 둔다(C3, C8, C12). 낡음 검사는 정본이 바뀔 때 가리키는 쪽에 다시 보라고 알리지만, 사람이 그 표시를 지우거나(C27) 뜻이 바뀌었는지 판단해 판을 올려야 한다(C9).

ADR 관행이 권하는 기계 검사는 서식 린트(C21)이고, Docs as Code는 문서에 자동 테스트를 붙이는 것을 원칙에 넣는다(C22).

**이 저장소의 현행.** 규칙은 정본 하나를 두고 다른 곳은 가리킨다(C23). 운영 문서가 ADR을 가리키는 "까닭은 [ADR …]에" 꼴이 규칙에서 결정으로 가는 링크다(C24). 기계 검사는 조사 기록 안에서만 돈다. 주장이 출처 목록에 있는 ID를 쓰는지, 다른 표가 가리키는 주장 ID가 주장 표에 있는지를 본다(C25). 운영 문서, 스킬, ADR 사이의 링크는 어떤 검사도 보지 않는다(C26).

**함의(결정은 #714).**

- 존재 검사는 싸다. 운영 문서와 스킬의 상대 링크와 절 앵커를 `npm run check`에 더하는 일이고, 기존 도구(C19)나 짧은 스크립트로 된다. ID를 새로 매길 필요가 없다.
- 덮음 검사("규칙마다 결정 기록이 있다")는 규칙마다 ID가 있어야 하고, 지도의 "기존 규칙은 미리 소급하지 않는다"와 부딪친다. 하려면 바뀐 규칙에만 거는 범위가 필요하다.
- 낡음 검사는 가리키는 쪽이 대상의 판을 함께 적어야 한다. 정본이 바뀔 때 가리키는 곳을 모두 다시 보게 만들지만, 표시를 지우는 손이 PR마다 든다.
- 대체 링크를 양쪽에 적는 꼴을 고르면 짝 검사를 함께 두어야 한다(C15, C16). 한쪽만 적고 다른 쪽을 계산하는 꼴(C10)은 그 검사가 필요 없다.
