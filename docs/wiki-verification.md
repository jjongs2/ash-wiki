# 위키 검증

주장을 판정하고, 미검증 주장을 모아 한 번 더 조사하는 방법입니다. 어떤 출처가 1층인지는 [ADR 0005](adr/0005-source-hierarchy-with-background-claims.md), 노트의 표현과 식별 정보를 어디까지 들이는지는 [ADR 0001](adr/0001-isolation-boundary.md)을 따릅니다.

## 판정

주장마다 셋 가운데 하나로 판정합니다. 게시되는 것은 검증 완료뿐입니다.

| 판정      | 뜻                                               | 처리                                    |
| --------- | ------------------------------------------------ | --------------------------------------- |
| 검증 완료 | 1층 출처가 주장을 뒷받침합니다                   | 인용을 달아 게시합니다                  |
| 미검증    | 뒷받침을 못 찾았지만 다시 시도할 여지가 있습니다 | 게시하지 않고 `verify:` 이슈에 남깁니다 |
| 제외      | 다시 시도해도 검증될 여지가 없습니다             | 버립니다                                |

검증 완료가 아닐 때 갈림길은 하나입니다. **다시 시도할 여지가 있는가.** 있으면 미검증, 없으면 제외입니다. 제외는 공개 출처로 확인할 수 있는 사실이 아닌 주장입니다. 예: 평가, 비유, 원본에만 있는 예시.

### 좁혀 쓰기

출처가 주장의 일부만 뒷받침하면 주장을 쪼갭니다. 뒷받침되는 부분은 검증 완료로 쓰고, 나머지는 따로 판정합니다. 예: "A는 B이고 C다"에서 출처가 B만 말하면, "A는 B다"를 게시하고 "A는 C다"를 따로 판정합니다.

출처가 주장과 다르게 말하고 출처 쪽이 분명하면, 주장을 출처대로 고쳐 씁니다. 고친 주장은 검증 완료입니다.

표준·규제 원문이 아닌 1층 출처는 그것을 펴낸 발행기관의 말입니다. 동작 주장과 배경 주장은 아래처럼 범위를 맞춥니다.

- 발행기관 하나의 자료만이 뒷받침하는 주장은 본문에 그 발행기관이나 제품의 이름을 적어 그 범위로 좁혀 씁니다. 예: "CAN 버스는 120 Ω 꼬임쌍선이다"를 "SN65HVD23x는 120 Ω 종단을 둔 꼬임쌍선 버스를 전제한다"로 씁니다.
- 서로 다른 발행기관 둘 이상이 같은 내용을 말하면 일반 명제로 쓰고, 모두 인용합니다.

좁혀 쓴 문장은 출처의 그 대목이 무엇을 다루는지에 따라 아래 세 갈래 가운데 하나로 씁니다. 꼴을 바꿔도 문장의 범위는 그대로여야 합니다.

| 출처의 대목                        | 꼴                        | 예                                                                       |
| ---------------------------------- | ------------------------- | ------------------------------------------------------------------------ |
| 특정 제품(부품 번호가 붙은 칩, IP) | 제품을 주어로 씁니다      | "SN65HVD23x는 120 Ω 종단을 둔 꼬임쌍선 버스를 전제한다"                  |
| 한 발행기관만 말하는 일반 원리     | "X에 따르면 …다"로 씁니다 | "TI 앱노트에 따르면 CAN의 버스 접근은 이벤트 구동이며 무작위로 일어난다" |
| 출처가 한 행위가 곧 내용인 것      | 보고 동사를 남깁니다      | "CiA는 …라 부르기를 권한다"                                              |

- 제품: 출처 문장에 부품 번호가 없어도 됩니다. 데이터시트의 "the device"는 표지의 부품이고, 여러 부품을 다루면 제품군 이름으로 씁니다. 어느 제품의 대목인지는 출처를 열어 확인합니다.
- 일반 원리: 벤더 문서가 제품 없이 원리를 설명하는 대목도 여기입니다. 예: MCP2515 데이터시트가 오류 에코 플래그가 생기는 까닭을 설명하는 대목은 "MCP2515 데이터시트에 따르면 …"으로 씁니다.
- 출처의 행위: 동사가 출처가 한 행위(명명, 권고, 값·분류의 제시)이고 그 목적어가 이름·권고·값일 때만 보고 동사를 남깁니다. 예: 발행기관마다 다른 권장 버스 길이를 "TI 앱노트는 40 m를 제시하고"처럼 나란히 적는 문장. "설명한다", "적는다"처럼 사실을 전하기만 하는 동사는 남기지 않습니다.

같은 출처가 한 문단에서 연달아 뒷받침하는 문장은 첫 문장에만 출처 표시를 답니다. [인용 마커](wiki-conventions.md#인용)처럼 문단을 넘겨 묶지 않으며, 목록 항목과 콜아웃은 하나하나를 문단 하나로 봅니다. 문장을 옮기거나 쪼갤 때는 출처 표시가 떨어져 나가지 않았는지 봅니다.

좁혀 써도 주장의 종류는 바뀌지 않습니다. 표준이 무엇을 정의하거나 요구하는지를 말하는 문장은 누구의 말로 좁혀 쓰든 규범 주장이고, 규범 주장의 1층으로만 검증합니다. 예: "CiA에 따르면 두 CAN FD는 호환되지 않는다"는 CiA가 펴내지 않은 명세(ISO 11898-1, Bosch CAN FD)에 대한 규범 주장이므로 CiA 자료로 검증하지 않습니다.

그래서 규범 주장은 좁혀 쓰지 않습니다. 표준을 주어로 두고, 정한다·둔다·규정한다처럼 정의나 요구를 말하는 동사를 씁니다. 예: "Bosch CAN 2.0 규격은 버스 매체를 정하지 않는다." 권고 자체가 내용이면 위 셋째 갈래를 따릅니다. 예: "Bosch CAN 2.0 규격은 계수기 값이 약 96을 넘으면 이를 검사할 수단을 두기를 권한다."

여러 필자가 기고하는 매체(CAN Newsletter 등)의 기사는 필자가 속한 발행기관의 자료로 셉니다. 소속이 드러나지 않으면 매체를 펴낸 발행기관의 자료로 셉니다.

### 표준의 판

표준·규제는 판마다 같은 내용을 다르게 말하기도 합니다. 그래서 문장이 무엇을 말하는지에 따라 어느 판으로 검증할지가 정해집니다. 이 절의 규칙은 리뷰가 봅니다.

- **현행판**은 표준의 판 가운데 지금 유효한 판입니다. 표준이 나뉘거나 합쳐져 다른 표준으로 이어졌으면, 이어받은 표준의 현행판입니다. 표준 페이지가 있으면 `edition`과 `status`로 확인합니다.
- **폐지된 판**은 현행판이 아닌 판입니다.

현행 규정을 말하는 문장은 현행판으로만 검증합니다. 두 판이 모두 뒷받침해도 현행판만 인용합니다.

폐지된 판은 **이력 문장**에서만 인용합니다. 이력 문장은 판 사이의 변화(도입, 삭제, 이름 변경, 서술 변경)를 말하는 문장입니다. 표준 페이지의 개정 이력 절 항목은 이력 문장이고, 개정 이력 절 밖에서도 쓸 수 있습니다.

- 주어에 판 연도를 적고 과거 시제로 씁니다. 예: "ISO 11898-1:2015는 …로 정의했다."
- 현행판이 어떻게 다른지 함께 적고, 두 판을 모두 인용합니다.
- 그 판이 처음 넣은 것을 말하는 문장(도입)은 폐지된 판만 인용해도 됩니다. 예: "ISO 11898-1:2015는 CAN FD 프레임 포맷을 새로 넣었다."

현행판이 이름을 바꾼 개념은 본문을 현행판의 용어로 쓰고 현행판을 인용합니다. 옛 이름은 이력 문장으로만 씁니다. 예: LIN의 노드는 현행판의 이름인 commander와 responder로 쓰고, 옛 이름은 "ISO 17987-1:2016은 commander와 responder를 master와 slave라 불렀다"처럼 씁니다.

현행판의 공개 범위에서 같은 내용을 찾지 못하면 이력 문장으로 돌려 쓰지 않습니다. 이 주장은 미검증이고, 사유는 `공개 범위 밖`입니다.

### 게시 기준

검증 완료 주장만으로 정의 절을 채우지 못하는 페이지는 만들지 않습니다. 그 페이지의 주장은 모두 `verify:` 이슈로 옮깁니다.

### 미검증 사유

미검증에는 사유를 하나만 적습니다. 둘 이상에 해당하면 순위가 앞선 것을 고릅니다. 재조사는 사유마다 같은 방법으로 다시 시도합니다.

| 순위 | 사유            | 뜻                                                             | 재조사 방법                                                          |
| ---- | --------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1    | `출처와 어긋남` | 1층 출처가 다르게 말하는데, 어느 쪽이 맞는지 가리지 못했습니다 | 다른 판본과 다른 1층 출처로 대조합니다                               |
| 2    | `공개 범위 밖`  | 뒷받침하는 내용이 유료 표준의 공개되지 않은 부분에만 있습니다  | 발행기관의 공개 자료를 다시 찾고, 동작 주장이면 벤더 문서도 찾습니다 |
| 3    | `접근 실패`     | 출처를 찾았지만 열지 못했습니다                                | Wayback 스냅샷과 발행기관의 다른 경로를 찾습니다                     |
| 4    | `1층 없음`      | 뒷받침하는 출처가 1층이 아닙니다                               | 같은 사실을 담은 1층 출처를 찾습니다                                 |
| 5    | `출처 없음`     | 뒷받침하는 공개 출처를 찾지 못했습니다                         | 용어와 검색어를 바꿔 넓게 찾습니다                                   |

## `verify:` 이슈

주제마다 `verify: <주제>` 이슈 하나에 미검증 주장을 모읍니다.

1. 주제 계획이 발행합니다. 라벨은 `ready-for-agent`이고, 그 주제의 모든 묶음 티켓에 blocked-by를 겁니다. 묶음 티켓이 모두 닫혀야 재조사를 시작할 수 있습니다.
2. 인제스트는 묶음마다 코멘트를 하나만 답니다. 본문은 고치지 않습니다. 병렬 인제스트끼리 본문을 덮어쓰지 않기 위해서입니다. 미검증 주장이 없어도 없다고 답니다.
3. 재조사가 한 번 돈 뒤 이슈를 닫습니다.

주장은 자기 말로 씁니다. 노트의 표현과 식별 정보는 이슈에도 들이지 않습니다.

인제스트 코멘트는 이 꼴로 씁니다.

```md
묶음: <묶음 이름> (#<묶음 티켓>)

- `<슬러그>` <주장> — `<사유>`. 시도한 출처: <URL 또는 없음>
```

## 재조사

재조사는 이슈에 모인 주장과 출처만 봅니다. 노트는 읽지 않습니다.

1. 코멘트를 모아 이슈 본문을 `## <미검증 사유>` 절로 다시 씁니다. 절 순서는 사유의 순위를 따르고, 항목마다 `- [ ] <슬러그>: <주장>`으로 적습니다.
2. 절마다 사유의 재조사 방법으로 한 번 다시 시도하고, 항목을 다시 판정합니다.
3. 검증 완료가 된 주장을 페이지에 더하는 PR을 올립니다. 더한 페이지의 `verified`를 재조사한 날로 고치고, PR 본문에 `Closes #<verify: 이슈>`를 적습니다.
4. 이슈 본문에서 검증 완료가 된 항목은 체크하고, 제외가 된 항목은 취소선을 긋습니다. 남은 항목은 미검증으로 둔 채 PR 머지와 함께 이슈가 닫힙니다. 검증 완료가 하나도 없으면 PR 없이 이슈를 닫습니다.

재조사는 한 번만 합니다. 닫힌 이슈의 미검증 항목은 다시 열지 않습니다. 다만 `verify:` 이슈가 아직 열려 있는 동안 출처 위계가 넓어지면, 그 이슈의 미검증 항목을 새 위계로 다시 봅니다.

## 출처 상태

린트는 게시된 출처가 아직 살아 있는지를 아래 기준으로 봅니다. `npm run source-status`가 이 표를 읽어 해당하는 곳을 모읍니다. 이 절의 두 표(`source-status`, `bot-blocked-hosts`)의 열 이름이나 검사 이름을 바꾸면 스크립트(`tools/source-status/cli.ts`)도 함께 고쳐야 합니다.

<!-- table: source-status -->

| 검사       | 기준  | 뜻                                                                              |
| ---------- | ----- | ------------------------------------------------------------------------------- |
| `url`      | —     | 인용한 참고문헌 엔트리의 `url`이 리다이렉트를 따라간 뒤 2xx로 응답하지 않습니다 |
| `verified` | `180` | 페이지의 `verified`에서 기준 일수가 지났습니다                                  |

브라우저로는 열리는데 자동 요청이 실패하는 출처는 원인마다 따로 셉니다. `SKIP` 줄은 `확인 불가`로 찍히고, 그것만으로는 exit 1이 아닙니다.

- 봇 차단: 아래 봇 차단 호스트 표의 403은 `SKIP url-blocked`입니다.
- 중간 인증서 누락: 서버가 중간 인증서를 보내지 않아 인증서 검증에 실패하면, 브라우저처럼 leaf 인증서의 AIA 주소에서 중간 인증서를 받아 한 번 더 묻습니다. 받은 중간 인증서도 신뢰하는 루트까지 이어져야 통과하므로 검증은 느슨해지지 않습니다. AIA 주소가 없거나 다시 물어도 실패하면 `url` FAIL입니다.
- 시간 초과: 제한 시간(15초) 안에 답이 없거나 연결이 시간 초과되면 한 번 더 묻습니다. 그래도 답이 없으면 `SKIP url-timeout`입니다.

연결 거부, DNS 실패, 404 같은 그 밖의 실패는 `url` FAIL입니다.

### 봇 차단 호스트

아래 호스트는 자동 요청에 403을 돌려주지만 브라우저로는 열립니다. User-Agent를 바꿔도 풀리지 않습니다. 목록은 하위 도메인까지 덮습니다.
