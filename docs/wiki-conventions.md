# 위키 규약

위키 페이지의 표기 규칙입니다. 규칙마다 판정하는 쪽을 적습니다.

- `검사 <id>`: 콘텐츠 검사기가 판정합니다. PR마다, 그리고 main에 머지될 때 CI가 돌립니다.
- `리뷰`: 읽어 봐야 판정되는 규칙입니다. `/code-review`와 사람 리뷰가 봅니다.

검사기는 이 문서의 표를 직접 읽습니다. 표 바로 위의 `<!-- table: <이름> -->` 주석이 표 이름이고, 표의 열 이름을 바꾸면 검사기도 함께 고쳐야 합니다.

## 검사기

```sh
npm run check:content
```

검사마다 `OK`·`FAIL`·`SKIP` 한 줄을 찍고, 그 아래에 위반 위치를 `<파일>:<줄>: <내용>` 꼴로 찍습니다. FAIL이 하나라도 있으면 exit 1입니다. 파일 검사는 빌드가 실패해도 돌고, 산출물 검사(`output`)만 SKIP합니다.

`npm run check:content -- --no-build`는 사이트 빌드와 산출물 검사(`build`, `output`)를 SKIP하고 파일 검사만 돌립니다. 파일 검사의 결과는 옵션이 없을 때와 같습니다. 도해처럼 고치고 검사하기를 되풀이할 때 쓰고, PR 전 확인은 옵션 없이 돌립니다.

## 페이지 타입과 프론트매터

- 페이지 타입은 개념 페이지와 표준 페이지 둘입니다. 표준 페이지에만 있는 필드가 하나라도 있으면 표준 페이지로 봅니다. `검사 frontmatter`
- 표준 페이지의 주제는 출판물 하나입니다. 출판물은 발행기관 하나가 판(연도, 버전, 릴리스)을 매겨 펴내는 자료로, 문서 하나, 총제목 아래 여러 부로 나오는 시리즈(ISO 26262), 릴리스로 함께 나오는 문서 묶음(AUTOSAR Classic Platform)이 여기에 듭니다. 같은 계열의 딸린 문서(배치 지침 등)도 그 출판물에 듭니다. 시리즈의 한 부나 딸린 문서라도 판을 따로 매겨 펴내면 그 자체로 출판물입니다(ISO 11898-1). 릴리스 안의 문서처럼 묶음의 판을 따르는 문서는 그 묶음의 일부입니다(AUTOSAR의 SOME/IP 명세). 여러 기관이 번호 하나로 함께 펴내는 표준(ISO/SAE 21434)은 발행기관 하나로 봅니다. `리뷰`
- 머리말이 정의하는 대상이 그 출판물이거나 그 출판물로만 정해지는 틀(프레임워크, 모델, 프로토콜)이면 표준 페이지입니다. 예: CVSS, CMMI, TUF, Uptane, LwM2M `리뷰`
- 아래는 개념 페이지입니다. `리뷰`
  - 출판물 안의 일부: AUTOSAR OS, SOME/IP, SOME/IP-SD, CAN FD 프레임, 100BASE-T1, RXSWIN
  - 발행기관이나 출판물 계열 둘 이상에 걸친 기술: CAN(Bosch와 ISO), MQTT(OASIS와 ISO/IEC 20922)
  - 판이 없는 RFC 여럿으로 정해지는 기술: TLS, TCP
  - 표준 페이지가 따로 있는 출판물이 정한 개념: SOTIF(ISO 21448), PTP(IEEE 1588)
- 기준을 고른 까닭은 [ADR 0011](adr/0011-standard-page-by-publication.md)에 있습니다.
- 아래 표에 없는 필드는 위반입니다. `검사 frontmatter`
- 대문(`index.md`)과 태그 표시 이름 파일(`tags/`)은 `title`만 둡니다. `검사 frontmatter`
- `tags`에는 `content/tags/`에 표시 이름 파일이 있는 태그만 씁니다. 주제에 속하면 `<구역>/<주제>`, 어느 주제에도 속하지 않으면 `<구역>`을 답니다. `검사 frontmatter`

| 필드        | 개념 | 표준 | 형식        |
| ----------- | ---- | ---- | ----------- |
| `title`     | 필수 | 필수 | 문자열      |
| `tags`      | 필수 | 필수 | 태그 목록   |

형식은 다음과 같습니다.

- 문자열: 비어 있지 않은 문자열
- 문자열 목록, 태그 목록: 비어 있지 않은 문자열의 목록
- 날짜: `YYYY-MM-DD`. `verified`는 페이지의 모든 주장을 함께 마지막으로 검증한 날입니다. 새 페이지를 만들 때와 모든 주장을 다시 검증할 때만 오늘로 바꾸고, 주장 일부를 더하거나 고칠 때는 그대로 둡니다.
- 연도: 네 자리 정수. `edition`은 현행판의 연도입니다. 대체한 판 없이 폐지된 표준은 마지막 판의 연도입니다([표준의 판](wiki-verification.md#표준의-판)).
- 상태: 아래 표의 값 가운데 하나

<!-- table: status -->

| 값        | 뜻                                     |
| --------- | -------------------------------------- |
| `유효`    | 현행판이 유효합니다                    |
| `개정 중` | 현행판이 유효하고 개정이 진행 중입니다 |
| `폐지`    | 폐지되어 더는 유효하지 않습니다        |

발행기관의 상태 표시는 이렇게 대응합니다. 발행기관이 활성 목록에서 뺀 상태(IEEE Inactive-Reserved·Inactive-Withdrawn, NIST Withdrawn 등)는 `폐지`입니다. 유효한 문서로 계속 펴내되 개정만 멈춘 상태(SAE Stabilized 등)는 `유효`입니다. 예: `ieee-1028`, `sae-j3061` `리뷰`

## 절

- 절 제목은 `##`부터 `###`까지 씁니다. `리뷰`
- `###`은 한 `##` 절의 내용이 같은 축으로 나뉘는 하위 주제 둘 이상일 때 씁니다. 하위 절을 하나만 두지 않습니다. 표나 도해 없이 한두 문장뿐인 내용에는 하위 절 제목을 달지 않습니다. 다만 같은 축으로 나란히 둔 하위 절 가운데 하나가 짧은 것은 둡니다. `##` 제목 바로 아래에 `###`을 두지 않고 하위 주제를 묶는 문장을 먼저 두되, 묶을 말이 없으면 `###`으로 나누지 않습니다. `리뷰`
- 개념 페이지와 표준 페이지는 첫 `##` 앞에 제목 없는 머리말을 둡니다. 머리말은 콜아웃이나 목록 같은 블록이 아니라 문단으로 시작하고, 여러 문단이어도 됩니다. HTML 주석은 머리말로 치지 않습니다. `검사 lead`
- 머리말은 주제를 정의합니다. 표나 도해로 시작하지 않습니다. `리뷰`
- 개념 페이지는 머리말 → 내용 절 → 비교 절 순서로 씁니다. 내용 절은 페이지가 다루는 것에 따라 정합니다. `리뷰`
- 비교 절은 다른 개념과 비교할 대상이 분명할 때만 두고, 제목에 비교 대상을 드러냅니다. 예: `CAN과의 차이` `리뷰`
- 한계는 그 한계를 낳는 동작을 설명하는 내용 절에 씁니다. `리뷰`
- 표준 페이지는 머리말 → 범위 → 개정 이력 순서로 씁니다. 첫 두 `##`가 범위, 개정 이력이어야 하고, 제목은 앞머리만 맞으면 됩니다. 예: `개정 이력(2024)` `검사 section`
- 다른 표준과의 비교는 개정 이력 뒤에 두고, 제목에 비교 대상을 드러냅니다. 예: `Bosch CAN FD와의 차이` `리뷰`
- 영어 용어가 든 제목(`title`과 절 제목)은 sentence case로 씁니다. 첫 글자가 라틴 문자면 대문자로 쓰고, 나머지는 고유 이름과 표준·규격 이름이 아니면 소문자로 씁니다. 정식 표기가 소문자로 시작하는 고유 이름이 첫 낱말이면 그 표기를 그대로 둡니다. 예: `Credit-based shaper`, `Context switch`, `Dominant와 recessive`, `OSEK hook 루틴`, `x86` `리뷰`

## 마침표

- 문장은 산문 문단, 목록 항목, 표 셀 어디서든 마침표로 끝납니다. 명사구로 끝나는 목록 항목과 표 셀은 문장이 아니라 보지 않습니다. `리뷰`

마침표 규칙은 "다"로 끝나는 명사(라이다, 혼다 등)를 문장으로 잘못 볼 위험이 있어 리뷰가 봅니다.

## 출처 문장

- 페이지 글은 출처의 사실을 자기 말로 다시 쓰고, 출처의 문장을 직역하지 않습니다. 출처의 이용 조건은 번역과 수정을 허락하지 않지만, 사실은 보호 대상이 아닙니다. `리뷰`

## 인용

- 인용은 `[@키]`로 쓰고, 대괄호 하나에 키 하나만 넣습니다. `검사 citation`
- 한 자리에 인용이 여럿이면 `[@키1][@키2]`로 이어 쓰고, 키가 페이지에서 처음 나온 순서대로 씁니다. 인용 번호는 키가 처음 나온 순서로 매겨지므로, 그래야 번호가 `[1][3]`처럼 오름차순으로 렌더됩니다. 한 문단 안에서 사이에 공백, 줄바꿈, HTML 주석만 있어도 한 자리로 봅니다. `검사 citation`
- 인용 자리는 쉼표 앞, 마침표 뒤입니다. 예: `A이고[@키1], B다.[@키2]`. 쉼표 바로 뒤(사이에 공백이 있어도)나 마침표 바로 앞의 인용은 위반입니다. `검사 citation`
- 같은 출처가 연달아 뒷받침하는 문장과 절은 마지막 것에만 인용을 답니다. 예: `A이고, B다. C다.[@키]`. 문단을 넘겨 묶지 않습니다. 목록은 전체를 문단 하나로 보고, 목록을 여는 문장과는 다른 문단으로 봅니다. 콜아웃은 하나하나를 문단 하나로 봅니다. `리뷰`
- 목록을 쪼개거나 항목을 목록 밖으로 옮기면 인용을 다시 답니다. `리뷰`
- 모든 행이 같은 출처인 표는 표를 여는 문장에 인용을 한 번 답니다. 셀에는 달지 않습니다. 디스플레이 식을 소개하는 문장에 인용을 다는 것과 같습니다. `리뷰`
- 행마다 출처가 다른 표는 모든 행의 마지막 셀 끝에 인용을 답니다. 행은 따로 읽히므로, 같은 출처가 이어지는 행도 묶지 않습니다. `리뷰`
- 표를 쪼개거나 행을 표 밖으로 옮기면 인용을 다시 답니다. `리뷰`
- 인용 키는 `<발행기관>-<식별자>-<연도>` 꼴의 영문 소문자 kebab-case이고, 연도는 네 자리입니다. 예: `iso-11898-1-2024`. 발행기관의 자료가 아닌 원 논문, 원 저자의 글, 서베이, 연구소·대학의 자료는 `<첫 저자 성>-<제목 핵심어>-<연도>`로 씁니다. 예: `liu-hard-real-time-1973`, `sha-priority-inheritance-1990` `검사 citation`
- 참고문헌은 엔트리 하나를 파일 하나(`bib/<키>.bib`)로 둡니다. 파일 이름과 엔트리 키가 같아야 합니다. `검사 citation`
- 인용한 키는 모두 `bib/`에 엔트리가 있어야 합니다. `검사 citation`
- 엔트리에는 아래 `bib-fields` 표의 필드가 모두 있어야 합니다. `검사 citation`
- 보고서(`@techreport`)와 학위 논문(`@phdthesis`) 엔트리에는 아래 `bib-type-fields` 표의 필드도 있어야 합니다. `검사 citation`
- 한 문서에는 엔트리를 하나만 둡니다. 정규화한 `url`이 같은 엔트리가 둘 이상이면 위반입니다. 정규화 기준과 한 페이지의 여러 절을 인용하는 꼴은 [열린 PR과 겹치는 파일](#열린-pr과-겹치는-파일)에 있습니다. `검사 citation`
- 인용은 `[1]` 같은 번호로 렌더되고, 인용한 페이지 하단에 참고문헌이 붙습니다. `검사 output`
- 본문의 출처 표시는 [위키 검증의 좁혀 쓰기](wiki-verification.md#좁혀-쓰기)를 따릅니다. 인용 마커와 달리 문단을 넘어 묶는 출처 표시의 단위(출처 구간)도 거기에 있습니다. 여러 발행기관이 뒷받침하는 일반 명제에 어느 출처를 몇 개 인용하는지도 거기에 있습니다. `리뷰`

<!-- table: bib-fields -->

| 필드      | 형식   |
| --------- | ------ |
| `title`   | 문자열 |
| `url`     | URL    |
| `urldate` | 날짜   |

`urldate`는 접근일입니다. URL은 `http://`나 `https://`로 시작합니다.

<!-- table: bib-type-fields -->

| 엔트리 타입  | 필드   | 값               |
| ------------ | ------ | ---------------- |
| `techreport` | `type` | 보고서의 종류    |
| `phdthesis`  | `type` | 학위 논문의 종류 |

엔트리 타입(`@techreport`)과 `type` 필드는 다릅니다. `type` 필드는 참고문헌에서 보고서는 번호 앞에, 학위 논문은 제목 뒤에 찍히고, 비어 있으면 엔트리 타입 이름(`techreport`)이 대신 찍힙니다. 값은 [IEEE Reference Guide](https://journals.ieeeauthorcenter.ieee.org/wp-content/uploads/sites/7/IEEE_Reference_Guide.pdf)의 보고서·학위 논문 꼴을 따릅니다.

- 보고서는 발행기관이 적은 종류를 IEEE 약어(Technical → Tech., Report → Rep.)로 줄여 씁니다. 예: `Tech. Rep.`, `Tech. Memo.`, `Special Rep.`. 종류가 드러나지 않으면 `Tech. Rep.`입니다. `리뷰`
- 번호에 계열 이름이 든 보고서는 계열 이름을 `type`에, 나머지를 `number`에 둡니다. 예: `type = {NIST Special Publication}`, `number = {800-53 Revision 5}`. 그래야 계열 이름이 두 번 찍히지 않습니다. 계열 이름은 줄이지 않고 원문대로 씁니다. 예: `Planning Report`, `CS-Report` `리뷰`
- 학위 논문은 원문이 적은 대로 `Ph.D. thesis`나 `Ph.D. dissertation`으로 씁니다. 학위만 보고 고르지 않습니다. `리뷰`

열린 PR이 같은 키의 엔트리를 더했는지는 [열린 PR과 겹치는 파일](#열린-pr과-겹치는-파일)대로 봅니다.

## 용어

- 원어가 실무에서 자연스러운지 먼저 봅니다. 그다음 정착한 한국어, 정착한 음차 순으로 고릅니다. `리뷰`
- 표기를 정하기 전에 [용어 표기 결정](wiki-terms.md) 목록을 보고, 결정이 있으면 따릅니다. `리뷰`
- 선택이 갈리면 `term:` 이슈로 올립니다. 대화에서 소유자가 이미 정한 표기는 `term:` 이슈 없이, 그 결정을 적용하는 이슈나 PR에 적습니다. `리뷰`
- `term:` 이슈의 결정은 본문을 고치지 않고 "소유자 결정:"으로 시작하는 댓글로 남깁니다. 처음 올린 뒤 더하는 항목도 그 댓글에 적습니다. 본문에 남은 원래 질문과 추천, 댓글의 시점이 결정의 맥락이 됩니다. `리뷰`
- 이슈든 PR이든 소유자가 표기를 정하면, 그 결정을 적용하는 PR이 목록에 한 줄을 더합니다. 결정을 적은 댓글이나 본문은 그 자리에 그대로 두어, 목록의 번호로 까닭을 찾아갈 수 있게 합니다. `리뷰`

## 약어

- 약어는 페이지에서 처음 나올 때 풀이를 병기합니다. 예: `CAN(Controller Area Network)`. 풀이 문자열은 [용어 표기 결정](wiki-terms.md) 목록을 따릅니다. `리뷰`
- [풀이하지 않는 약어](wiki-abbreviations.md) 목록의 약어는 풀이하지 않습니다. 널리 쓰이는 약어이거나, 풀이하면 오히려 읽기 어려운 이름입니다. `리뷰`
- 조직 이름이거나 표준 번호의 앞머리로 굳은 약어도 풀이하지 않고 목록에 올립니다. 예: `RS-485`, `RFC 1122`. 종류는 조직 이름이면 `조직`이고, 표준 번호의 앞머리이거나 조직 이름이 그대로 표준 이름으로도 쓰이면(AUTOSAR, OSEK/VDX) `표준·규격 이름`입니다. 발행기관인지는 종류에 담지 않습니다. `리뷰`
- 자기 페이지(개념 페이지나 표준 페이지)가 있는 약어와, 열린 `ingest:` 티켓의 `## Pages` 표에 자기 페이지가 계획된 약어는 그 페이지에서만 풀이합니다. 다른 페이지에서는 풀이하지 않고, 처음 나올 때 그 페이지로 한 번 링크합니다. 예: CAN은 `can`에서만 풀이하고, 다른 페이지에서는 `[[can|CAN]]`으로 겁니다. ACK는 `[[can-acknowledgement|ACK]]`로, CVSS는 `[[common-vulnerability-scoring-system|CVSS]]`로 겁니다. `리뷰`
- 계획만 된 페이지는 아직 링크하지 않습니다. 풀이만 빼고, 링크는 페이지가 생긴 뒤 린트가 채웁니다. 예: CAN FD(`can-fd`), DLC(`data-length-code`) `리뷰`
- 약어를 머리말에서 풀이하는 다른 페이지로 거는 링크도 풀이를 대신합니다. 링크 글자에 그 약어가 든 링크가 약어보다 먼저 나오면, 그 페이지에서는 약어를 풀이하지 않습니다. 절로 거는 링크는 대상 페이지가 그 절에서 풀이해도 됩니다. 예: `[[autosar-icu-driver|ICU Driver]]`는 대상 머리말이 ICU를 풀이하므로 ICU를 풀지 않습니다. `리뷰`
- 모듈 이름과 모듈 약어의 풀이 안에 든 약어는 처음 나온 것으로 세지 않습니다. 이름은 그대로 두고, 그 약어가 본문 산문에 혼자 처음 쓰이는 자리에서 풉니다. 예: `L-SDU Router(LSduR)`, `CanTp(CAN Transport Layer)`로 쓰고, 뒤의 `L-SDU(Link Layer Service Data Unit)를 라우팅`에서 풉니다. `리뷰`
- 그 약어가 본문 산문에 혼자 쓰이는 자리가 없으면, 이름이 처음 나오는 자리에서 이름 안에서 풉니다. 도해 이름표에만 혼자 나오는 것은 혼자 쓰이는 자리로 치지 않습니다. 예: `GPT(General Purpose Timer) Driver` `리뷰`
- 이름 전체를 괄호로 풀어 쓰지 않습니다. `**DIO Driver**(Digital Input/Output Driver)`가 아니라 `**DIO Driver**`로 쓰고, DIO는 위 두 규칙대로 풉니다. `리뷰`
- 위 세 규칙은 풀이하지 않는 약어와, 링크가 풀이를 대신하는 약어의 규칙을 바꾸지 않습니다. 예: `CAN Driver`의 CAN은 풀지 않고, 그 페이지의 첫 `[[can|CAN]]` 링크가 맡습니다. `리뷰`

## 단위

- 수치와 라틴 문자 단위는 띄워 씁니다. 식 안에서는 `\,`로 띄웁니다. 예: `500 kbit/s`, `$0.2\,\mathrm{V}$` `리뷰`
- 수치와 한글 단위는 붙여 씁니다. 예: `8바이트` `리뷰`

단위 규칙은 오탐 위험이 있어 리뷰가 봅니다.

## 코드 표기

- 진법 표기와 바이트 열·비트 열은 백틱으로 씁니다. 예: `0x7F`, `0b1010`, `7Fh`, `01 02 03 04`, `0101 1000`. 옮겨 적는 값임을 드러내고, 본문 글꼴 Pretendard가 `0x`의 `x`를 `×`로 그리는 것을 코드 글꼴로 피합니다. `리뷰`
- 코드나 설정에 그대로 적는 이름도 백틱으로 씁니다. 함수, C 타입, 설정 파라미터와 그 값, 레지스터와 그 필드가 해당합니다. 예: `htonl`, `uint32_t`, `ComSignalEndianness`, `BIG_ENDIAN`, `CAN_BTR`, `SCTLR_ELx.EE`. 옮겨 적는 이름임을 드러냅니다. `리뷰`
- 프로토콜이 정한 메시지·서비스·필드·파라미터 이름과 데이터 타입 이름은 평문으로 둡니다. 표준이 camelCase로 적은 이름도 평문입니다. 예: DiagnosticSessionControl, OfferService, Message ID, suppressPosRspMsgIndicationBit, E_OK, uint8. 코드가 아니라 표준 문서의 용어입니다. `리뷰`
- 둘을 가르는 기준은 생김새가 아니라 의미입니다. 그 글자를 그대로 코드나 설정에 적는지 봅니다. 칩 이름, IP 이름, 모듈 이름과 풀이를 단 개념 약어는 평문입니다. 예: bxCAN, M_CAN, Dcm, CanTp, BRP(Baud Rate Prescaler). 대문자와 밑줄로 된 이름이 모두 코드는 아닙니다. `리뷰`
- 식 안의 이름은 수식 절의 규칙대로 `\mathrm`으로 씁니다. 식 안에서는 백틱이 코드로 렌더되지 않습니다. `리뷰`

## 수식

- 양 사이의 관계(합·차·곱·비·비교)와 양이 만족해야 하는 조건(판정 조건, 두 끝이 있는 범위)은 수식으로 씁니다. 상수와의 비교 조건도 포함합니다. 사양값(`최대 1 Mbit/s`, `1 Mbit/s까지 지원`)과 전형값(`약 3.5 V`, `약 0.5 VCC`)은 글로 둡니다. 기기나 포맷이 갖는 값의 범위(출력 전압, 공통 모드 범위, 데이터 길이)는 사양값이라 글로 둡니다. 예: `±8 V`, `2~3 V`. 표준이나 기능을 쓰는 조건인 범위는 식으로 씁니다. 예: 비트율 범위 `리뷰`
- 기호는 위키 전체가 같은 것을 씁니다. 규범 표준에 기호가 있으면 따르고, 없으면 일반 표기를 씁니다. 데이터시트마다 다른 기호를 옮기지 않습니다. 기호는 페이지에서 처음 쓸 때 말 뒤에 붙여 정의합니다. 예: `차동 전압 $V_\mathrm{diff}$`. 아래첨자가 본문 용어를 그대로 담아 기호만으로 뜻이 읽히면 정의하지 않습니다. 예: `$V_\mathrm{CAN\_H}$` `리뷰`
- 식 안의 용어와 이름은 본문 표기 그대로 `\mathrm`으로 씁니다. 예: `\mathrm{VCC}`, `V_\mathrm{CAN\_H}`. 기울어진 글자는 변수에만 씁니다. `리뷰`
- 식 안의 단위는 `\mathrm`으로 쓰고, 수치와 가는 공백(`\,`)으로 띄웁니다. 예: `0.2\,\mathrm{V}` `리뷰`
- 식은 인라인(`$…$`)으로 씁니다. 식의 한쪽 변에 덧셈·뺄셈으로 나뉘는 항이 셋 이상이거나, 분수(`\frac`로 쓸 나눗셈)가 들면 디스플레이(`$$…$$`)로 씁니다. `리뷰`
- 디스플레이 식은 표처럼 주장을 담을 수 있습니다. 식을 소개하는 앞 문장은 식이 무엇을 주는지 말하고, 식에 새로 나오는 기호를 정의하고, 인용을 답니다. `리뷰`

## 슬러그

- 슬러그는 파일 이름에서 `.md`를 뺀 것이고, 영문 소문자 kebab-case입니다. `검사 namespace`
- 페이지는 `content/` 바로 아래에 둡니다. 폴더를 쓰지 않습니다. 태그 표시 이름 파일(`content/tags/`)만 예외입니다. `검사 namespace`
- 슬러그, `aliases`, 위키링크 대상은 한 네임스페이스입니다. alias를 슬러그로 바꾼 값이 자기 슬러그를 포함한 페이지의 슬러그나 다른 페이지의 alias와 겹치면 안 됩니다. 슬러그로 바꾸면 소문자가 되므로 `CAN controller`는 `can-controller`와 겹칩니다. `검사 namespace`
- 제목(`title`)과 같은 alias를 두지 않습니다. 사이트에서 alias는 그 이름으로 오는 리다이렉트와 속성 표시만 하므로, 제목과 같으면 쓸모가 없습니다. `리뷰`

## 위키링크

- 위키링크 대상은 슬러그로만 씁니다. 표시 이름 없이 걸면 슬러그(앵커가 있으면 `슬러그 > 앵커`)가 그대로 링크 글자가 되므로, 이것이 대상의 `title`과 다르면 `[[슬러그|표시 이름]]`으로 씁니다. `검사 wikilink`
- 대상 페이지가 있어야 합니다. `검사 wikilink`
- 앵커가 가리키는 절이 있어야 합니다. `검사 wikilink`
- 다른 페이지의 개념이 처음 나오는 자리에 그 페이지로 위키링크를 겁니다. 그 페이지로 가는 링크가 이미 이 페이지에 있으면 더 걸지 않습니다. 약어 절의 "처음 나올 때 그 페이지로 한 번 링크"와 같습니다. 다만 하위 개념에 거는 절 링크는 그 페이지로 가는 링크와 따로 세고, 같은 하위 개념에는 한 번만 겁니다. 링크 글자와 가는 곳이 다른 링크는 독자에게 같은 링크가 되풀이된 것으로 보이지 않고, 머리말로 가는 페이지 링크는 하위 개념의 절로 데려가지 못하기 때문입니다. `리뷰`
- 링크에 절(`[[슬러그#절 제목|표시 이름]]`)을 붙일지는 링크가 거는 것에 따라 정합니다. `리뷰`
  - 대상 페이지의 주제 개념, 곧 머리말이 정의하는 개념을 거는 링크에는 붙이지 않습니다.
  - 대상 페이지의 한 절에서 정의되는 하위 개념을 거는 링크에는, 처음 거는 링크라도 그 절을 붙입니다. 예: `[[schedulability-analysis#이용률|이용률]]`. 머리말에서 정의되거나 여러 절에 걸쳐 나오는 개념이면 붙이지 않습니다. 하위 개념에 자기 페이지가 있으면 절 링크가 아니라 그 페이지로 겁니다.
  - 주제 개념과 그 하위 개념이 `X의 Y`처럼 붙어 나오면 Y에만 절 링크로 겁니다. 이 절 링크가 X의 페이지로 가는 링크를 겸합니다. 예: `AVB의 [[avb#SR 클래스|SR 클래스]]`
  - 링크가 든 문장이 다른 페이지의 한 부분을 가리키면(예: `…은 [[X#절 제목|X]]에서 다룬다`), 링크 글자가 주제 개념이어도 가리키는 내용이 한 절에 모여 있을 때 그 절을 붙입니다.
- 주장 없이 다른 페이지로 넘기는 안내 문장(예: `…은 [[X#절 제목|X]]에서 다룬다`)의 링크는 아래처럼 셉니다. `리뷰`
  - 주제 개념을 링크 글자로 쓴 절 링크는 X 페이지로 가는 링크를 겸합니다. `X의 Y`의 Y 절 링크가 겸하는 것과 같습니다.
  - 이런 링크가 있으면, X가 그 앞에 링크 없이 나와도 X 페이지 링크를 더 걸지 않습니다. 첫 등장 자리 규칙의 예외입니다.
  - 안내 문장의 링크가 페이지 링크(`[[X|X]]`)면 안내 문장을 지우고, 링크는 X가 처음 나오는 자리로 옮깁니다. 그 자리에 이미 링크가 있으면 더 걸지 않습니다.
  - 하위 개념을 링크 글자로 쓴 절 링크는 위 첫 등장 규칙대로 X 페이지로 가는 링크와 따로 셉니다.
- 같은 블록에 같은 페이지로 가는 링크가 또 있으면, 절 링크의 링크 글자는 그 페이지의 `title`이나 다른 링크의 링크 글자와 달라야 합니다. 같으면 같은 링크가 두 번 걸린 것으로 보여, 둘째 링크가 절로 간다는 것을 마우스를 올려야 압니다. 블록은 문단, 제목, 표의 행 하나입니다. 목록과 콜아웃은 그 안의 문단마다 따로 봅니다. `검사 wikilink`
- 그때 절 링크는 절이 다루는 것에만 겁니다. 어느 페이지의 절인지 앞 문장에서 드러나지 않거나, 링크가 든 절의 제목이 링크 글자와 같아 지금 읽는 절로 읽힐 때만 링크 앞에 `<제목>의`를 적습니다. 예: `[[flexray|FlexRay]]의 정적 세그먼트는 … 세그먼트의 구성은 [[flexray#통신 사이클|통신 사이클]]에서 다룬다`. 앞 문장의 말을 되풀이하지 않게 씁니다. `리뷰`
- 태그 목록은 `[[tags/<태그>|표시 이름]]`으로 겁니다. 표시 이름 파일이 있는 태그만 걸 수 있습니다. `검사 wikilink`
- 표 셀 안에서는 표시 이름 앞의 `|`를 `\|`로 씁니다. 예: `[[checksum\|체크섬]]`. `|`를 그대로 두면 prettier가 셀 경계로 보고 `[[checksum | 체크섬]]`으로 갈라 열을 하나 더 만듭니다. `검사 wikilink`

## 중복

- 개념 하나의 설명은 주인 페이지(`CONTEXT.md`)가 맡습니다. 다른 페이지는 그 개념을 한 문장과 링크로만 다룹니다. `리뷰`
- 같은 인용으로 같은 주장을 두 페이지 이상에서 하면 주인 페이지에만 두고, 나머지 페이지는 한 문장과 링크로 줄입니다. 페이지마다 따로 읽힌다는 것은 남길 이유가 되지 않습니다. `리뷰`
- 주인 페이지로 가는 링크는 그 페이지에 한 번 있으면 됩니다. 줄인 한 문장 안에 다시 걸 필요는 없습니다. 이미 한 문장으로 줄어 있는 주장을, 주장 없이 링크만 하는 문장으로 바꾸지 않습니다. `리뷰`

## 강조

- 강조(`**`)는 용어를 정의하는 자리에만 씁니다. 머리말에서 주제를 정의하는 문장의 주제어와, 본문에서 새로 정의되는 하위 용어가 여기에 해당합니다. 정의하는 자리는 정의 문장(`X는 …이다`, `…을 X라 한다`, `A는 X를 …로 정의한다`, `…을 X라 부른다`)과 정의 목록 항목(`- X: …`)입니다. 이미 정의한 것에 다른 이름을 붙이는 `…라고도 부른다`는 정의하는 자리가 아닙니다. 같은 용어는 한 페이지에서 한 번만 강조하고, 한 문단에 강조가 여럿이어도 됩니다. 주제어에 풀이가 붙으면 풀이는 강조 밖에 둡니다. 예: `**CAN ACK**(Acknowledgement)는`. 강조 안에는 위키링크를 넣지 않습니다. `리뷰`
- 강조는 렌더되어야 합니다. 닫는 `**` 앞이 문장 부호이고 바로 뒤에 조사가 붙으면 강조가 풀리지 않고 `**`가 그대로 보입니다. 예: `**CAN(Controller Area Network)**은`. 강조 범위를 줄이거나(`**CAN**(Controller Area Network)은`) 문장을 바꿉니다. `검사 emphasis`

## 표

- 같은 속성을 가진 항목이나 이름과 값의 짝이 넷 이상 이어지면 표로 씁니다. 예: 서비스와 SID의 짝 `리뷰`
- 표에 담을 값을 바로 뒤의 도해가 이미 보이면 표 대신 산문으로 씁니다. 도해의 글자는 페이지의 주장에 있어야 하므로, 산문은 표가 담던 주장을 모두 담습니다. `리뷰`
- 산문을 표로, 또는 표를 산문으로 바꾸는 것은 주장을 고치는 일이 아닙니다. 바꾼 곳의 인용 키 집합은 바꾸기 전과 같아야 합니다. `리뷰`

## 도해

- 도해는 출처를 근거로 새로 그립니다. 출처의 그림을 옮기지 않는 까닭은 [출처 문장](#출처-문장)과 같습니다. `리뷰`
- 도해는 SVG 파일 하나로 `content/diagrams/`에 두고 `![[diagrams/<파일 이름>.svg]]`로 넣습니다. 라이트·다크 두 테마가 같은 파일을 씁니다. `검사 wikilink`
- 도해의 글자와 수치는 위키 페이지의 주장에 있는 것만 씁니다. 도해를 넣는 페이지의 주장이 아니어도 됩니다. `리뷰`
- 도해는 그것이 나타내는 주장이 있는 문단 바로 뒤에 넣습니다. 여러 페이지에 맞는 도해는 파일 하나를 함께 씁니다. `리뷰`
- 파일 이름은 그림의 내용을 나타내는 영문 소문자 kebab-case입니다. 열린 PR이 같은 이름의 도해를 더했는지는 [열린 PR과 겹치는 파일](#열린-pr과-겹치는-파일)대로 봅니다. `리뷰`
- `<image>`나 `<feImage>`로 래스터나 외부 파일을 넣지 않습니다. `검사 svg`
- 배경은 칠하지 않습니다. 사이트 배경이 그대로 비쳐야 두 테마에서 읽힙니다. `리뷰`
- 테두리, 폭, 가운데 정렬은 사이트가 맡습니다(`quartz/styles/custom.scss`). SVG에는 그림을 두르는 틀을 그리지 않습니다. `리뷰`
- 사이트는 `viewBox` 1단위를 `0.85rem / 12`로 그립니다. 그래서 `font-size="12"` 글자는 본문의 0.85배로, 도해 폭과 상관없이 크기가 같습니다. 틀 안쪽보다 넓은 도해만 틀에 맞춰 줄어듭니다(`quartz/styles/custom.scss`). `리뷰`
- 루트 `<svg>`에 `viewBox`를 둡니다. `viewBox`는 그림의 상하좌우 여백이 같게 잡습니다. 사이트는 `viewBox`를 틀 가운데에 놓으므로, 그림이 `viewBox` 안에서 쏠리면 틀 안에서도 쏠려 보입니다. 검사는 여백의 차가 허용치를 넘으면 옮긴 `viewBox`를 알려 줍니다. 허용치와 그 근거는 `tools/check-content/diagram-margin.ts`에 있습니다. `검사 svg`
- 그림은 `viewBox` 안에 둡니다. `viewBox` 밖은 사이트에서 그려지지 않습니다. 검사는 `viewBox` 밖에 칠한 것이 있으면 넘친 변과 양을 알려 주고, 이때는 여백 치우침을 알리지 않습니다. 밖을 얼마나 넓혀 보는지는 `tools/check-content/diagram-margin.ts`에 있습니다. `검사 svg`
- 글자는 Pretendard로 그립니다. 루트 `<svg>`에 `font-family="Pretendard, sans-serif"`와 `text-rendering="geometricPrecision"`을 두고, `<style>`에서 사이트와 같은 Pretendard CSS를 `@import`로 불러옵니다(넣을 줄은 검사가 알려 줍니다). SVG는 `<object>`로 들어가 별도 문서로 그려지므로 사이트의 웹 폰트를 물려받지 못합니다. 브라우저가 검사와 같은 폰트로, 글자 폭을 픽셀에 맞춰 반올림하지 않고 그려야 검사가 잰 여백이 독자가 보는 여백과 맞습니다. `검사 svg`
- 루트 `<svg>`에 `font-variant="none"`을 두어 합자를 끕니다. 끄지 않으면 Pretendard가 `0x`의 `x`를 `×`로 그리는 때가 있습니다. 예: `ID 0x8100`. 숫자·대문자 옆의 하이픈, 대시, 콜론(`15765-2`, `10:30`)이 조금 내려가는 것은 감수합니다. 두 동작이 같은 기능에 묶여 있어 하나만 끌 수 없습니다. `검사 svg`

### 도해의 색

도해는 `<object>`로 들어가 별도 문서로 그려지므로 사이트 테마를 모릅니다. 그래서 SVG는 색을 토큰으로 쓰고, 사이트가 현재 테마의 값을 넣습니다(`plugins/diagram-theme`). 스크립트가 돌지 않는 곳(SVG 파일을 직접 열 때, 피드 리더)에서는 대체값으로 그려집니다.

- SVG의 색은 표현 속성 안에 `var(--<이름>, <대체값>)`으로 씁니다. 예: `fill="var(--ink, #727981)"`. 이름은 아래 표에 있어야 하고, 대체값은 그 행의 대체값과 같아야 합니다. 이 꼴 밖에는 `none`, `transparent`, `inherit`, 그라디언트 참조(`url(#id)`)만 씁니다. `검사 svg`
- SVG 안에서 사용자 정의 속성(`--x: …`)을 선언하지 않습니다. 여백 검사가 쓰는 래스터라이저(sharp에 든 librsvg)는 선언을 무시하고 대체값으로만 그려, 선언한 값은 검사와 브라우저에서 다르게 그려집니다. `검사 svg`
- 루트 `<svg>`에 `fill`을 둡니다(토큰이나 `none`). 두지 않으면 색을 적지 않은 도형과 글자가 검정으로 그려져 다크 테마에서 보이지 않습니다. `검사 svg`
- 범주 도형은 그 색의 면(`<색>-tint`)과 폭 1.5 테두리(`<색>`)로 칠하고, 안의 글자는 `on-fill`로 씁니다. `리뷰`
- 기본 범주와, 범주가 하나뿐인 도해의 닫힌 도형은 `surface` 면과 `ink` 외곽선으로 그립니다. 안에 다른 도형을 담는 틀(그룹 틀, 영역 경계)은 칠하지 않습니다. `리뷰`
- 그 밖에는 채움 밖의 글자를 `text`, 선·화살표·외곽선을 `ink`, 범주 색의 선을 `<색>`으로 씁니다. 점이나 화살촉처럼 글자를 담지 않는 작은 표지는 그 선과 같은 색으로 채웁니다. `리뷰`
- 범주는 색만으로 구분하지 않고 라벨로도 적습니다. `리뷰`
- 범주 색은 구분할 것이 있을 때만 씁니다. 범주가 하나뿐이면 범주 색을 쓰지 않습니다. 범주가 여럿이면 기본이 되는 범주(가장 많거나 배경 역할을 하는 것)에는 쓰지 않고 나머지에만 씁니다. `리뷰`
- 색으로 나누는 것은 뜻이 다른 범주(예: 요청과 응답)이거나, 같은 것을 그림 안의 여러 자리에서 따라가게 할 때(예: 바이트 순서의 각 바이트)뿐입니다. 층이나 순서처럼 위치만 다른 것은 색으로 나누지 않습니다. `리뷰`
- 한 페이지에 들어가는 도해끼리는 같은 개념을 같은 색으로 씁니다. `리뷰`
- 반투명(`opacity`, `fill-opacity`)으로 색을 바꾸지 않습니다. 대비가 표의 값과 달라집니다. `리뷰`

### 도해의 모양

- 선 두께는 1(보조선), 1.5(도형, 화살표), 3(강조: 신호 파형, 데이터 곡선)만 씁니다. `검사 svg`
- 점선은 두 가지입니다. `검사 svg`는 값이 둘 중 하나인지, 선 두께와 짝이 맞는지 봅니다.
  - 보조 점선 `3 3`: 폭 1인 기준선, 눈금, 경계, 지시선
  - 윤곽 점선 `5 4`: 폭 1.5 이상인 틀, 선택·조건부 요소, 대기 구간, 간접 흐름, 계열을 구분하는 선
- `<rect>`의 모서리 반경(`rx`, `ry`)은 0과 2만 씁니다. `검사 svg` 맞붙는 칸(비트 필드, 바이트 칸)과 축 위에 이어지는 구간은 둥글면 틈이 생긴 것처럼 보이므로 0이고, 그 밖의 상자는 0이나 2입니다. `리뷰`
- 글자 크기는 11 이상입니다. `baseline-shift`나 `dy`로 옮긴 첨자 `<tspan>`만 9 이상입니다. `검사 svg`
- 같은 줄의 두 상자 사이 칸에 글자만 있으면, 그 글자는 잉크의 세로 중심을 상자의 세로 중심에 맞춥니다. `_`처럼 baseline 쪽에 앉는 구분자는 글자 대신 상자 세로 중심의 선으로 그립니다. 칸에 화살표 같은 다른 그림이 있으면 글자는 그 라벨이므로 이 규칙 밖입니다. 한쪽 상자에 붙인 라벨도 이 규칙 밖입니다. 검사는 세로 중심이 같은 두 `<rect>` 사이 칸의 가운데에 놓이고 어느 상자에도 들지 않는 글자를 봅니다. 허용치와 그 근거는 `tools/check-content/source-checks.ts`에 있습니다. `검사 svg`

## 열린 PR과 겹치는 파일

동시에 열린 PR끼리 같은 경로의 bib 엔트리나 도해를 따로 더하기도 합니다. bib 엔트리나 도해를 더한 브랜치는 push 직전에, 열린 PR 가운데 같은 경로의 파일을 더한 것이 있는지 봅니다. 아래 명령은 이 브랜치가 더한 파일마다 그 파일을 건드리는 열린 PR을 `<파일> #<PR>`로 찍습니다. 자기 PR은 빼고 봅니다. `리뷰`

```sh
git fetch origin
join <(git diff --name-only --diff-filter=A origin/main...HEAD -- bib/ content/diagrams/ | sort) \
  <(gh pr list --state open --limit 200 --json number,files \
      --jq '.[] | .number as $n | .files[] | "\(.path) #\($n)"' | sort)
```

찍힌 PR이 있으면 상대 파일을 `git fetch origin pull/<PR>/head`와 `git show FETCH_HEAD:<파일>`로 봅니다.

bib 엔트리는 두 파일의 정규화한 `url`만 비교합니다. 정규화는 스킴(`http`·`https`), 앞머리 `www.`, 끝 슬래시만 맞춥니다. 조각(`#…`), 쿼리(`?…`), Wayback 접두(`https://web.archive.org/web/<시각>/`)는 그대로 둡니다. 조각은 같은 페이지의 다른 절을, 쿼리와 Wayback 시각은 다른 문서를 가립니다. 제목 표기, `urldate`, 그 밖의 필드 차이는 판단에 쓰지 않습니다. 검사기도 같은 기준으로 저장소 안의 엔트리를 견줍니다.

- 정규화한 `url`이 같으면 같은 문서입니다. 내 파일을 상대 PR의 파일로 글자 그대로 덮어씁니다. 두 브랜치가 같은 내용의 파일을 더하면 git이 충돌 없이 합칩니다. `리뷰`
- 정규화한 `url`이 다르면 다른 문서입니다. 내 키를 바꾸고, 파일 이름과 본문의 인용을 함께 고칩니다. `리뷰`
- 같은 절을 가리키는 키는 하나로 합치고, 지운 키를 인용하던 페이지는 남은 키를 인용합니다. 한 HTML 페이지의 다른 절을 따로 인용하면 `url`에 그 절의 앵커를 달아 엔트리를 따로 둡니다. 예: `…/xrat/V4_xsh_chap01.html#tag_22_02_09`(B.2.9 Threads) `리뷰`

도해는 두 파일의 내용을 비교합니다.

- 글자 그대로 같으면 그대로 둡니다. `리뷰`
- 다르면 내 도해의 이름을 바꾸고, 그 도해를 넣은 줄(`![[diagrams/<파일 이름>.svg]]`)을 함께 고칩니다. `리뷰`

## 빌드

- 사이트가 빌드되어야 합니다. `검사 build`
- 페이지의 태그마다 태그 목록이 생기고, 그 목록에 페이지가 나와야 합니다. `검사 output`
- 수식은 KaTeX로 렌더되어야 합니다. KaTeX는 렌더 오류가 있어도 빌드를 멈추지 않고 페이지에 남깁니다. 문법 오류는 식 전체가 `.katex-error`로, 정의되지 않은 명령은 `.katex` 안에서 그 이름이 오류 색(`#cc0000`)으로 그려집니다. 둘 다 위반입니다. `검사 output`
- 본문에 취소선이 렌더되면 안 됩니다. GFM은 `~` 하나짜리 취소선도 받아서, 한 문단에 범위 표기 `~`가 둘 있으면 그 사이가 취소선이 됩니다. 이때는 범위 표기 `~`를 `\~`로 씁니다. 위키는 취소선을 쓰지 않으므로 `~~…~~`도 위반입니다. `검사 output`
