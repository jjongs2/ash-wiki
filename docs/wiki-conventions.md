# 위키 규약

위키 페이지의 표기 규칙입니다. 규칙마다 판정하는 쪽을 적습니다.

- `검사 <id>`: 콘텐츠 검사기가 판정합니다. PR마다 CI가 돌립니다.
- `리뷰`: 읽어 봐야 판정되는 규칙입니다. `/code-review`와 사람 리뷰가 봅니다.

검사기는 이 문서의 표를 직접 읽습니다. 표 바로 위의 `<!-- table: <이름> -->` 주석이 표 이름이고, 표의 열 이름을 바꾸면 검사기도 함께 고쳐야 합니다.

## 검사기

```sh
npm run check:content
```

검사마다 `OK`·`FAIL`·`SKIP` 한 줄을 찍고, 그 아래에 위반 위치를 `<파일>:<줄>: <내용>` 꼴로 찍습니다. FAIL이 하나라도 있으면 exit 1입니다. 파일 검사는 빌드가 실패해도 돌고, 산출물 검사(`output`)만 SKIP합니다.

## 페이지 타입과 프론트매터

- 페이지 타입은 개념 페이지와 표준 페이지 둘입니다. 표준 페이지에만 있는 필드가 하나라도 있으면 표준 페이지로 봅니다. `검사 frontmatter`
- 아래 표에 없는 필드는 위반입니다. `검사 frontmatter`
- 대문(`index.md`)과 태그 표시 이름 파일(`tags/`)은 `title`만 둡니다. `검사 frontmatter`
- `tags`에는 `content/tags/`에 표시 이름 파일이 있는 태그만 씁니다. 주제에 속하면 `<구역>/<주제>`, 어느 주제에도 속하지 않으면 `<구역>`을 답니다. `검사 frontmatter`

<!-- table: frontmatter -->

| 필드        | 개념 | 표준 | 형식        |
| ----------- | ---- | ---- | ----------- |
| `title`     | 필수 | 필수 | 문자열      |
| `tags`      | 필수 | 필수 | 태그 목록   |
| `aliases`   | 선택 | 선택 | 문자열 목록 |
| `verified`  | 필수 | 필수 | 날짜        |
| `publisher` | —    | 필수 | 문자열      |

| `status`    | —    | 필수 | 상태        |

형식은 다음과 같습니다.

- 문자열: 비어 있지 않은 문자열
- 문자열 목록, 태그 목록: 비어 있지 않은 문자열의 목록
- 날짜: `YYYY-MM-DD`. `verified`는 페이지의 모든 주장을 함께 마지막으로 검증한 날입니다. 새 페이지를 만들 때와 모든 주장을 다시 검증할 때만 오늘로 바꾸고, 주장 일부를 더하거나 고칠 때는 그대로 둡니다.
- 연도: 네 자리 정수. `edition`은 현행판의 연도입니다.
- 상태: 아래 표의 값 가운데 하나

| --------- | -------------------------------------- |
| `유효`    | 현행판이 유효합니다                    |

| `폐지`    | 폐지되어 더는 유효하지 않습니다        |

## 절

- 절 제목은 `##`부터 `###`까지 씁니다. `리뷰`
- 개념 페이지는 정의 → 구조·동작 → 비교·한계 순서로 씁니다. `리뷰`
- 표준 페이지는 정의 → 범위 → 개정 이력 순서로 씁니다. 다른 표준과의 비교는 그 뒤에 두고, 제목에 비교 대상을 드러냅니다. 예: `Bosch CAN FD와의 차이` `리뷰`

## 인용

- 인용은 `[@키]`로 쓰고, 대괄호 하나에 키 하나만 넣습니다. `검사 citation`
- 인용 자리는 쉼표 앞, 마침표 뒤입니다. 예: `A이고[@키1], B다.[@키2]` `리뷰`
- 같은 출처가 연달아 뒷받침하는 문장과 절은 마지막 것에만 인용을 답니다. 예: `A이고, B다. C다.[@키]`. 문단을 넘겨 묶지 않으며, 목록 항목과 콜아웃은 하나하나를 문단 하나로 봅니다. `리뷰`
- 인용 키는 `<발행기관>-<식별자>-<연도>` 꼴의 영문 소문자 kebab-case이고, 연도는 네 자리입니다. 예: `iso-11898-1-2024` `검사 citation`
- 참고문헌은 엔트리 하나를 파일 하나(`bib/<키>.bib`)로 둡니다. 파일 이름과 엔트리 키가 같아야 합니다. `검사 citation`
- 인용한 키는 모두 `bib/`에 엔트리가 있어야 합니다. `검사 citation`
- 엔트리에는 아래 표의 필드가 모두 있어야 합니다. `검사 citation`
- 인용은 `[1]` 같은 번호로 렌더되고, 인용한 페이지 하단에 참고문헌이 붙습니다. `검사 output`
- 본문의 출처 표시는 [위키 검증의 좁혀 쓰기](wiki-verification.md#좁혀-쓰기)를 따릅니다. `리뷰`

<!-- table: bib-fields -->

| 필드      | 형식   |
| --------- | ------ |
| `title`   | 문자열 |
| `url`     | URL    |
| `urldate` | 날짜   |

`urldate`는 접근일입니다. URL은 `http://`나 `https://`로 시작합니다.

## 용어

- 원어가 실무에서 자연스러운지 먼저 봅니다. 그다음 정착한 한국어, 정착한 음차 순으로 고릅니다. `리뷰`
- 선택이 갈리면 `term:` 이슈로 올립니다. `리뷰`

## 약어

- 약어는 페이지에서 처음 나올 때 풀이를 병기합니다. 예: `CAN(Controller Area Network)` `리뷰`
- 아래 표의 약어는 풀이하지 않습니다. 널리 쓰이는 약어이거나, 풀이하면 오히려 읽기 어려운 이름입니다. `리뷰`
- 조직 이름이거나 표준 번호의 앞머리로 굳은 약어도 풀이하지 않고, 표의 `표준화 기구`나 `표준·규격 이름` 줄에 올립니다. 예: `RS-485`, `RFC 1122` `리뷰`

| 종류             | 약어                                            |
| ---------------- | ----------------------------------------------- |
| 널리 쓰이는 약어 | CPU, ECU, MCU                                   |
| 표준화 기구      | ISO, SAE, IEC, IEEE, ITU-T, TIA, EIA, CiA, NMEA |
| 표준·규격 이름   | AUTOSAR, OSEK/VDX, RFC, RS                      |
| 핀과 신호        | CAN_H, CAN_L, RXD, TXD                          |
| 전원             | GND, VCC                                        |
| ISO 위원회 번호  | SC, TC                                          |

- 자기 개념 페이지가 있는 약어와, 열린 `ingest:` 티켓의 `## Pages` 표에 자기 페이지가 계획된 약어는 그 페이지에서만 풀이합니다. 다른 페이지에서는 풀이하지 않고, 처음 나올 때 그 페이지로 한 번 링크합니다. 예: CAN은 `can`에서만 풀이하고, 다른 페이지에서는 `[[can|CAN]]`으로 겁니다. ACK는 `[[can-acknowledgement|ACK]]`로 겁니다. `리뷰`
- 계획만 된 페이지는 아직 링크하지 않습니다. 풀이만 빼고, 링크는 페이지가 생긴 뒤 린트가 채웁니다. 예: CAN FD(`can-fd`), DLC(`data-length-code`) `리뷰`

## 단위

- 수치와 라틴 문자 단위는 띄워 씁니다. 식 안에서는 `\,`로 띄웁니다. 예: `500 kbit/s`, `$0.2\,\mathrm{V}$` `리뷰`
- 수치와 한글 단위는 붙여 씁니다. 예: `8바이트` `리뷰`

단위와 인용 자리 규칙은 오탐 위험이 있어 리뷰가 봅니다. 실제 위반이 둘 이상 나오면 검사로 올립니다.

## 수식

- 양 사이의 관계(합·차·곱·비·비교)와 양이 만족해야 하는 조건(판정 조건, 두 끝이 있는 범위)은 수식으로 씁니다. 상수와의 비교 조건도 포함합니다. 사양값(`최대 1 Mbit/s`, `1 Mbit/s까지 지원`)과 전형값(`약 3.5 V`, `약 0.5 VCC`)은 글로 둡니다. 기기나 포맷이 갖는 값의 범위(출력 전압, 공통 모드 범위, 데이터 길이)는 사양값이라 글로 둡니다. 예: `±8 V`, `2~3 V`. 표준이나 기능을 쓰는 조건인 범위는 식으로 씁니다. 예: 비트율 범위 `리뷰`
- 기호는 위키 전체가 같은 것을 씁니다. 규범 표준에 기호가 있으면 따르고, 없으면 일반 표기를 씁니다. 데이터시트마다 다른 기호를 옮기지 않습니다. 기호는 페이지에서 처음 쓸 때 말 뒤에 붙여 정의합니다. 예: `차동 전압 $V_\mathrm{diff}$`. 아래첨자가 본문 용어를 그대로 담아 기호만으로 뜻이 읽히면 정의하지 않습니다. 예: `$V_\mathrm{CAN\_H}$` `리뷰`
- 식 안의 용어와 이름은 본문 표기 그대로 `\mathrm`으로 씁니다. 예: `\mathrm{VCC}`, `V_\mathrm{CAN\_H}`. 기울어진 글자는 변수에만 씁니다. `리뷰`
- 식 안의 단위는 `\mathrm`으로 쓰고, 수치와 가는 공백(`\,`)으로 띄웁니다. 예: `0.2\,\mathrm{V}` `리뷰`
- 식은 인라인(`$…$`)으로 씁니다. 식의 한쪽 변에 항이 셋 이상이면 디스플레이(`$$…$$`)로 씁니다. 디스플레이 식은 새 주장을 담지 않습니다. 식을 소개하는 앞 문장이 주장 전체를 글로 담고, 인용도 그 문장에 답니다. `리뷰`

## 슬러그

- 슬러그는 파일 이름에서 `.md`를 뺀 것이고, 영문 소문자 kebab-case입니다. `검사 namespace`
- 페이지는 `content/` 바로 아래에 둡니다. 폴더를 쓰지 않습니다. 태그 표시 이름 파일(`content/tags/`)만 예외입니다. `검사 namespace`
- 슬러그, `aliases`, 위키링크 대상은 한 네임스페이스입니다. alias를 슬러그로 바꾼 값이 자기 슬러그를 포함한 페이지의 슬러그나 다른 페이지의 alias와 겹치면 안 됩니다. 슬러그로 바꾸면 소문자가 되므로 `CAN controller`는 `can-controller`와 겹칩니다. `검사 namespace`

## 위키링크

- 위키링크 대상은 슬러그로만 씁니다. 표시 이름 없이 걸면 슬러그(앵커가 있으면 `슬러그 > 앵커`)가 그대로 링크 글자가 되므로, 이것이 대상의 `title`과 다르면 `[[슬러그|표시 이름]]`으로 씁니다. `검사 wikilink`
- 대상 페이지가 있어야 합니다. `검사 wikilink`
- 태그 목록은 `[[tags/<태그>|표시 이름]]`으로 겁니다. 표시 이름 파일이 있는 태그만 걸 수 있습니다. `검사 wikilink`

## 강조

- 강조(`**`)는 용어를 정의하는 자리에만 씁니다. 정의 절 첫 문장의 주제어와, 본문에서 새로 정의되는 하위 용어가 여기에 해당합니다. 정의하는 자리는 정의 문장(`X는 …이다`, `…을 X라 한다`)과 정의 목록 항목(`- X: …`)입니다. 같은 용어는 한 페이지에서 한 번만 강조하고, 한 문단에 강조가 여럿이어도 됩니다. 주제어에 풀이가 붙으면 풀이는 강조 밖에 둡니다. 예: `**CAN ACK**(Acknowledgement)는`. 강조 안에는 위키링크를 넣지 않습니다. `리뷰`
- 강조는 렌더되어야 합니다. 닫는 `**` 앞이 문장 부호이고 바로 뒤에 조사가 붙으면 강조가 풀리지 않고 `**`가 그대로 보입니다. 예: `**CAN(Controller Area Network)**은`. 강조 범위를 줄이거나(`**CAN**(Controller Area Network)은`) 문장을 바꿉니다. `검사 emphasis`

## 도해

- 도해는 출처를 근거로 새로 그립니다. `리뷰`
- 도해는 SVG 파일 하나로 `content/diagrams/`에 두고 `![[diagrams/<파일 이름>.svg]]`로 넣습니다. 라이트·다크 두 테마가 같은 파일을 씁니다. `검사 wikilink`
- 도해의 글자와 수치는 위키 페이지의 주장에 있는 것만 씁니다. 도해를 넣는 페이지의 주장이 아니어도 됩니다. `리뷰`
- 도해는 그것이 나타내는 주장이 있는 문단 바로 뒤에 넣습니다. 여러 페이지에 맞는 도해는 파일 하나를 함께 씁니다. `리뷰`
- 파일 이름은 그림의 내용을 나타내는 영문 소문자 kebab-case입니다. `리뷰`
- SVG의 색은 아래 표의 값만 씁니다. `none`, `transparent`, `inherit`, 그라디언트 참조(`url(#id)`)도 쓸 수 있습니다. `검사 svg`
- 루트 `<svg>`에 `fill`을 둡니다(팔레트 값이나 `none`). 두지 않으면 색을 적지 않은 도형과 글자가 검정으로 그려져 다크 테마에서 보이지 않습니다. `검사 svg`
- `<image>`나 `<feImage>`로 래스터나 외부 파일을 넣지 않습니다. `검사 svg`
- 배경은 칠하지 않습니다. 사이트 배경이 그대로 비쳐야 두 테마에서 읽힙니다. `리뷰`
- 테두리, 폭, 가운데 정렬은 사이트가 맡습니다(`quartz/styles/custom.scss`). SVG에는 그림을 두르는 틀을 그리지 않습니다. `리뷰`
- 사이트는 `viewBox` 1단위를 `0.85rem / 12`로 그립니다. 그래서 `font-size="12"` 글자는 본문의 0.85배로, 도해 폭과 상관없이 크기가 같습니다. 틀 안쪽보다 넓은 도해만 틀에 맞춰 줄어듭니다(`quartz/styles/custom.scss`). `리뷰`
- 루트 `<svg>`에 `viewBox`를 둡니다. `viewBox`는 그림의 상하좌우 여백이 같게 잡습니다. 사이트는 `viewBox`를 틀 가운데에 놓으므로, 그림이 `viewBox` 안에서 쏠리면 틀 안에서도 쏠려 보입니다. 검사는 여백의 차가 허용치를 넘으면 옮긴 `viewBox`를 알려 줍니다. 허용치와 그 근거는 `tools/check-content/diagram-margin.ts`에 있습니다. `검사 svg`
- 채움 도형 안의 글자는 `on-fill`, 도형 밖의 글자와 선은 `ink`로 씁니다. `on-fill` 글자는 `채움` 색 위에만 둡니다. `리뷰`
- 범주는 색만으로 구분하지 않고 라벨로도 적습니다. 채움 색 다섯은 밝기가 같습니다. `리뷰`
- 글자는 Pretendard로 그립니다. 루트 `<svg>`에 `font-family="Pretendard, sans-serif"`와 `text-rendering="geometricPrecision"`을 두고, `<style>`에서 사이트와 같은 Pretendard CSS를 `@import`로 불러옵니다(넣을 줄은 검사가 알려 줍니다). SVG는 `<object>`로 들어가 별도 문서로 그려지므로 사이트의 웹 폰트를 물려받지 못합니다. 브라우저가 검사와 같은 폰트로, 글자 폭을 픽셀에 맞춰 반올림하지 않고 그려야 검사가 잰 여백이 독자가 보는 여백과 맞습니다. `검사 svg`
- 반투명(`opacity`, `fill-opacity`)으로 색을 바꾸지 않습니다. 대비가 표의 값과 달라집니다. `리뷰`

## 빌드

- 사이트가 빌드되어야 합니다. `검사 build`
- 페이지의 태그마다 태그 목록이 생기고, 그 목록에 페이지가 나와야 합니다. `검사 output`
- 수식은 KaTeX로 렌더되어야 합니다. KaTeX는 렌더 오류가 있어도 빌드를 멈추지 않고 페이지에 남깁니다. 문법 오류는 식 전체가 `.katex-error`로, 정의되지 않은 명령은 `.katex` 안에서 그 이름이 오류 색(`#cc0000`)으로 그려집니다. 둘 다 위반입니다. `검사 output`
- 본문에 취소선이 렌더되면 안 됩니다. GFM은 `~` 하나짜리 취소선도 받아서, 한 문단에 범위 표기 `~`가 둘 있으면 그 사이가 취소선이 됩니다. 이때는 범위 표기 `~`를 `\~`로 씁니다. 위키는 취소선을 쓰지 않으므로 `~~…~~`도 위반입니다. `검사 output`
