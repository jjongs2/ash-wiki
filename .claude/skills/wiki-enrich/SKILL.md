# 보강

주제 하나를 소스 노트 없이 공개 출처로 넓히고 고친다. 발행한 티켓은 인제스트가 노트 대신 티켓의 출처 후보로 처리한다. 용어는 `CONTEXT.md`를 따른다. 주제 이름은 `content/tags/<주제 태그>.md`의 `title`이다(예: CAN). 파일이 없으면 새 주제이니 표시 이름을 소유자에게 묻는다.

먼저 읽는다: `docs/source-hierarchy.md`(1층 출처), `docs/wiki-conventions.md`(슬러그, 페이지 타입, 태그), `docs/wiki-verification.md`(판정, 표준의 판, 정정, `verify:` 이슈).

`ASH_WIKI_NOTES`는 열지 않는다. 보강은 공개 출처와 게시된 페이지만 본다.

## 1. 열린 티켓 확인

열린 `ingest:` 티켓 가운데 `## Pages` 표의 태그에 주제 태그가 있는 것과, 열린 `verify: <주제>` 이슈를 찾는다. `gh` 사용법은 `docs/agents/issue-tracker.md`를 따른다.

하나라도 있으면 번호를 알리고 멈춘다. 진행 중인 주제 계획이나 보강과 슬러그가 겹치거나 `verify:` 이슈가 둘이 되기 때문이다.

완료: 열린 티켓이 없다.

## 2. 지도 자료

계획 파일은 저장소 밖, 세션의 scratchpad 디렉터리(없으면 `mktemp -d`)에 쓴다.

**지도 자료 목록**을 정한다. 주제를 넓게 훑을 공개 자료로, 발행기관의 자료, 벤더 문서, 백과, 교재, 개관 글을 가리지 않는다. 자료마다 제목, URL, 발행기관, 1층 여부를 적는다. 1층 여부는 출처 위계로 가리고, 1층이면 어느 주장 종류에 대해서인지 적는다.

주제의 기존 페이지를 모두 읽고, 목록의 자료를 하나도 빼지 않고 대조한다. 자료마다 페이지에 없는 개념과 주장, 페이지와 다르게 말하는 곳을 적는다.

1층이 아닌 자료는 지도로만 쓴다. 무엇을 찾아볼지 알려 줄 뿐, 출처 후보나 인용이 되지 않는다.

출처는 [인제스트 검증자 프롬프트](../wiki-ingest/verifier.md)의 출처 여는 법대로 연다.

완료: 목록의 자료마다 대조 결과가 계획 파일에 있다.

## 3. 제안

대조 결과를 제안 항목으로 옮긴다. 항목은 세 종류다.

- **새 페이지**: 주제에 없는 개념의 페이지. 슬러그, 타입, 태그는 위키 규약을 따른다.
- **주장 추가**: 기존 페이지에 없는 주장
- **정정**: 기존 페이지의 주장과 다르게 말하는 1층 출처가 있는 곳. 위키 검증 문서의 정정 절로 처리될 항목이다.

항목마다 1층 출처 후보를 적는다. 내용이 있는 위치(절, 쪽, 표)까지 적는다. 후보가 없는 항목은 빼고, 계획 파일의 뺀 항목에 이유와 함께 남긴다.

주제 태그나 구역 태그의 표시 이름 파일이 없으면 그 파일과 대문 목록 줄의 추가도 제안한다. 이 추가에는 출처 후보가 필요 없다.

제안과 티켓은 자기 말로 쓴다. 지도 자료의 표현을 옮기지 않는다(`docs/wiki-conventions.md`의 출처 문장 절).

항목을 **페이지 묶음**으로 나눈다. 서로 위키링크로 자주 엮이는 개념끼리 묶고, PR 하나로 리뷰할 만한 크기로 둔다. 같은 페이지의 항목은 한 묶음에 둔다. 태그 추가는 그 태그를 처음 쓰는 묶음에 둔다.

alias를 둘 새 페이지는 alias를 미리 정하고, 두 페이지 이상이 다룰 개념마다 주인 페이지를 정한다. 기존 페이지와 겹치는 개념도 담는다. 둘은 [발행](#6-발행)의 `## 범위` 절에 들어간다.

완료: 대조 결과마다 제안 항목이 있거나 뺀 이유가 있고, 제안 항목마다 1층 출처 후보와 묶음이 있다. 두 페이지 이상이 다룰 개념마다 주인 페이지가 있다.

## 4. 비평

Agent 도구로 빈 컨텍스트 서브에이전트(`general-purpose`) 하나를 띄운다. 계획 파일 경로와 주제 태그를 주고, 저장소 문서는 이 스킬이 먼저 읽은 셋을 읽게 한다. 주제의 기존 페이지와 출처 후보는 직접 열어 보게 한다. 볼 것:

- 출처 후보가 그 항목의 내용을 담는가
- 새 페이지나 주장 추가가 기존 페이지와 겹치지 않는가, 겹치는 개념을 주인 페이지 표가 모두 덮는가
- 슬러그, 타입, 태그가 규약에 맞는가
- 정정이 표준의 판 규칙에 맞는가

비평마다 반영하거나 반영하지 않은 이유를 계획 파일에 적는다.

완료: 모든 비평 항목에 반영 여부와 이유가 있다.

## 5. 승인

대화에 지도 자료 목록, 묶음별 제안 항목, alias와 주인 페이지, 뺀 항목, 비평 반영 요약을 보이고 소유자의 승인을 기다린다. 고쳐 달라고 하면 고쳐서 다시 보인다.

완료: 소유자가 이 제안을 발행하라고 분명히 말했다. 그 전에는 아무것도 발행하지 않는다.

## 6. 발행

`gh` 사용법과 blocked-by API는 `docs/agents/issue-tracker.md`를 따른다. 묶음 티켓이 `verify:` 이슈 번호를 적으므로 `verify:` 이슈를 먼저 만든다. 이 보강을 부른 티켓이 있으면 두 본문 모두 `## Parent`에 그 번호를 적고, 없으면 `## Parent` 절을 뺀다.

**`verify: <주제>`**: 라벨과 blocked-by는 위키 검증 문서의 `verify:` 이슈 절을 따른다.

```md
## Parent

#<보강 티켓>

## What to build

<주제> 보강의 미검증 주장을 모으고 재조사한다. 절차는 `docs/wiki-verification.md`를 따른다.
```

**`ingest: <묶음 이름>`**: 묶음마다 하나. 라벨 `ready-for-agent`. 표는 제안 항목마다 한 줄이고, 같은 슬러그의 줄은 붙여 적는다. `요지`는 새 페이지면 다룰 범위, 주장 추가면 더할 주장, 정정이면 고칠 주장과 출처가 말하는 것이다. `## Tags`는 태그 추가가 있을 때만 둔다. `## 범위`의 두 표는 [주제 계획](../wiki-plan/SKILL.md)의 `ingest:` 템플릿과 같은 꼴이고, alias 표는 alias를 둘 새 페이지가 없으면 뺀다.

```md
## Parent

#<보강 티켓>

## Pages

| 슬러그     | 종류      | 타입 | 태그            | 요지   | 출처 후보      |
| ---------- | --------- | ---- | --------------- | ------ | -------------- |
| `<슬러그>` | 새 페이지 | 개념 | `<구역>/<주제>` | <요지> | <URL> (<위치>) |

## 범위

alias(병렬 인제스트끼리 겹치지 않게 미리 정함):

| 페이지     | alias   |
| ---------- | ------- |
| `<슬러그>` | <alias> |

주인 페이지:

| 개념   | 주인       | 링크만 하는 곳         |
| ------ | ---------- | ---------------------- |
| <개념> | `<슬러그>` | `<슬러그>`, `<슬러그>` |

## Tags

- `<구역>/<주제>`: 표시 이름 <이름>, 대문 목록의 `<구역>` 아래

## Acceptance criteria

- [ ] `npm run check:content` 통과
- [ ] 검증자 판정 반영
- [ ] `verify:` 코멘트 (#<verify 이슈>)
```

묶음 티켓을 모두 만든 뒤 `verify:` 이슈에 blocked-by를 건다. 보강을 부른 티켓이 있으면 발행한 티켓 목록을 코멘트로 남긴다.

완료: 묶음마다 티켓이 있고, `gh api repos/<owner>/<repo>/issues/<verify 이슈> --jq .issue_dependencies_summary.blocked_by`가 묶음 수와 같다.
