# Reader Testing

게시된 페이지 전체를 위키 규칙을 모르는 독자에게 읽혀, 리뷰와 린트가 보지 않는 읽기 경험의 문제를 찾고 고친다. 콘텐츠 PR이 새로 쓰거나 고친 부분은 PR을 올리기 전에 위키 검증 문서의 독자 검토가 본다. 이 스킬은 독자 에이전트가 페이지마다 하나씩 돌아 비용이 크므로 소유자가 부를 때만 돈다. 용어는 `GLOSSARY.md`를 따른다.

인자가 주제 태그나 구역 태그면 그 태그를 단 페이지(구역 태그는 하위 태그를 단 페이지까지), 슬러그 목록이면 그 페이지들이 대상이다. 아래 `<대상>`은 태그면 `content/tags/<태그>.md`의 `title`, 슬러그 목록이면 슬러그를 쉼표로 이은 것이다.

- 소유자가 6단계의 보고를 확인하기 전에는 push, PR, 이슈, 코멘트를 하지 않는다.
- `ASH_WIKI_NOTES`는 열지 않는다. 게시된 페이지와 출처만 보므로 격리 자기 점검은 하지 않는다.

## 1. 시작

- `git fetch origin` 뒤 `origin/main`에서 worktree와 브랜치를 만든다. 브랜치는 `CONTRIBUTING.md`의 브랜치 절대로 이슈 번호 없이 `content/reader-<영문 kebab-case 요약>`이다.
- **기준 SHA**를 `git merge-base origin/main HEAD`로 적어 둔다. 캡처, 반영 뒤 점검, 프리뷰가 모두 이것을 기준으로 삼는다.
- 새 worktree에서 `npm ci`를 돌린다. 캡처가 쓰는 `playwright`가 의존성에 있다.

완료: worktree와 브랜치가 있고, 기준 SHA를 적었다.

## 2. 캡처

배포 사이트가 기준 SHA의 페이지를 내는지 확인한다. 참고문헌은 `bib/`에서 렌더되므로 `content/`와 함께 본다.

```sh
git fetch origin
git rev-parse origin/main
gh api repos/<owner>/<repo>/commits/<그 SHA>/check-runs --jq '.check_runs[] | select(.name == "Cloudflare Pages") | .conclusion'
git diff --quiet <기준 SHA> origin/main -- content/ bib/
```

`conclusion`이 `success`이고 diff가 없으면 배포 사이트에서 캡처한다. 아니면(배포 중, 실패, 그 뒤 main이 페이지를 바꿈) 1단계의 worktree를 고치기 전에 로컬 빌드로 캡처한다.

```sh
npm run prebuild
npx quartz build -d content -o <scratchpad>/site
```

캡처는 한 번만 받는다. `<인자>`는 태그면 `--topic <태그>`, 슬러그 목록이면 슬러그를 그대로 준다. 로컬 빌드면 `--site <scratchpad>/site`를 더한다.

```sh
npm run reader-capture -- --out <scratchpad>/capture <인자>
```

- 페이지마다 데스크톱 폭과 390px 폭 스크린샷을 조각으로, 렌더된 본문을 독자 텍스트로 받는다. 본문이 링크한 페이지는 `linked/`에 독자 텍스트만 받는다. 독자가 브라우저를 직접 다루지 않는 것은, 병렬로 도는 독자가 브라우저 하나를 나눠 쓰면 탭이 엉키기 때문이다.
- 출력은 페이지마다 폭별 조각 수와 이미지 토큰 어림이다. 6단계의 비용에 옮긴다.
- 브라우저가 없다고 멈추면 `npx playwright install --only-shell chromium`으로 받는다. 이 명령은 캐시에서 지금 `playwright` 판이 쓰지 않는 브라우저를 지운다.

캡처를 마치면 대상 쪽 수와 어림 비용을 소유자에게 보이고, 3단계로 넘길 페이지를 고르게 한다. 어림은 페이지당 약 13만 토큰을 상한으로 잡는다. `network` 구역 119쪽을 독자, 가르기, 점검까지 돌린 실측이다. 묻지 않고 띄우면 소유자가 처음 끼어드는 5단계에는 독자 비용이 이미 다 든 뒤다.

완료: 대상 페이지마다 텍스트와 두 폭의 조각이 있고, 캡처한 곳(배포 사이트나 로컬 빌드)을 적었고, 소유자가 3단계로 넘길 페이지를 골랐다.

## 3. 읽기

읽는다: [reader.md](reader.md).

[reader.md](reader.md)의 지시 블록과 반환 꼴 블록을 이어 `<scratchpad>/capture/지시.md`에 옮긴다. 소유자가 고른 페이지마다 독자를 하나씩 Agent 도구(`general-purpose`, 모델 `sonnet`)로 띄운다. 모델을 정하지 않으면 메인 세션의 모델을 물려받는다. 한 메시지에 모두 띄워 병렬로 돌리고, 동시 실행 한도(지금 20)를 넘으면 나눠 띄운다. 프롬프트는 띄우는 프롬프트를 채워 쓴다.

독자에게 위키 규칙 문서, 페이지의 원본 마크다운, 티켓, 메인 세션의 판단은 주지 않는다.

반환마다 확인한다.

- 반환 꼴의 키가 모두 있다.
- 인용이 그 페이지나 링크된 페이지의 텍스트에 글자 그대로 있다(`grep -F`).

빠진 것이나 텍스트에 없는 인용은 SendMessage로 그 독자에게 돌려보낸다. Agent 도구의 결과에 나온 독자마다의 토큰과 시간을 6단계의 비용에 옮긴다.

완료: 페이지마다 확인을 통과한 반환이 있다.

## 4. 가르기

읽는다: `docs/wiki-conventions.md`, `docs/wiki-abbreviations.md`, `docs/wiki-terms.md`, `docs/wiki-verification.md`의 판정과 좁혀 쓰기 절, [린트 스킬](../wiki-lint/SKILL.md)의 3. 가르기.

반환의 `다시 읽은 문장`, `모호한 곳`, `없던 것`, `모순`, `시각 요소`의 항목을 모은다. 여러 독자가 같은 곳을 적었으면 하나로 합친다. 항목마다 `content/`의 원본과 렌더된 조각을 보고 넷으로 가른다.

| 갈래 | 기준                                                                    | 처리                                 |
| ---- | ----------------------------------------------------------------------- | ------------------------------------ |
| A    | 고친 뒤에도 모든 주장의 내용과 인용이 그대로인 것                       | 5단계에서 고친다                     |
| B    | 주장의 내용이나 인용을 건드리는 것                                      | 5단계에서 재판정을 거쳐 고친다       |
| C    | 고치면 위키 규칙을 어기는 것. 규칙 안에서 고칠 길이 있으면 A나 B로 간다 | 7단계에서 `docs: 규약 검토 모음`으로 |
| D    | 페이지 범위 밖의 바람                                                   | 걸러 내고 건수만 센다                |

- A와 B를 가르는 기준은 [린트 스킬](../wiki-lint/SKILL.md)의 3. 가르기에서 굵게 쓴 수정 기준이다. 그 절이 수정으로 드는 태그, 위키링크, 표기는 린트가 찾는 것일 뿐이다. 문장을 다시 쓴 수정은 주장의 뜻(위키 검증 문서 독자 검토 절의 반영 뒤 재판정 줄)과 인용 자리를 바꾸지 않을 때만 A다. 아래는 A가 아니다.
  - 한정어, 관계, 사실 더하기
  - 시제, 주어, 동사 바꾸기
  - 인용 키를 다른 문장으로 옮기기
  - 다른 출처 구간 사이에 끼우기([ADR 0016](../../../docs/adr/0016-source-run-by-edition.md))
- C는 어기게 되는 규칙의 파일과 절을 적는다.
- 링크된 페이지에서 걸린 곳도 같은 기준으로 가르고, 같은 PR에서 고친다.
- 페이지 글이 아니라 사이트의 렌더에서 오는 것(인용 번호의 줄바꿈 등)은 넷에 넣지 않고 6단계의 보고에 따로 적는다.

완료: 사이트의 렌더에서 오는 것을 뺀 모든 항목이 A, B, C, D 가운데 하나다.

## 5. 고치기

읽는다: 위키 규약에서 고치는 자리에 걸리는 절. 도해를 고치면 도해 절.

1단계의 worktree 브랜치에서 아래 차례로 고친다.

1. **A**: 4단계의 A 기준대로 고친다. 인용 키는 고치기 전과 같은 문장에 둔다.
2. **A 점검**: 새 맥락 에이전트 하나를 Agent 도구(`general-purpose`)로 띄워, 기준 SHA와의 diff와 4단계의 A 기준만 주고 A로 고친 곳을 점검받는다. 반환은 고친 곳마다 A인지, 뜻을 바꿨는지, 규약만 어겼는지와 그 까닭이다. 뜻을 바꾼 곳은 되돌려 B로 옮기고, 규약만 어긴 곳은 고친다.
3. **B 고르기**: B 건수와 페이지별 목록을 소유자에게 보이고, 건수와 상관없이 재판정할 B를 고르게 한다. 고르지 않은 B는 고치지 않고 6단계의 보고에 남긴다.
4. **B**: 고른 B마다 고친 문장이 인용하는 출처를 다시 열어, 문장마다 `[@<키>] (<위치>)`를 단다. 새 출처가 필요하면 위키 규약의 인용 절대로 엔트리를 더한다. 그다음 인제스트의 출처 경로 검증자 프롬프트 [source-verifier.md](../wiki-ingest/source-verifier.md)로 재판정받는다.
   - 브리프와 띄우는 프롬프트는 그 파일의 머리말대로 채운다. 고친 문장은 프롬프트의 `## 초안` 절로 주므로 `<기준 커밋>`은 "없음"이고, 브리프의 `## 현행판 표`와 `## 사본 목록`도 "없음"이다.
   - `## 초안` 절의 첫 줄은 "Reader Testing이 고친 문장이다. 모두 새로 판정할 문장이다."이다. `(기존: …)`는 달지 않는다. 원래 문장이 틀려서 고친 것이 아니라 정정이 아니기 때문이다.
   - 검증 완료인 문장만 반영하고, 반환에 `고쳐 쓸 문장`이 있으면 그 문장으로 넣는다. 반영할 때 인용 위치는 뺀다. 검증 완료가 아니면 원래 문장을 두고 6단계의 보고에 적는다.
   - 주장을 바꾼 페이지의 `verified`는 위키 규약의 페이지 타입과 프론트매터 절대로 둔다.

고친 뒤 `npm run check:diff -- --base <기준 SHA>`로 위키 검증 문서의 반영 뒤 점검을 하고, `CONTRIBUTING.md`의 PR 전 확인을 돌린다. 커밋 메시지는 `content: <대상> Reader Testing 수정`이다.

완료: A 점검을 거친 A와, 소유자가 고르고 검증 완료인 B가 커밋됐고, 반영 뒤 점검의 후보를 모두 봤고, PR 전 확인이 통과한다.

## 6. 짧은 보고

소유자에게 아래를 짧게 알리고 멈춘다.

- 대상과 캡처한 곳(배포 사이트나 로컬 빌드)
- 갈래별 건수와 주요 항목. A와 B는 고친 곳, C는 어기게 되는 규칙, D는 건수만
- 검증되지 않아 원래 문장을 둔 B
- 소유자가 고르지 않은 B의 페이지별 목록
- 사이트의 렌더에서 오는 것
- 비용: 캡처는 페이지당 데스크톱 조각의 이미지 토큰, 독자는 페이지당 토큰과 시간, 가르기와 점검에 띄운 에이전트는 토큰
- 전후를 비교할 명령과 기준 SHA:

  ```sh
  cd <worktree> && WIKI_DIFF=<기준 SHA> npm run preview:diff
  ```

완료: 보고를 마쳤다. 소유자가 확인하기 전에는 7단계로 넘어가지 않는다.

## 7. PR과 C

소유자가 확인에서 고치라고 한 것을 고친 뒤 5단계의 점검을 다시 돌린다.

1. A나 B를 고쳤으면 `CONTRIBUTING.md`의 리뷰 절대로 리뷰를 돌려 반영하고 PR을 올린다. bib 엔트리나 도해를 더했으면 push 직전에 위키 규약의 열린 PR과 겹치는 파일 절대로 본다. 제목은 `content: <대상> Reader Testing 수정`, 본문은 `CONTRIBUTING.md`의 세 부분이다. Verification에는 캡처한 곳, 갈래별 건수, B의 재판정 결과, 반영 뒤 점검과 PR 전 확인을 적는다. PR을 연 뒤 리뷰 요약 코멘트를 단다.
2. C가 있으면 열린 `docs: 규약 검토 모음` 이슈에 [모음 이슈 템플릿](../../../.github/ISSUE_TEMPLATE/convention-review.md)의 꼴로 한 코멘트에 한 항목씩 남긴다. **문제**에는 걸린 페이지와 독자가 읽은 뜻, 1의 PR이 있으면 그 번호를 적는다. 열린 모음 이슈가 없으면 템플릿의 제목, 라벨, 본문으로 연다.

완료: 고친 것이 있으면 PR과 리뷰 요약 코멘트가 있고, C가 모두 모음 이슈의 코멘트로 있다.
