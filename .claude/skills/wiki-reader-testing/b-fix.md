# B 반영 프롬프트

Reader Testing B 이슈를 반영하는 세션의 차례와 고치기 에이전트 프롬프트다. B 이슈 본문이 이 파일을 가리킨다. 항목은 Reader Testing 4단계의 D 기준을 거쳤으므로 다시 거르지 않는다.

고친 문장이 따를 규칙은 아래에 있고, 이 파일은 다시 적지 않는다.

- 위키 검증 문서의 [좁혀 쓰기](../../../docs/wiki-verification.md#좁혀-쓰기), [이론 주장](../../../docs/wiki-verification.md#이론-주장), [표준의 판](../../../docs/wiki-verification.md#표준의-판), [상태 문장](../../../docs/wiki-verification.md#상태-문장)
- 출처 위계 문서의 [1층 출처](../../../docs/source-hierarchy.md#1층-출처)
- 위키 검증 문서의 [반영 뒤 재판정](../../../docs/wiki-verification.md#반영-뒤-재판정) 절

## 차례

1. 항목을 페이지 묶음으로 나눈다. 묶음마다 고치기 에이전트 하나와 검증자(`source-verifier`) 하나를 짝짓는다. 작업 폴더는 Reader Testing 4단계의 작업 폴더 줄을 따라 묶음마다 `.work/b-fix/<묶음>/`에 둔다.
2. 고치기 에이전트를 아래 지시 블록으로 Agent 도구(`general-purpose`)에 띄운다.
3. 고친 문장을 반영 뒤 재판정 절대로 그 묶음의 검증자에게 판정받는다. 반환의 `고쳐 쓸 문장`은 그 묶음의 고치기 에이전트가 넣는다. 묶음의 페이지는 `source-verifier`의 띄우는 프롬프트 절의 묶는 줄대로 검증자 하나에 맡긴다. 띄우는 프롬프트의 `## 더할 지시` 절에 "새 문장을 그 자체로 판정하고, 두 문장이 같은 대목을 두고 어긋날 때만 정정 갈래로 본다."를 둔다. 검토를 반영한 뒤의 재판정에서는 "`(편집)` 문장은 `<기준 커밋>`이 아니라 `HEAD`의 문장과 견준다."도 더한다.
4. 같은 묶음을 다시 고치거나 다시 판정할 때는 새로 띄우지 않고 그 묶음의 두 에이전트를 SendMessage로 이어 쓴다. 고치기 에이전트가 받은 출처 사본은 검증자 브리프의 `## 사본 목록`에 넣어 다시 쓴다.
5. 위키 검증 문서의 반영 뒤 점검을 거친 뒤, 검토 절의 1회차를 돈다. 표기 검토, 도해를 고쳤으면 도해 검토, 그리고 독자 검토다. 지적은 메인 세션이 페이지마다 그 묶음의 고치기 에이전트에게 SendMessage로 보내 반영하게 한다. 고치기 에이전트는 자기 작업 폴더에 처리 줄을 남기고, 뜻을 바꾼 고침은 3대로 다시 판정받는다.
6. **재독**: 검토 절의 2회차다. 표기·도해 검토와 외부 독자가 1회차 커밋과의 diff를 보고, 두 축 리뷰가 브랜치 전체를 함께 본다. 2회차에 티켓과 같은 오독이 다시 나온 문장은 검토 절대로 되돌리고 PR 본문에 적는다. 티켓과 다른 독자 검토 지적은 독자 검토 절대로 거르고 다시 읽히지 않는다.

PR 본문에는 처리가 원래대로인 항목을 까닭과 함께 적고, Verification에는 검토 절의 처리 결과를 적는다.

## 고치기 지시

채울 자리는 `<worktree>`, `<작업 폴더>`, B 이슈 번호와 맡은 줄이다.

````md
너는 Reader Testing B 이슈의 항목을, 그 문장이 인용한 출처에 맞춰 고치는 에이전트다. 저장소 `<worktree>`의 페이지를 고치고, 작업 파일은 `<작업 폴더>`에만 둔다. `ASH_WIKI_NOTES`는 열지 않는다.

먼저 읽는다.

- B 이슈 #<번호>의 본문에서 맡은 줄: <슬러그와 줄>
- `docs/wiki-verification.md`: 좁혀 쓰기, 이론 주장, 표준의 판, 상태 문장, 반영 뒤 재판정 절과, 검토 절의 처리 줄
- `docs/source-hierarchy.md`: 1층 출처 절
- `docs/source-access.md`: 머리의 공통 줄과 호스트별 여는 법 절
- `docs/wiki-conventions.md`: 페이지 타입과 프론트매터, 절, 슬러그, 출처 문장, 인용, 약어, 용어, 중복 절. 도해를 고치면 `docs/wiki-diagrams.md`도
- `docs/wiki-terms.md`, `docs/wiki-abbreviations.md`

할 일:

1. 줄마다 그 문장이 인용한 출처를 열어, 외부 독자가 걸린 곳에 출처가 답하는지 본다. 받은 사본은 `<작업 폴더>/sources/`에 둔다.
2. 답하면 위 규칙대로 페이지를 고친다. 인용 키와 위치는 반영 뒤 재판정 절을 따른다. 답하지 않으면 고치지 않는다.
3. 검사는 `npm run check:content -- --no-build`로만 돌린다. 뒤에 메인 세션이 검토의 지적을 보내면 모아 반영하고, 지적마다 `<작업 폴더>/처리.md`에 처리 줄을 남긴다. 변수, 반복문, heredoc이 든 bash는 `<작업 폴더>`의 Python 파일로 돌린다.

반환은 마지막 메시지 하나이고, 파일로 쓰지 않는다. 아래 JSON 배열에 맡은 줄마다 하나씩 적는다.

```json
[
  {
    "page": "<슬러그>",
    "줄": "<이슈의 인용>",
    "처리": "고침 | 다르게 풂 | 원래대로: 출처가 답하지 않음 | 원래대로: 새 출처 필요",
    "고친 문장": "<페이지에 넣은 문장 전체에 [@<키>] (<위치>)를 단 것, 원래대로면 null>",
    "옮긴 원문": [{ "구절": "<원문 그대로>", "조건·닫힌 목록·대상 한정": "" }],
    "사본": ["<작업 폴더 안의 경로>"],
    "까닭": "<원래대로나 다르게 풂이면 한 줄>"
  }
]
```

- `다르게 풂`: 외부 독자가 물은 것을 다른 길(링크, 다른 문장)로 풀었다.
- `옮긴 원문`: 고친 문장이 옮긴 원문의 조건, 닫힌 목록, 대상 한정마다 그 구절과 함께 적는다. 없으면 빈 배열이다.
````
