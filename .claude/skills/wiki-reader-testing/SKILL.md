# Reader Testing

게시된 페이지의 표본에 독자 검토(위키 검증 문서의 검토 절)를 돌려, 검토와 린트가 보지 않는 읽기 경험의 문제를 찾는다. 주장을 건드리지 않는 것은 고치고, 건드리는 것은 이슈로 넘긴다. 이 스킬은 외부 독자가 페이지마다 하나씩 돌아 비용이 크므로 소유자가 부를 때만 돈다. 용어는 `GLOSSARY.md`를 따른다.

인자가 주제 태그나 구역 태그면 그 태그를 단 페이지(구역 태그는 하위 태그를 단 페이지까지) 가운데 무작위 20쪽(20쪽 이하면 모두), 슬러그 목록이면 그 페이지 모두가 대상이다. 다섯 실행의 외부 독자 반환으로 재면, 무작위 20쪽은 쪽의 5% 이상에 있는 꼴 가운데 95%를 잡는다. 주제별로 나눠 고르지 않고 태그 전체에서 고르며, 빠진 주제는 2단계에서 소유자가 바꾼다. 아래 `<대상>`은 태그면 `content/tags/<태그>.md`의 `title`, 슬러그 목록이면 슬러그를 쉼표로 이은 것이다.

- 소유자가 6단계의 보고를 확인하기 전에는 push, PR, 이슈, 코멘트를 하지 않는다.
- `ASH_WIKI_NOTES`는 열지 않는다. 게시된 페이지만 보므로 격리 자기 점검은 하지 않는다.

## 1. 시작

- `git fetch origin` 뒤 `origin/main`에서 worktree와 브랜치를 만든다. 브랜치는 `CONTRIBUTING.md`의 브랜치 절을 따라 이슈 번호 없이 `content/reader-<영문 kebab-case 요약>`이다.
- **기준 SHA**를 `git merge-base origin/main HEAD`로 적어 둔다. 캡처, 반영 뒤 점검, 프리뷰가 모두 이것을 기준으로 삼는다.
- 새 worktree에서 `npm ci`를 돌린다.

완료: worktree와 브랜치가 있고, 기준 SHA를 적었다.

## 2. 고르기와 캡처

태그면 대상 슬러그에서 20쪽을 무작위로 뽑는다. 20쪽 이하면 모두 나온다. 슬러그 목록이면 그대로 쓴다.

```sh
npm run --silent reader-capture -- --list --topic <태그> | shuf -n 20
```

뽑은 슬러그와 어림 비용을 소유자에게 보이고, 소유자가 슬러그를 바꾸면 바꾼 목록을 쓴다. 어림은 페이지당 약 13만 토큰으로 잡는다. 묻지 않고 띄우면 소유자가 처음 끼어드는 6단계에는 외부 독자 비용이 이미 다 든 뒤다.

그다음 배포 사이트가 기준 SHA의 페이지를 내는지 확인한다. 참고문헌은 `bib/`에서 렌더되므로 `content/`와 함께 본다.

```sh
git fetch origin
git rev-parse origin/main
gh api repos/<owner>/<repo>/commits/<그 SHA>/check-runs --jq '.check_runs[] | select(.name == "Cloudflare Pages") | .conclusion'
git diff --quiet <기준 SHA> origin/main -- content/ bib/
```

`conclusion`이 `success`이고 diff가 없으면 배포 사이트에서 캡처한다. 아니면(배포 중, 실패, 그 뒤 main이 페이지를 바꿈) 1단계의 worktree를 고치기 전에 로컬 빌드로 캡처한다.

```sh
npm run prebuild
npx quartz build -d content -o .work/site
```

빌드, 캡처, 외부 독자의 반환, 가르기 기록은 1단계 worktree의 `.work/` 아래에 두고, 명령은 그 worktree 루트에서 돌린다. scratchpad는 세션을 다시 시작하면 비어 캡처와 가르기 기록을 잃는다. 캡처는 소유자가 정한 슬러그 목록으로 한 번만 받는다. 로컬 빌드면 `--site .work/site`를 더한다.

```sh
npm run reader-capture -- --out .work/capture <슬러그>...
```

- 도해 틀 안쪽 폭이 도해 폭 문턱과 어긋난다고 알리고 0이 아닌 코드로 끝나도, 캡처 파일은 다 받은 것이다. 알림을 소유자에게 그대로 보이고 이어 간다.
- 브라우저가 없다고 멈추면 `npx playwright install --only-shell chromium`으로 받는다. 이 명령은 캐시에서 지금 `playwright` 판이 쓰지 않는 브라우저를 지운다.

완료: 소유자가 대상 슬러그를 정했고, 그 페이지마다 텍스트와 두 폭의 조각이 있고, 캡처한 곳(배포 사이트나 로컬 빌드)을 적었다.

## 3. 읽기

읽는다: [reader.md](reader.md).

[reader.md](reader.md)의 지시 블록과 반환 꼴 블록을 이어 `.work/capture/지시.md`에 옮긴다. 그다음 Workflow 도구로 [read-pages.js](read-pages.js)를 `scriptPath`로, `args`에 `{ "capture": "<worktree>/.work/capture", "slugs": [<2단계의 슬러그>] }`를 주어 부른다. 두 경로는 절대 경로다. 스크립트가 페이지마다 외부 독자(`external-reader`) 하나를 범위 "페이지 통째"로 띄운다.

Workflow가 끝나면 페이지마다 [reader.md](reader.md)의 반환 확인을 한다. 인용이 맞지 않는 항목은 반환 파일에서 지우지 않고 그 항목에 `"인용 불일치": true`를 더해 4단계로 넘긴다. 외부 독자는 인용을 "…"로 줄이기도 해, 페이지에 있는 자리도 맞지 않을 수 있다. 외부 독자에게 돌려보내지 않는 것은, 끝난 Workflow 에이전트에 SendMessage가 닿는다는 근거가 없고, 새로 띄우면 이미지까지 다시 읽어 페이지당 수만 토큰이 들기 때문이다. 파일이 없거나 키가 빠진 페이지만 `slugs`에 그 슬러그를 주어 같은 스크립트를 다시 돌린다.

Workflow의 전체 토큰과 걸린 시간은 끝날 때 오는 알림의 `<usage>`에 있는 `subagent_tokens`와 `duration_ms`다. 이 둘을 6단계의 비용에 옮긴다.

완료: 페이지마다 확인을 통과한 반환 파일이 있고, 인용 불일치를 표시한 항목의 건수와 Workflow의 토큰과 시간을 적었다.

## 4. 가르기

읽는다: `docs/wiki-conventions.md`의 페이지 타입과 프론트매터, 절, 슬러그, 출처 문장, 인용, 약어, 용어, 중복 절, `docs/wiki-abbreviations.md`, `docs/wiki-terms.md`, `docs/wiki-verification.md`의 판정, 좁혀 쓰기, 반영 뒤 재판정 절, [린트 스킬](../wiki-lint/SKILL.md)의 3. 가르기.

반환의 `다시 읽은 문장`, `모호한 곳`, `막힌 낱말`, `모순`, `시각 요소`의 항목을 모은다. 인용 불일치를 표시한 항목은 페이지에서 그 자리를 찾아, 찾으면 인용을 페이지의 글자로 바꾸고 찾지 못하면 버린다. 여러 외부 독자가 같은 곳을 적었으면 하나로 합친다. 항목마다 `content/`의 원본과 렌더된 조각을 보고 넷으로 가른다. 모든 항목은 D 기준을 먼저 받고, D가 아닌 것만 A, B, C로 간다. 가르기를 에이전트에 나눠 맡기면 브리프는 이 절을 가리키기만 하고, 갈래 기준을 다시 적거나 한쪽으로 기울이는 말(예: "확신이 서지 않으면 B")을 더하지 않는다. 다시 적은 기준과 기울기는 항목을 B로 쏠리게 한다.

| 갈래 | 기준                                                                            | 처리                                 |
| ---- | ------------------------------------------------------------------------------- | ------------------------------------ |
| A    | 고친 뒤에도 모든 주장의 내용과 인용이 그대로인 것                               | 5단계에서 고친다                     |
| B    | 주장의 내용이나 인용을 건드리는 것                                              | 7단계에서 이슈로 넘긴다              |
| C    | 고치면 위키 규칙을 어기는 것. 규칙 안에서 고칠 길이 있으면 A나 B로 간다         | 7단계에서 `docs: 규약 검토 모음`으로 |
| D    | 고치지 않아도 독자가 틀린 뜻을 갖고 떠나지 않는 바람(페이지 범위 안팎 상관없음) | 걸러 내고 건수만 센다                |

- A와 B를 가르는 기준은 [린트 스킬](../wiki-lint/SKILL.md)의 3. 가르기에서 굵게 쓴 수정 기준이다. 그 절이 수정으로 드는 태그 정합, 위키링크, 용어 불일치는 린트가 찾는 것일 뿐이다. 문장을 다시 쓴 수정은 주장의 뜻(위키 검증 문서 반영 뒤 재판정 절의 첫 줄)과 인용 자리를 바꾸지 않을 때만 A다. 아래는 A가 아니다.
  - 한정어, 관계, 사실 더하기
  - 시제, 주어 바꾸기와, 말의 힘(위키 검증 문서 반영 뒤 재판정 절의 첫 줄)이 달라지는 동사 바꾸기. 같은 뜻의 동사로 바꾸는 것은 A다
  - 모호한 문장을 한쪽 뜻으로 정하는 어순 바꾸기와 꾸밈 대상 옮기기
  - 가리키는 말을 앞 문장의 말로 풀어 같은 말이 되풀이되는 것
  - 나누면 [합의 문서](../../../docs/wiki-verification.md#합의-문서) 구간 규칙상 출판물 주어를 다시 써야 하는 문장 나누기
  - 인용 키를 다른 문장으로 옮기기
  - 다른 출처 구간 사이에 끼우기([ADR 0016](../../../docs/adr/0016-source-run-by-edition.md))
- 예외로, 출처 구간의 이어지는 문장에서 가리키는 말("이 표준", "이 권고")과 개념 주어를 서로 바꾸는 것, 가리키는 말이 다른 출처로도 읽히는 자리에서 그 말을 출처 구간 규칙대로 판 연도를 뗀 출처 이름으로 바꾸는 것과 그에 따라 바뀌는 동사(정의·요구 동사와 서술 사이)는 범위와 말의 힘이 그대로이고 [출처 구간 규칙](../../../docs/wiki-verification.md#좁혀-쓰기)을 지키면 A다. 예: "이 권고는 CBC의 IV를 예측할 수 없게 고르도록 정한다."를 "CBC의 IV는 예측할 수 없게 고른다."로
  - 범위: 가리키는 말에 딸린 한정을 떼어 주장이 모든 경우로 넓어지면 A가 아니다. 예: "이 간행물의 방식 가운데 암묵적 키 인증을 주는 것은 정적 키 쌍을 쓰는 방식뿐이다."를 "암묵적 키 인증을 주는 키 합의 방식은 정적 키 쌍을 쓰는 방식뿐이다."로
  - 말의 힘: 위키 검증 문서 반영 뒤 재판정 절의 첫 줄이 정한 갈래다. 가리키는 말 속의 문서 종류 이름("이 권고")이 아니라 동사로 본다. "정한다"를 서술로 바꾸는 것은 그대로다. "권한다"나 "예로 든다"를 서술로 바꾸면 바뀐 것이다. 서술을 "정한다"로 바꾸는 것은 출처의 그 대목이 요구일 때만 그대로다.
  - 동사가 출처의 행위(명명, 권고, 값·분류의 제시)인 문장의 주어는 가리키는 말이어도 출처 구간 규칙의 보고 동사 주어라 바꾸지 않는다. 예: "이 간행물은 키 합의 방식을 … 나누고"
- 막힌 낱말은 걸린 까닭이 오독이면 D 기준에 들지 않으므로 A나 B다. 오독을 낳지 않아도 이름의 정체만 빠진 낱말은 거르지 않고, 이미 있는 페이지나 절로 링크해 풀리면 A, 그 밖에는 B다. B로 두면 약어 풀이와 bib의 이름 가운데 어느 것인지 적고, 적을 수 없으면 D처럼 거른다. 본문에 풀이를 더하는 것은 B다. 나머지(`필요했던 것`이 개념 풀이나 배경인 것)는 D처럼 걸러 내고 6단계에서 건수만 센다.
  - 이름의 정체만 빠진 낱말: 약어 풀이, 페이지가 이미 인용한 bib가 외부 독자가 물은 제조사·종류를 담은 이름, 이미 있는 페이지나 절로 링크해 풀리는 낱말이다. 자기 페이지가 있는 약어도 링크로 풀린다.
  - 읽는 페이지 자신의 절로 거는 링크는 링크로 풀리는 것에 들지 않는다. 그 낱말이 같은 페이지 뒤에서 풀리면 D다.
  - 약어가 든 식별자(`SWE.6.BP1`)는 약어 일반을 다루는 절로 걸어 풀지 않는다.
  - 자기 페이지가 없고, [풀이하지 않는 약어](../../../docs/wiki-abbreviations.md) 목록에 있거나 같은 까닭이 드는 약어는 풀지 않으므로 거른다. bib에 제조사만 있는 이름도 거른다.
  - 도해 이름표에만 나오는 낱말은 도해를 고치지 않고 앞 문단에서 풀거나 링크한다.
  - 원문은 열지 않는다.
- C는 어기게 되는 규칙의 파일과 절을 적는다. 규칙의 까닭이 그 경우에도 들어맞으면 C로 보내지 않고, D처럼 걸러 내고 건수만 센다.
- 링크된 페이지에서 걸린 곳도 같은 기준으로 가르고, A면 같은 PR에서 고친다.
- 페이지 글이 아니라 사이트의 렌더에서 오는 것(인용 번호의 줄바꿈 등)은 넷에 넣지 않고 6단계의 보고에 따로 적는다.

가르기나 고치기를 에이전트에 나눠 맡기면 에이전트마다 `.work/` 아래에 작업 폴더를 따로 두고, 검사는 `npm run check:content -- --no-build`로만 돌린다. 빌드와 PR 전 확인은 메인 세션이 모아 한 번 돌린다. 한 worktree와 폴더에서 검사를 함께 돌리면 빌드가 서로 부딪쳐 죽거나 남의 스크립트를 덮어쓴다.

완료: 사이트의 렌더에서 오는 것과 버린 인용 불일치 항목을 뺀 모든 항목이 A, B, C, D 가운데 하나다.

## 5. 고치기

읽는다: 4단계의 위키 규약 절. 도해를 고치면 도해 규약.

1단계의 worktree 브랜치에서 A를 4단계의 A 기준대로 고친다. 인용 키는 고치기 전과 같은 문장에 둔다. 에이전트에 나눠 맡기면 4단계의 작업 폴더와 검사 줄을 따른다. 도해는 외부 독자가 작은 글자나 잘림을 짚은 것만 폭을 줄여 다시 그리고, 그 밖의 도해는 폭을 그대로 두고 고친다([도해 규약](../../../docs/wiki-diagrams.md)).

고친 뒤 `npm run check:diff -- --base <기준 SHA>`로 위키 검증 문서의 반영 뒤 점검을 하고, `CONTRIBUTING.md`의 PR 전 확인을 돌린다. 커밋 메시지는 `content: <대상> Reader Testing 수정`이다.

그다음 위키 검증 문서 검토 절의 1회차를 돈다. Reader Testing 수정 PR은 검증자가 돌지 않는 흐름이라 표기 검토와, 도해를 고쳤으면 도해 검토만 돈다. 독자 검토는 돌지 않는다.

- **표기 검토**: `style-reviewer`에 위키 검증 문서의 표기 검토 절대로 넣고 띄운다. 고침 목록(`고침.md`)은 A로 고친 곳이다. "바뀜 의심"인 고침과, 고친 곳이 4단계의 "A가 아니다" 목록에 들고 예외에 들지 않는 고침은 되돌려 B로 옮긴다. 메인 세션은 같은 뜻으로 본 동사 바꾸기를 말의 힘으로 다시 본다.
- **도해 검토**: `diagram-reviewer`에 위키 검증 문서의 도해 검토 절대로 넣고 띄운다. 기준 렌더는 2단계의 조각이고, 새 렌더는 2단계의 로컬 빌드와 캡처 명령으로 2단계와 다른 폴더에 받는다. 지적이 고쳐지지 않는 도해는 되돌린다.

지적은 메인 세션이 모아 반영하고, 위키 검증 문서의 처리 줄을 남긴다.

완료: A가 커밋됐고, 1회차의 지적마다 처리 줄이 있고, 반영 뒤 점검의 후보를 모두 봤고, PR 전 확인이 통과한다.

## 6. 짧은 보고

B 이슈 본문 초안을 7단계 1의 꼴로 1단계 worktree의 `.work/`에 쓴 뒤, 소유자에게 아래를 짧게 알리고 멈춘다.

- 대상과 캡처한 곳(배포 사이트나 로컬 빌드)
- 갈래별 건수와 주요 항목. A는 고친 곳, B는 넘길 항목의 칸별 건수와 주요 항목, C는 어기게 되는 규칙, D와 걸러 낸 C·막힌 낱말은 건수만
- B 이슈 본문 초안의 경로
- 사이트의 렌더에서 오는 것
- 3단계에서 인용 불일치를 표시한 항목과 그 가운데 4단계에서 버린 건수
- 비용: 캡처는 페이지당 데스크톱 조각의 이미지 토큰, 외부 독자는 다시 돌린 실행까지 합친 Workflow 전체 토큰과 걸린 시간과 그것을 페이지 수로 나눈 값, 가르기와 점검에 띄운 에이전트는 토큰
- 전후를 비교할 명령과 기준 SHA:

  ```sh
  cd <worktree> && WIKI_DIFF=<기준 SHA> npm run preview:diff
  ```

완료: 보고를 마쳤다.

## 7. 이슈와 PR

소유자의 확인으로 고친 것은 2회차의 diff에 든다. 고친 뒤에는 5단계의 반영 뒤 점검과 PR 전 확인을 다시 돌린다.

1. B가 있으면 이슈 하나를 올린다. B는 Reader Testing이 고치지 않고, 소유자가 triage해 티켓으로 처리한다.
   - 제목 `content: <대상> Reader Testing B`, 라벨 `needs-triage`
   - 본문 첫 두 줄은 아래다. 둘째 줄은 [B 반영 프롬프트](b-fix.md)를 가리킨다.

     ```md
     기준 SHA: `<기준 SHA>`. D 기준을 거친 항목이라 triage는 다시 거르지 않는다.

     반영은 [B 반영 프롬프트](https://github.com/jjongs2/ash-wiki/blob/main/.claude/skills/wiki-reader-testing/b-fix.md)를 따른다.
     ```

     그 아래는 `## 모순`, `## 모호한 곳`, `## 다시 읽은 문장`, `## 막힌 낱말`, `## 시각 요소` 차례의 절이고, 항목이 없는 절은 뺀다.

   - 줄은 ``- `<슬러그>` "<인용>" — <걸린 까닭>``이다. 모순은 두 인용을 `↔`로 잇고, 시각 요소는 인용 대신 걸린 요소를 적는다. 걸린 까닭은 그 칸의 반환(외부 독자가 읽은 뜻, 필요했던 것, 걸린 곳)을 한 구로 줄인다. 인용은 A를 고친 뒤의 글 그대로이고, 인용 키는 적지 않는다. 막힌 낱말 줄은 걸린 까닭 앞에 4단계의 갈래대로 `[오독]`, `[약어]`, `[bib]` 가운데 하나를 단다.
2. C가 있으면 열린 `docs: 규약 검토 모음` 이슈에 [모음 이슈 템플릿](../../../.github/ISSUE_TEMPLATE/convention-review.md)의 꼴로, 규칙(파일과 절)마다 코멘트 하나를 남긴다. **문제**에는 그 규칙에 걸린 페이지와 외부 독자가 읽은 뜻을 모은다. 열린 모음 이슈가 없으면 템플릿의 제목, 라벨, 본문으로 연다.
3. A를 고쳤으면 위키 검증 문서 검토 절의 2회차를 돈다. 표기 검토와 도해 검토가 1회차 커밋과의 diff를 보고, `CONTRIBUTING.md`의 리뷰 절대로 두 축 리뷰를 함께 돌린다. 반영하고 PR을 올린다. 도해를 더했으면 push 직전에 위키 규약의 열린 PR과 겹치는 파일 절을 따라 본다. 제목은 `content: <대상> Reader Testing 수정`, 본문은 `CONTRIBUTING.md`의 PR 본문 절을 따르고, 1의 이슈가 있으면 그 번호를 적는다. Verification에는 캡처한 곳, 갈래별 건수, B 이슈의 건수, 위키 검증 문서 검토 절의 처리 결과와 PR 전 확인을 적는다.

완료: B가 있으면 B 이슈가, C가 있으면 규칙마다 모음 이슈의 코멘트가 있고, 고친 것이 있으면 PR(B 이슈가 있으면 그 번호를 적은)이 있다.
