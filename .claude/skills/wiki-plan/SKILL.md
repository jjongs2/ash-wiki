# 주제 계획

주제 하나(예: CAN)를 페이지 묶음으로 나눠, 인제스트가 frontier에서 바로 집어 들 티켓으로 발행한다. 용어는 `GLOSSARY.md`를 따른다.

먼저 읽는다: `docs/adr/0001-isolation-boundary.md`(격리 경계), `docs/wiki-conventions.md`(슬러그, 페이지 타입, 태그), `docs/wiki-terms.md`(용어 표기 결정), `docs/wiki-verification.md`의 `verify:` 이슈 절.

## 1. 노트 읽기

`ASH_WIKI_NOTES`가 가리키는 디렉터리에서 주제에 해당하는 노트를 모두 읽는다. 변수가 비어 있으면 멈추고 소유자에게 설정을 요청한다.

노트 경로와 파일 이름은 대화에만 쓴다. 계획 파일, 티켓, 코멘트에는 개념만 남는다.

완료: 주제에 해당하는 노트 파일을 빠짐없이 읽었다.

## 2. 계획 쓰기

계획 파일은 저장소 루트의 `.work/plan-<주제>/`에 쓴다. `<주제>`는 주제 태그의 `/`를 `-`로 바꾼 것이고, `.work/`는 [인제스트](../wiki-ingest/SKILL.md)의 준비 문단이 정한 작업 폴더로 재시작에 지워지지 않는다. 담을 것:

- **페이지 목록**: 페이지마다 슬러그, 타입(개념·표준), 태그. 태그는 여럿 적을 수 있고, 주 태그를 먼저 적는다. 규칙은 위키 규약을 따르고, 타입은 `docs/wiki-conventions.md`의 페이지 타입과 프론트매터 절에 있는 출판물 기준으로 고른다. 기준의 예에 바로 들지 않아 판단이 갈리는 페이지는 근거를 한 줄 적는다.
- **페이지 묶음**: 묶음마다 이름과 페이지. 서로 위키링크로 자주 엮이는 개념끼리 묶고, PR 하나로 리뷰할 만한 크기로 둔다.
- **기존과의 관계**: `content/`의 페이지와 열린 `ingest:` 티켓을 보고, 이미 있거나 계획된 슬러그와 겹치는 것을 빼고 적는다. 게시 기준에 못 미쳐 만들지 않았던 페이지를 다시 다루면, `보류` 항목을 위키 검증 문서의 게시 기준 절을 따라 이어받는다. 이어받은 출처 후보는 `## 범위`의 줄로만 적는다. 페이지 표에 `출처 후보` 열을 두면 인제스트가 그 티켓을 출처 경로로 처리하기 때문이다.
- **뺀 개념**: 노트에 나오지만 페이지로 만들지 않는 개념과 그 이유(다른 주제에 속함, 공개 출처로 확인할 사실이 아님 등).
- **범위**: 묶음마다 [발행](#5-발행)의 `ingest:` 템플릿에 있는 `## 범위` 절의 다섯 부분. 주인 페이지 표는 두 페이지 이상이 다룰 개념마다 한 줄이고, 기존 페이지나 다른 주제의 페이지와 겹치는 개념도 담는다.

묶음 안의 페이지는 슬러그 순으로 적는다.

완료: 노트에 나오는 개념마다 들어갈 페이지가 있거나 뺀 이유가 적혀 있다. 묶음마다 범위가 있다.

## 3. 비평

Agent 도구로 빈 컨텍스트 서브에이전트(`general-purpose`) 하나를 띄운다. 계획 파일 경로를 주고, 노트는 `ASH_WIKI_NOTES`에서 읽게 한다. 저장소 문서는 이 스킬이 먼저 읽은 넷을 읽게 한다. 볼 것:

- 빠진 개념, 겹치는 페이지, 너무 넓거나 좁은 페이지
- 슬러그, 타입, 태그가 규약에 맞는가
- 묶음이 개념으로 묶였는가, 묶음 이름과 순서가 노트의 챕터 구성을 옮기지 않았는가
- 주인 페이지 표가 묶음 사이의 겹침을 모두 덮는가
- 페이지마다 머리말을 채울 공개 1층 정의가 있을 법한가. 출처는 열지 않고, 포괄 개념 페이지처럼 정의가 없을 법한 페이지를 짚는다. 반영하면 그 페이지의 범위에 표시한다.

비평마다 반영하거나 반영하지 않은 이유를 계획 파일에 적는다.

완료: 모든 비평 항목에 반영 여부와 이유가 있다.

## 4. 승인

대화에 페이지 표, 묶음, 묶음별 범위, 뺀 개념, 비평 반영 요약을 보이고 소유자의 승인을 기다린다. 고쳐 달라고 하면 고쳐서 다시 보인다. 소유자가 묶음 구성이나 페이지 배정을 바꾸면, 바뀐 부분에 3단계의 비평을 다시 돌린 뒤 보인다.

완료: 소유자가 이 계획을 발행하라고 분명히 말했다. 그 전에는 아무것도 발행하지 않는다.

## 5. 발행

`gh` 사용법과 blocked-by API는 `docs/agents/issue-tracker.md`를 따른다. 묶음 티켓이 막을 `verify:` 이슈를 먼저 만든다. 인제스트는 그 번호를 본문이 아니라 의존 관계에서 읽는다. 주제 계획 티켓이 있으면 두 본문 모두 `## Parent`에 그 번호를 적고, 없으면 `## Parent` 절을 뺀다.

**`verify: <주제>`**: 라벨과 blocked-by는 위키 검증 문서의 `verify:` 이슈 절을 따른다. 주제 이름은 `content/tags/<구역>/<주제>.md`의 `title`이다.

```md
## Parent

#<주제 계획 티켓>

## What to build

<주제>의 미검증 주장을 모으고 재조사한다. 절차는 `docs/wiki-verification.md`를 따른다.
```

**`ingest: <묶음 이름>`**: 묶음마다 하나. 라벨 `ready-for-agent`. `## 범위`의 alias 표는 주제의 모든 묶음에서 alias를 둘 페이지를 담고, 그런 페이지가 없으면 뺀다. alias는 위키 규약의 슬러그 절을 따른다. 주인 페이지 표는 그 묶음의 페이지가 주인이거나 링크만 하는 곳인 줄을 담는다. 타입 판단이 갈려 계획 파일에 근거를 적은 페이지는 `## Pages` 표 아래에 근거를 한 줄씩 옮기고, 그런 페이지가 없으면 뺀다.

인수 기준은 하네스(콘텐츠 검사기와 인제스트의 에이전트 단계)가 이미 강제하는 것을 적지 않고, 아래 한 줄을 모든 묶음 티켓에 늘 싣는다. `## Pages`, 주인 페이지 표, 표시 이름 파일, 대문 구역 표와 README의 다루는 주제 표, 검증자 판정 반영, PR 전 확인, 격리 자기 점검, `verify:` 코멘트는 하네스가 본다. `## 표기 결정`은 보강의 티켓에만 있고, 결정 줄과 적용할 페이지를 묶음마다 나눠 맡으므로 "이 묶음이 맡은"을 둔다.

```md
## Parent

#<주제 계획 티켓>

## Pages

| 슬러그     | 타입 | 태그            |
| ---------- | ---- | --------------- |
| `<슬러그>` | 개념 | `<구역>/<주제>` |

- `<슬러그>` 타입 근거: <출판물 기준으로 고른 까닭>

## 범위

다른 묶음·기존 페이지와 겹치지 않게 주제 계획이 정한 것만 적는다. 그 밖의 범위는 인제스트가 정한다.

- `<슬러그>`: <다룰 것>.

alias(병렬 인제스트끼리 겹치지 않게 미리 정함):

| 페이지     | alias   |
| ---------- | ------- |
| `<슬러그>` | <alias> |

주인 페이지:

| 개념   | 주인                        | 링크만 하는 곳                           |
| ------ | --------------------------- | ---------------------------------------- |
| <개념> | `<슬러그>`                  | `<슬러그>`, `<슬러그>`                   |
| <개념> | <주제> 주제(아직 계획 없음) | `<슬러그>`. 이름만 두고 링크하지 않는다. |

출처로 확인할 점:

- <출처를 열어 봐야 정해지는 것>

출처 후보: <발행기관과 자료>

## Acceptance criteria

- [ ] `## 표기 결정`이 있으면: 이 묶음이 맡은 결정 줄이 용어 표기 결정 목록에 있고, 이 묶음이 맡은 페이지가 결정(조건 포함)을 따른다.
```

묶음 티켓을 모두 만든 뒤 `verify:` 이슈에 blocked-by를 건다.

마지막으로 주제 계획 티켓이 있으면 그 티켓에 발행한 티켓 목록을 코멘트로 남긴다.

완료: 묶음마다 티켓이 있고, `gh api repos/<owner>/<repo>/issues/<verify 이슈> --jq .issue_dependencies_summary.blocked_by`가 묶음 수와 같다.
