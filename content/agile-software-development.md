ISO/IEC/IEEE 24765:2017은 **애자일 개발**(agile development)을 반복 개발, 잦은 점검과 조정, 점진적 인도를 바탕으로 하는 소프트웨어 개발 접근 방식으로 정의한다. 이 접근 방식에서 요구와 해결책은 여러 기능을 갖춘 팀의 협업과 이해관계자의 지속적인 피드백을 거치며 발전한다.[@iso-iec-ieee-24765-obp-2017] 애자일 방법은 짧은 반복 개발 주기마다 시연할 수 있는 동작하는 제품을 만들고, 고객을 자주 참여시키며, 요구 변경에 열려 있다.[@ieee-swebok-v4-0a-2026] 점진·반복 생명주기 자체는 [[software-development-life-cycle#예측형에서 적응형까지|소프트웨어 개발 생명주기]]에서 다룬다.

## 등장

애자일 방법은 무거운(heavyweight) 개발 방식의 대안으로 나왔다.[@ieee-swebok-v4-0a-2026][@iso-iec-33202-obp-2024]

애자일 방법은 대규모 소프트웨어 개발 프로젝트에서 쓰던 무거운 계획 기반 방법의 큰 부담을 줄이려고 1990년대에 개발되었다. 애자일 방법이 가볍다고 여겨지는 것은 짧은 반복 개발 주기, 스스로 조직하는 팀, 더 단순한 설계, 코드 [[refactoring|리팩터링]], [[test-driven-development|테스트 주도 개발]], 잦은 고객 참여, 개발 주기마다 시연할 수 있는 동작하는 제품을 강조하기 때문이다. SWEBOK V4.0a에 따르면 애자일 방법은 Deming의 [[pdca-cycle|PDCA 사이클]]을 [[software-engineering|소프트웨어 공학]]에 적용한 것으로 볼 수 있다.[@ieee-swebok-v4-0a-2026]

## 애자일 선언

Extreme Programming, [[scrum|Scrum]], DSDM(Dynamic Systems Development Method) 같은 경량 개발 방법을 대표하던 열일곱 명이 2001년 2월 11일부터 13일까지 미국 유타주 Snowbird에 모여 Manifesto for Agile Software Development(애자일 선언)에 합의했고, 참석자 모두가 선언에 서명했다.[@highsmith-agile-manifesto-history-2001] 선언의 저자들은 선언을 agilemanifesto.org에 공개하고, 저자가 아닌 지지자들의 서명도 받아 명단으로 실었다.[@beck-agile-manifesto-signatories-2016]

선언의 저자들은 네 가지 가치를 두 항목을 견주는 꼴로 적고, 뒤 항목에도 가치가 있지만 앞 항목을 더 중시한다고 밝혔다.[@beck-agile-manifesto-2001]

| 더 중시하는 것      | 그보다 덜 중시하는 것 |
| ------------------- | --------------------- |
| 개인과 상호작용     | 프로세스와 도구       |
| 동작하는 소프트웨어 | 포괄적인 문서         |
| 고객과의 협력       | 계약 협상             |
| 변화에 대응하기     | 계획을 따르기         |

선언의 저자들은 이 가치 뒤에 열두 원칙을 두었다. 요지는 다음과 같다.[@beck-agile-manifesto-principles-2001]

- 가치 있는 소프트웨어를 일찍부터 끊이지 않게 인도해 고객을 만족시키는 일을 가장 앞에 둔다.
- 개발이 많이 진행된 뒤에 들어온 요구 변경도 받아들이고, 변화를 고객의 경쟁력으로 돌린다.
- 동작하는 소프트웨어를 몇 주에서 몇 달 사이 간격으로 자주 인도하되, 간격은 짧을수록 좋다.
- 업무 쪽 사람과 개발자는 프로젝트 기간 내내 날마다 함께 일한다.
- 의욕 있는 사람들을 중심으로 프로젝트를 꾸리고, 필요한 환경과 지원을 주며 일을 해낼 것이라 믿고 맡긴다.
- 개발 팀에 정보를 전하고 팀 안에서 정보를 나누는 데는 얼굴을 맞댄 대화가 가장 효율적이고 효과적이다.
- 진척을 재는 첫째 척도는 동작하는 소프트웨어다.
- 지속 가능한 개발을 추구해, 후원자, 개발자, 사용자가 한결같은 속도를 기한 없이 이어 갈 수 있어야 한다.
- 기술적 탁월함과 좋은 설계에 늘 관심을 두면 민첩성이 높아진다.
- 할 필요가 없는 일은 되도록 하지 않고 넘기는 단순함이 핵심이다.
- 가장 좋은 아키텍처, 요구, 설계는 스스로 조직하는 팀에서 나온다.
- 팀은 정기적으로 더 효과적으로 일할 방법을 돌아보고 그에 맞춰 행동을 다듬는다.[@beck-agile-manifesto-principles-2001]

## 가치·원칙과 실천

애자일은 고객에게 늘 가치를 인도하는 일이나 기술적 탁월함에 대한 헌신 같은 가치·원칙과, [[scrum#이벤트|Sprint Planning]]이나 회고 같은 실천을 분명히 나눈다.[@ieee-swebok-v4-0a-2026]

SWEBOK V4.0a에 따르면 애자일을 두고 여러 오해가 생겼고, 이 지식 체계가 나온 2026년에도 일부가 남아 있었다. 이 지식 체계는 그 예로 애자일이 그 자체로 하나의 방법이라는 것, 문서를 만들지 않아도 되므로 폭포수보다 빠르다는 것, 애자일의 방법과 실천이 빈약하거나 체계가 없다는 것을 든다.[@ieee-swebok-v4-0a-2026]

## 대표 방법

널리 쓰이게 된 애자일 방법에는 XP(Extreme Programming)와 Scrum 등이 있다. [[devops|DevOps]]는 애자일 개발의 잦은 반복이 주는 피드백에, 운영 환경에서 오는 피드백을 더한다.[@ieee-swebok-v4-0a-2026]

Scrum 말고도 널리 쓰이는 애자일 방법으로는 앞 문단의 XP를 비롯해 다음이 있다.[@ieee-swebok-v4-0a-2026]

- **RAD**(rapid application development): 주로 데이터 중심의 업무 시스템 개발에 쓰인다. 특수 목적의 데이터베이스 개발 도구로 새 업무 애플리케이션이나 고친 업무 애플리케이션을 빠르게 개발하고, 테스트하고, 배포한다.
- **XP**: 요구사항을 스토리나 시나리오로 적고, 테스트를 먼저 만들며, 고객이 팀에 직접 들어와 대개 [[acceptance-testing|인수 테스트]]를 정한다. [[software-review#여러 이름|페어 프로그래밍]]을 쓰고, 코드의 리팩터링과 [[continuous-integration|지속적 통합]]을 계속한다. 스토리는 태스크로 나뉘어 우선순위가 매겨지고, 추정되고, 개발되고, 테스트된다. 증분마다 자동 테스트와 수동 테스트를 하고, 증분은 두어 주마다 출시할 만큼 자주 나올 수 있다.
- **FDD**(feature-driven development): 모델 주도의 짧은 반복 개발 방식으로, 도메인의 범위를 잡는 제품 모델 개발, 요구나 기능(feature) 목록 작성, 기능 개발 계획 수립, 반복마다의 기능 설계, 기능의 코딩·테스트·통합이라는 다섯 단계를 거친다. [[software-development-life-cycle#예측형에서 적응형까지|점진 개발 방식]]과 비슷하고, XP와도 비슷하지만 코드 소유권을 팀이 아니라 개인에게 준다. 소프트웨어 전체의 아키텍처를 중시해, 계속된 리팩터링에 기대기보다 처음부터 기능을 바르게 만들도록 한다.
- **Lean**: Toyota Production System에서 온 lean 제조 원칙을 소프트웨어 개발에 맞춰 적용한다. 가장 단순한 판의 제품을 먼저 내는 Minimum Viable Product 전략을 택해, 사용자의 피드백에서 배우고 그에 따라 반복한다. 개별 개발 프로세스가 아니라 개발 프로세스 전체를 최적화하려 하며, 설계, 제조, 판매, 서비스 인도를 아우르는 가치 흐름 전체를 보고 흐름을 최적화해 서비스를 사용자에게 빨리 인도한다.[@ieee-swebok-v4-0a-2026]

[[kanban|Kanban]]도 Lean의 생각을 많이 적용한 가벼운 프로세스이지만, 워크플로 관리와 시각화를 지원한다는 점에서 위의 Lean 방법과는 몇 가지 근본적인 차이가 있다.[@ieee-swebok-v4-0a-2026]

SWEBOK V4.0a에 따르면 2026년에는 복잡한 프로젝트에 애자일 생명주기 모델이 점점 더 많이 쓰였지만, 큰 프로젝트와 포트폴리오로 애자일을 넓히는 일은 여전히 어려웠다. 대규모·엔터프라이즈 애자일 접근은 많은 애자일 팀을 관리하고 애자일 원칙과 실천을 기업 전체에 적용하려는 시도다.[@ieee-swebok-v4-0a-2026]

ISO/IEC/IEEE 24765 용어집은 ISO/IEC TR 7052:2023의 정의를 따라 XP를, 반복적인 계획·작업 절차에 테스트 주도 설계나 페어 프로그래밍 같은 기술적 절차를 결합한 애자일 소프트웨어 개발의 한 형태로 정의한다.[@ieee-cs-sevocab-2026]

## 사용자 스토리

**사용자 스토리**(user story)는 사용자가 시스템의 일부로 이루려는 것을 짧게 적은 것이다.[@iso-iec-tr-7052-obp-2023] ISO/IEC 33202:2024는 사용자 스토리를 원하는 기능을 간단히 적은 것으로 정의한다.[@iso-iec-33202-obp-2024] 사용자 스토리는 [[software-requirements-specification#명세 기법|구조화된 자연어 요구 명세]]의 한 꼴이고, [[acceptance-test-driven-development#행위 주도 개발|behavior driven development]]에서도 기능 단위를 적는 데 쓴다.[@ieee-swebok-v4-0a-2026]

사용자 스토리는 흔히 "As <역할> … so that <목적>"의 뼈대로 쓴다.[@ieee-swebok-v4-0a-2026][@iso-iec-tr-7052-obp-2023] 스토리 뒤에는 [[acceptance-test-driven-development#인수 기준|인수 기준]]이 붙는다. 사용자 스토리에는 3C(Card, Conversation, Confirmation)라 부르는 세 가지 핵심 측면이 있다.[@istqb-ctfl-syllabus-2024]

- **Card**: 사용자 스토리를 적는 매체. 예: 인덱스 카드, 전자 보드의 항목
- **Conversation**: 소프트웨어를 어떻게 쓸지에 대한 설명. 문서로 남기거나 말로 한다.
- **Confirmation**: 인수 기준[@istqb-ctfl-syllabus-2024]

좋은 사용자 스토리가 갖출 요건을 **INVEST**(Independent, Negotiable, Valuable, Estimable, Small, Testable)라 부른다.[@istqb-ctfl-syllabus-2024]

## 테스트에 주는 영향

ISTQB 용어집은 애자일 소프트웨어 개발을, 반복·점진 개발에 바탕을 두고 요구와 해결책이 스스로 조직하는 다기능 팀의 협업으로 발전하는 소프트웨어 개발 생명주기 모델의 묶음으로 정의한다.[@istqb-glossary-agile-software-development-2026]

애자일 소프트웨어 개발은 프로젝트 내내 변경이 일어날 수 있다고 가정하므로, 애자일 프로젝트에서는 작업 산출물의 문서를 가볍게 하고 [[regression-testing|회귀 테스트]]를 쉽게 하는 폭넓은 테스트 자동화를 선호한다. 수동 테스트는 대부분 사전 테스트 분석과 설계를 많이 요구하지 않는 [[software-testing#테스트 기법의 분류|경험 기반 테스트 기법]]으로 한다.[@istqb-ctfl-syllabus-2024]

## 생명주기 표준과 애자일

[[iso-iec-ieee-12207|ISO/IEC/IEEE 12207:2026]]은 애자일 접근과 방법에도 적용할 수 있다고 둔다. 이 표준은 프로젝트 정의의 주석에서, 애자일과 DevOps 같은 지속적 개발 접근이 시작·종료 기준이 정해진 프로젝트 없이도 제품과 서비스를 만들 수 있다고 제시한다.[@iso-iec-ieee-12207-obp-2026]

[[v-modell-xt|V-Modell XT]] 2.4는 Scrum 같은 애자일 방식이 프로젝트 맥락에 따라 이 모델과 잘 결합할 수 있다고 둔다.[@weit-v-modell-xt-2-4-2024]

## 폭포수 모델과의 차이

애자일 마인드셋은 소통의 중요성, 변경에 열려 있음, 기술적 탁월함에 대한 헌신, 고객에게 늘 가치를 인도함 같은 가치와 원칙에 바탕을 둔다는 점에서, 요구 명세의 구현을 약속하는 데 더 초점을 두는 예측형 마인드셋과 다르다. [[waterfall-model|폭포수 모델]]이 예측형 생명주기의 한 예인 것과 달리, 애자일 개발은 요구가 바뀌면 개발의 어느 단계에서든 고칠 수 있는, 변경에 열린 생명주기를 내세운다.[@ieee-swebok-v4-0a-2026]
