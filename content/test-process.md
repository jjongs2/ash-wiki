**테스트 프로세스**(test process)는 테스트 목표를 이루려고 하는 테스트 활동의 묶음이다.[@iso-iec-ieee-29119-2-obp-2021][@istqb-glossary-test-process-2026] 테스트 프로세스는 상황에 맞게 조정할 수 있고, 테스트를 어떻게 하는지는 개발 생명주기, 테스트 대상의 중요도와 [[risk-based-testing#리스크|리스크]], 일정과 예산 같은 프로젝트 제약 등 맥락에 따라 달라진다.[@istqb-ctfl-syllabus-2024]

## ISO/IEC/IEEE 29119-2의 프로세스 모델

[[iso-iec-ieee-29119|ISO/IEC/IEEE 29119]]-2:2021은 테스트 프로세스를 조직, 테스트 관리, 동적 테스트의 세 층으로 나눈다.[@iso-iec-ieee-29119-2-obp-2021]

- **조직 테스트 프로세스**(organizational test process): 조직 테스트 명세를 만들고 관리한다. 대표적인 조직 테스트 명세는 테스트 정책과 조직 테스트 실무(organizational test practices)다.
- **테스트 관리 프로세스**(test management processes): 테스트 전략과 계획(test strategy and planning), 테스트 모니터링과 제어, 테스트 완료의 세 프로세스로, 테스트를 조율하고 모니터링하고 제어한다.
- **동적 테스트 프로세스**(dynamic test processes): 테스트 설계와 구현, 테스트 환경과 데이터 관리(test environment and data management), 테스트 실행, 테스트 사건 보고(test incident reporting)의 네 프로세스다.[@iso-iec-ieee-29119-2-obp-2021]

같은 표준은 각 프로세스를 이렇게 정의한다. 테스트 전략과 계획 프로세스는 테스트 전략을 설계하고 테스트 계획을 마쳐 테스트 계획서를 만들고 유지한다. 테스트 모니터링과 제어 프로세스는 테스트가 테스트 계획서와 조직 테스트 명세대로 이루어지게 한다. 테스트 완료 프로세스는 쓸모 있는 테스트 자산을 뒤에 쓸 수 있게 하고, 테스트 환경을 알맞은 상태로 두고, 테스트 결과를 기록해 이해관계자에게 알린다. 테스트 설계와 구현 프로세스는 [[test-case|테스트 케이스]]와 테스트 절차를 끌어내 명세하고, 테스트 환경과 데이터 관리 프로세스는 테스트 환경과 테스트 데이터를 갖추고 유지한다. 테스트 실행 프로세스는 테스트 설계와 구현에서 만든 테스트 절차를 준비된 테스트 환경에서 실행하고 그 결과를 기록하며, 테스트 사건 보고 프로세스는 테스트 실행에서 찾은, 후속 조치가 필요한 사건을 관련 이해관계자에게 보고한다.[@iso-iec-ieee-29119-2-obp-2021]

ISO/IEC/IEEE 29119-3:2021은 테스트 문서의 서식을 그 문서를 내는 프로세스별로 나눈다. 테스트 계획서, 테스트 상태 보고서, 테스트 완료 보고서는 테스트 관리 프로세스의 문서로, 테스트 실행 로그와 테스트 사건 보고서는 동적 테스트 프로세스의 문서로 둔다.[@iso-iec-ieee-29119-3-obp-2021]

## 테스트 활동

ISTQB CTFL v4.0.1 강의계획서는 테스트 프로세스가 대개 아래 활동 묶음으로 이루어진다고 본다. 활동은 순서대로 늘어놓았지만 흔히 되풀이되거나 나란히 진행된다.[@istqb-ctfl-syllabus-2024]

| 활동                   | 하는 일                                                                                                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 테스트 계획            | 목표를 정하고, 제약 안에서 그 목표를 이룰 접근법을 고른다.                                                                                                                          |
| 테스트 모니터링과 제어 | 계획에 견주어 진행을 계속 살피고, 목표를 이루는 데 필요한 조치를 한다.                                                                                                              |
| 테스트 분석            | [[v-model#테스트 기준\|테스트 기준]]을 분석해 테스트할 수 있는 특성을 찾고, [[test-case#테스트 조건\|테스트 조건]]을 정해 리스크를 고려해 우선순위를 매긴다.                        |
| 테스트 설계            | 테스트 조건을 테스트 케이스와 그 밖의 testware로 다듬고, [[test-coverage\|커버리지]] 항목을 찾고, 테스트 데이터 요구사항을 정하고 테스트 환경을 설계한다.                           |
| 테스트 구현            | 테스트 데이터 같은 testware를 만들거나 구하고, 테스트 케이스를 테스트 절차로 엮어 [[test-case#테스트 스위트\|테스트 스위트]]로 묶고, 테스트 환경을 갖춰 바르게 차려졌는지 확인한다. |
| 테스트 실행            | 실행 일정에 따라 테스트를 실행하고, 실제 결과를 기대 결과와 견주고, 이상을 분석해 보고한다.                                                                                         |
| 테스트 완료            | 마일스톤에서 하며, 뒤에 쓸 testware를 보관하거나 넘기고, 교훈과 개선점을 찾고, 테스트 완료 보고서를 써서 알린다.                                                                    |

## 테스트 계획서

**테스트 계획서**(test plan)는 이룰 테스트 목표와, 그 목표를 이룰 수단과 일정을 적어 테스트 활동을 조율하는 문서다.[@iso-iec-ieee-29119-3-obp-2021][@istqb-glossary-test-plan-2026] 테스트 계획서는 테스트 프로젝트의 목표, 자원, 프로세스를 적고, 대개 다음 내용을 담는다.[@istqb-ctfl-syllabus-2024]

- 테스트의 맥락(범위, 테스트 목표, 테스트 기준)
- 가정과 제약
- 이해관계자(역할, 책임, 테스트와의 관계, 교육 필요)
- 의사소통(형식, 빈도, 문서 서식)
- 리스크 목록(제품 리스크와 프로젝트 리스크)
- 테스트 접근법([[software-testing#테스트 레벨|테스트 레벨]], [[test-type|테스트 유형]], 테스트 기법, 산출물, 진입 기준과 종료 기준, [[software-testing#테스트의 독립성|테스트의 독립성]], 측정할 메트릭, 테스트 데이터와 테스트 환경 요구사항)
- 예산과 일정[@istqb-ctfl-syllabus-2024]

테스트 계획서에 담는 리스크는 [[risk-based-testing|리스크 기반 테스트]]에서 다룬다.

## 진입 기준과 종료 기준

**진입 기준**(entry criteria)은 정해진 작업을 공식적으로 시작하기 위한 조건의 묶음이다.[@istqb-glossary-entry-criteria-2026] 흔한 진입 기준은 자원(사람, 도구, 환경, 테스트 데이터, 예산, 시간)과 testware(테스트 기준, 테스트할 수 있는 요구사항, 사용자 스토리, 테스트 케이스)를 갖췄는지, 그리고 테스트 대상의 처음 품질이 어떤지(스모크 테스트를 통과했는지 등)다.[@istqb-ctfl-syllabus-2024]

**종료 기준**(exit criteria)은 활동을 끝났다고 볼 조건이고, completion criteria라고도 부른다.[@iso-iec-ieee-29119-2-obp-2021][@istqb-glossary-exit-criteria-2026] 흔한 종료 기준은 철저함의 척도(커버리지 수준, 해결하지 않은 결함 수, [[software-metric#결함 밀도|결함 밀도]], 실패한 테스트 케이스 수)와 예·아니오로 가리는 기준(계획한 테스트를 모두 실행했는지, [[software-testing#정적 테스트와 동적 테스트|정적 테스트]]를 했는지, 찾은 결함을 모두 보고했는지)이다. 시간이나 예산이 다 떨어지는 것도 종료 기준으로 볼 수 있고, 이해관계자가 리스크를 검토해 받아들이면 다른 기준을 채우지 못해도 테스트를 끝낼 수 있다.[@istqb-ctfl-syllabus-2024]

ISTQB CTFL v4.0.1 강의계획서는 진입 기준과 종료 기준을 테스트 레벨마다 정하기를 권한다. 두 기준은 테스트 목표에 따라 달라진다. 순차 개발 모델에서는 흔히 한 테스트 레벨의 종료 기준이 다음 레벨의 진입 기준의 일부가 되도록 정하지만, 일부 반복 개발 모델에서는 그렇지 않을 수 있다. [[agile-software-development|애자일 소프트웨어 개발]]에서는 종료 기준을 흔히 [[scrum#산출물과 약속|Definition of Done]]이라 부르고, 사용자 스토리가 개발이나 테스트를 시작하려면 채워야 할 진입 기준을 **Definition of Ready**라 부른다.[@istqb-ctfl-syllabus-2024]

SWEBOK V4.0a에 따르면 달성한 코드 커버리지나 기능 커버리지 같은 철저함의 척도와 결함 밀도나 운용 신뢰도의 추정은 테스트를 끝낼지 정하는 데 쓸모 있는 근거이지만, 그것만으로는 충분하지 않다. 이 결정에는 남아 있을 수 있는 failure가 낳을 비용과 리스크를 테스트를 이어 가는 비용과 견주는 일도 든다.[@ieee-swebok-v4-0a-2026]

## 추정과 우선순위

테스트 노력 추정은 테스트 목표를 이루는 데 드는 테스트 작업의 양을 예측하는 일이고, 추정은 여러 가정에 기대며 늘 오차가 따른다. 작은 작업의 추정이 대개 큰 작업보다 정확하므로, 큰 작업은 작은 작업으로 쪼개어 추정할 수 있다. 테스트 노력 추정 기법으로는 다음이 있다.[@istqb-ctfl-syllabus-2024]

- **비율 기반 추정**(estimation based on ratios): 메트릭 기반 기법이다. 조직의 앞선 프로젝트에서 모은 수치로 비슷한 프로젝트의 표준 비율을 끌어내 새 프로젝트의 테스트 노력을 추정한다. 예를 들어 앞 프로젝트의 개발 노력 대 테스트 노력이 3:2였고 이번 프로젝트의 개발 노력이 600인일로 예상되면, 테스트 노력은 400인일로 추정한다.
- **외삽**(extrapolation): 메트릭 기반 기법이다. 현재 프로젝트에서 되도록 일찍 측정해 모은 데이터를 대개 수학 모델로 외삽해 남은 작업의 노력을 근사한다. ISTQB CTFL v4.0.1 강의계획서에 따르면 외삽은 반복 개발 생명주기에 잘 맞는다. 예를 들어 다음 반복의 테스트 노력을 앞선 세 반복의 평균으로 추정한다.
- **Wideband Delphi**: 전문가 기반의 반복 기법이다. 전문가마다 따로 노력을 추정하고, 합의한 범위를 벗어난 추정이 있으면 논의한 뒤 다시 따로 추정하기를 합의에 이를 때까지 되풀이한다. 그 변형인 Planning Poker는 애자일 소프트웨어 개발에서 흔히 쓰며, 노력의 크기를 나타내는 숫자 카드로 추정한다.
- **3점 추정**(three-point estimation): 전문가 기반 기법이다. 전문가가 가장 낙관적인 추정 $a$, 가장 그럴듯한 추정 $m$, 가장 비관적인 추정 $b$를 내고, 그 가중 산술 평균을 최종 추정 $E$로 삼는다.[@istqb-ctfl-syllabus-2024]

3점 추정의 가장 널리 쓰이는 꼴은 아래 식으로 최종 추정 $E$와 측정 오차 $\mathrm{SD}$를 구한다. 예를 들어 $a = 6$, $m = 9$, $b = 18$인시면 $E = 10$, $\mathrm{SD} = 2$이므로 최종 추정은 10±2인시다.[@istqb-ctfl-syllabus-2024]

$$
E = \frac{a + 4m + b}{6}, \qquad \mathrm{SD} = \frac{b - a}{6}
$$

![[diagrams/three-point-estimation-example.svg]]

테스트 케이스와 테스트 절차를 명세해 테스트 스위트로 묶고 나면, 실행 순서를 정한 테스트 실행 일정으로 늘어놓을 수 있다. 가장 흔히 쓰이는 테스트 케이스 우선순위 전략은 다음과 같다.[@istqb-ctfl-syllabus-2024]

- **리스크 기반 우선순위**: 리스크 분석의 결과로 실행 순서를 정한다.
- **커버리지 기반 우선순위**: 구문 커버리지 같은 커버리지로 실행 순서를 정해, 가장 높은 커버리지를 이루는 테스트 케이스를 먼저 실행한다. 변형인 **추가 커버리지 우선순위**(additional coverage prioritization)는 커버리지가 가장 높은 테스트 케이스를 먼저 실행하고, 그 뒤로는 커버리지를 가장 많이 더하는 테스트 케이스를 차례로 고른다.
- **요구사항 기반 우선순위**: 테스트 케이스로 추적되는 요구사항의 우선순위로 실행 순서를 정해, 가장 중요한 요구사항에 관련된 테스트 케이스를 먼저 실행한다. 요구사항의 우선순위는 이해관계자가 정한다.[@istqb-ctfl-syllabus-2024]

우선순위대로 늘어놓는 것이 이상적이지만, 테스트 케이스나 테스트하는 기능 사이에 의존이 있으면 그렇게 되지 않을 수 있다. 우선순위가 높은 테스트 케이스가 낮은 테스트 케이스에 의존하면 낮은 것을 먼저 실행해야 한다. 실행 순서는 특정 시간에만 쓸 수 있는 테스트 도구, 테스트 환경, 사람 같은 자원도 고려해야 한다.[@istqb-ctfl-syllabus-2024]

## 모니터링과 제어

테스트 모니터링은 테스트에 관한 정보를 모으는 일이다. 그 정보로 테스트 진행을 평가하고, 제품 리스크·요구사항·[[acceptance-test-driven-development#인수 기준|인수 기준]]의 커버리지 목표처럼 종료 기준이나 그에 딸린 테스트 작업을 채웠는지 잰다. 테스트 제어는 모니터링에서 얻은 정보로 가장 효과적이고 효율적인 테스트를 이루는 데 필요한 지침과 시정 조치를 통제 지시(control directive)의 꼴로 내린다. 통제 지시의 예는 다음과 같다.[@istqb-ctfl-syllabus-2024]

- 식별한 리스크가 실제 문제가 되면 테스트의 우선순위를 다시 매김
- 재작업 때문에 테스트 항목이 진입 기준이나 종료 기준을 채우는지 다시 평가함
- 테스트 환경의 인도가 늦어지면 테스트 일정을 조정함
- 필요한 때와 곳에 자원을 더함[@istqb-ctfl-syllabus-2024]

테스트 메트릭은 계획한 테스트 일정과 예산에 견준 진행, 테스트 대상의 현재 품질, 테스트 목표나 반복의 목표에 견준 테스트 활동의 효과를 보이려고 모은다. 흔한 테스트 메트릭은 다음과 같다.[@istqb-ctfl-syllabus-2024]

| 메트릭               | 예                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 프로젝트 진행 메트릭 | 작업 완료, 자원 사용, 테스트 노력                                                                                                         |
| 테스트 진행 메트릭   | 테스트 케이스 구현의 진행, 테스트 환경 준비의 진행, 실행한·실행하지 않은 테스트 케이스와 통과·실패한 테스트 케이스의 수, 테스트 실행 시간 |
| 제품 품질 메트릭     | 가용성, 응답 시간, mean time to failure                                                                                                   |
| 결함 메트릭          | 찾은·고친 결함의 수와 우선순위, 결함 밀도, [[defect-management#결함 예방과 결함 데이터 분석\|DDP]]                                        |
| 리스크 메트릭        | 잔여 리스크 수준                                                                                                                          |
| 커버리지 메트릭      | 요구사항 커버리지, 코드 커버리지                                                                                                          |
| 비용 메트릭          | 테스트 비용, 조직의 품질 비용                                                                                                             |

## 실행과 완료의 산출물

- **테스트 로그**(test log): 테스트 실행에 관한 세부 사항을 시간순으로 적은 기록이다.[@istqb-glossary-test-log-2026]
- **사건 보고서**(incident report): 정의와 결함 보고서와의 관계, 처리는 [[defect-management#결함 보고서와 사건 보고서|결함 관리]]에서 다룬다.
- **테스트 진행 보고서**(test progress report): 기준선에 견준 테스트 활동의 진행, 리스크, 결정할 대안을 담는 정기 테스트 보고서이고, test status report라고도 부른다.[@istqb-glossary-test-progress-report-2026] 테스트 진행 보고서는 테스트 모니터링과 제어 중에 대개 정기적으로 낸다.[@istqb-ctfl-syllabus-2024]
- **테스트 완료 보고서**(test completion report): ISO/IEC/IEEE 29119-3:2021은 테스트 완료 보고서를 수행한 테스트를 요약한 보고서로 정의하고, test summary report를 같은 말로 둔다.[@iso-iec-ieee-29119-3-obp-2021] 테스트 완료 보고서는 완료 마일스톤에서 내며, 테스트 항목을 종료 기준에 견주어 평가한다.[@istqb-glossary-test-completion-report-2026] 테스트 완료 보고서는 테스트 완료 중에 쓰고, 테스트 계획서의 목표와 종료 기준에 견준 평가, 완화하지 못한 리스크와 고치지 않은 결함, 교훈을 담는다. ISTQB CTFL v4.0.1 강의계획서는 프로젝트나 반복이 끝날 때, 릴리스 마일스톤 등에서 여는 [[scrum#이벤트|회고]]의 결과를 기록하기를 권한다. 그 결과는 대개 테스트 완료 보고서에 담긴다.[@istqb-ctfl-syllabus-2024]
