**체크섬**(checksum)은 데이터에서 계산해 데이터 뒤에 덧붙여 보내는 값으로, 오류를 검출하는 데 쓴다.[@iec-60050-811-37-15-2017][@microchip-an1148-2008] 수신 측은 받은 데이터로 체크섬을 다시 계산해 오류를 검사한다.[@microchip-an1148-2008][@ietf-rfc-1071-1988]

체크섬은 데이터를 바이트나 워드 단위로 더한 합으로 만들기도 한다.[@ietf-rfc-1071-1988][@microchip-xc8-pic-ug-2026]

## 구조·동작

### 인터넷 체크섬

RFC 1071은 IP(Internet Protocol), UDP, TCP가 쓰는 체크섬을 **인터넷 체크섬**이라 부른다.[@ietf-rfc-1071-1988] RFC 791은 IP 헤더 체크섬을 헤더의 모든 16비트 워드를 1의 보수로 더한 합의 1의 보수로 정한다.[@ietf-rfc-791-1981] RFC 9293은 TCP 체크섬을 의사 헤더를 포함한 헤더와 데이터의 16비트 워드를 같은 방식으로 더해 구하도록 정한다.[@ietf-rfc-9293-2022] RFC 768은 UDP 체크섬을 의사 헤더, UDP 헤더, 데이터를 같은 방식으로 더해 구하도록 정한다.[@ietf-rfc-768-1980]

1의 보수 덧셈은 최상위 비트에서 넘친 올림수를 최하위 비트에 다시 더한다.[@ietf-rfc-1071-1988][@microchip-enc28j60-2012]

RFC 791과 RFC 9293은 체크섬을 계산할 때 체크섬 필드를 0으로 두도록 정한다.[@ietf-rfc-791-1981][@ietf-rfc-9293-2022] RFC 1071에 따르면 수신 측이 체크섬 필드까지 포함해 1의 보수 합을 구했을 때 모든 비트가 1이면 검사를 통과한다. 1의 보수 합은 교환 법칙과 결합 법칙이 성립해서, 바이트의 짝·홀 자리만 지키면 어떤 순서와 묶음으로 더해도 합이 같다. 또 하드웨어의 [[byte-order|바이트 순서]]와 상관없이 같은 방법으로 구할 수 있다.[@ietf-rfc-1071-1988]

### Fletcher 체크섬과 Adler-32

**Fletcher 체크섬**은 데이터를 더한 합 $A$와, $A$를 다시 누적한 합 $B$ 두 개를 체크섬으로 쓴다.[@microchip-xc8-pic-ug-2026][@ietf-rfc-1146-1990] RFC 1146에 따르면 $B$에는 옥텟마다 자리에 따른 가중치가 붙어서, Fletcher 알고리즘은 표준 TCP 체크섬과 달리 데이터그램 안에서 옥텟이나 워드가 자리를 바꾼 것을 찾아낸다.[@ietf-rfc-1146-1990]

RFC 1950에 따르면 **Adler-32**는 Fletcher 알고리즘을 32비트로 넓히고 개선한 것이다. RFC 1950은 Adler-32를 바이트의 합 $s_1$과 $s_1$ 값들의 합 $s_2$로 정한다. 두 합은 65521로 나눈 나머지로 유지하고, $s_1$은 1, $s_2$는 0에서 시작하며, 결과는 $s_2 \times 65536 + s_1$로 저장한다. zlib 포맷은 압축 전 데이터의 Adler-32를 싣고, RFC 1950은 규격을 따르는 압축 해제기가 이를 검사해 값이 틀리면 오류를 알리도록 요구한다. 두 합 가운데 바이트를 더하기만 한 $s_1$은 $s_2$와 달리 바이트의 위치와 순서에 민감하지 않다.[@ietf-rfc-1950-1996]

LIN이 쓰는 체크섬은 [[lin#체크섬|LIN]]에서 다룬다.

## 비교·한계

[[cyclic-redundancy-check|CRC]]는 체크섬보다 오류 검출 능력이 크다.[@microchip-an1148-2008][@ietf-rfc-1071-1988] RFC 1071에 부록으로 실린 IEN 45에 따르면 CRC 다항식 부호는 프로그램으로 구현하기에 비용이 크다.[@ietf-rfc-1071-1988]
