**소프트웨어 리뷰**(software review)는 사람이 작업 산출물이나 프로세스를 살펴 평가하거나 의견을 내는 활동이다.[@istqb-glossary-review-2026][@ieee-cs-sevocab-2026] ISTQB 용어집은 리뷰를 사람이 작업 산출물이나 프로세스의 품질을 평가하는 [[software-testing#정적 테스트와 동적 테스트|정적 테스트]]의 한 유형으로 정의한다.[@istqb-glossary-review-2026] ISO/IEC/IEEE 24765 용어집은 리뷰를 작업 산출물을 프로젝트 인원, 관리자, 사용자, 고객 같은 이해관계자에게 보여 의견이나 승인을 받는 프로세스나 회의로 정의한다.[@ieee-cs-sevocab-2026]

정적 기법과 동적 기법의 구분은 [[verification-and-validation#정적 기법과 동적 기법|검증과 확인]]에서 다룬다. 사람이 읽고 이해할 수 있는 작업 산출물이면 무엇이든 리뷰할 수 있다. [[software-requirements-specification|요구사항 명세]], 소스 코드, [[test-process#테스트 계획서|테스트 계획]], [[test-case|테스트 케이스]], 모델이 그 예다.[@istqb-ctfl-syllabus-2024]

## 리뷰 유형

리뷰 유형은 비공식부터 공식까지 걸쳐 있고, 흔히 쓰는 유형으로 다음이 있다.[@istqb-ctfl-syllabus-2024]

| 유형                                          | 진행                                                              | 목적                                                                                                 |
| --------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 비공식 리뷰(informal review)                  | 정해진 절차를 따르지 않고, 공식 문서로 된 결과를 요구하지 않는다. | 이상 찾기                                                                                            |
| 워크스루(walkthrough)                         | 저자가 이끈다.                                                    | 품질 평가와 신뢰 쌓기, 리뷰어 교육, 합의, 새 아이디어, 저자의 동기 부여와 개선, 이상 찾기            |
| 기술 리뷰(technical review)                   | 기술 역량을 갖춘 리뷰어가 하고, 진행자가 이끈다.                  | 기술 문제에 대한 합의와 결정, 이상 찾기, 품질 평가와 신뢰 쌓기, 새 아이디어, 저자의 동기 부여와 개선 |
| [[software-inspection\|인스펙션]](inspection) | 가장 공식적인 유형으로, 일반 리뷰 절차를 빠짐없이 따른다.         | 이상을 최대한 많이 찾기                                                                              |

필요한 공식성의 수준은 따르는 [[software-development-life-cycle|소프트웨어 개발 생명주기]], 개발 프로세스의 성숙도, 리뷰할 작업 산출물의 중요도와 복잡도, 법이나 규제의 요구사항, 감사 추적의 필요 같은 요인에 달려 있다. 같은 작업 산출물을 처음에는 비공식 리뷰로, 나중에는 더 공식적인 리뷰로 살피듯 여러 유형으로 리뷰할 수도 있다. ISTQB CTFL v4.0.1 강의계획서에 따르면 알맞은 리뷰 유형을 고르는 것은 리뷰 목표를 이루는 열쇠다. 이 강의계획서는 리뷰 유형을 목표만이 아니라 프로젝트의 요구, 쓸 수 있는 자원, 작업 산출물의 종류와 리스크, 비즈니스 도메인, 회사 문화 같은 요인도 보고 고르기를 권한다.[@istqb-ctfl-syllabus-2024]

인스펙션의 절차와 역할은 [[software-inspection#Fagan 인스펙션|소프트웨어 인스펙션]]에서 다룬다. [[ieee-1028|IEEE 1028-2008]]은 경영 리뷰, 기술 리뷰, 인스펙션, 워크스루, 감사의 수행 절차를 정한다.[@ieee-1028-2008] 감사는 [[software-quality#평가, 감사, 검증|소프트웨어 품질]]에서 다룬다.

## 리뷰 절차

ISTQB CTFL v4.0.1 강의계획서는 ISO/IEC 20246의 일반 리뷰 절차를 따라 리뷰 활동을 다섯으로 나눈다.[@istqb-ctfl-syllabus-2024]

1. 계획: 리뷰의 목적, 범위, 대상 산출물, 평가할 [[software-quality-model|품질 특성]], [[test-process#진입 기준과 종료 기준|종료 기준]] 등을 정한다.
2. 리뷰 시작: 참여자가 산출물에 접근할 수 있고 자기 역할을 이해하게 한다.
3. 개별 리뷰: 리뷰어가 각자 산출물을 살펴 이상, 권고, 질문을 찾아 기록한다.
4. 소통과 분석: 찾은 이상마다 상태, 담당자, 조치를 정한다.
5. 수정과 보고: 결함마다 [[defect-management#결함 보고서와 사건 보고서|결함 보고서]]를 만들고, 종료 기준을 만족하면 산출물을 받아들인다.[@istqb-ctfl-syllabus-2024]

리뷰의 주요 역할로는 관리자, 저자, 진행자(moderator, facilitator라고도 함), 기록자(scribe, recorder라고도 함), 리뷰어, 리뷰 리더가 있다.[@istqb-ctfl-syllabus-2024]

## 성공 요인

ISTQB CTFL v4.0.1 강의계획서는 리뷰의 성공을 좌우하는 요인으로 다음을 든다.[@istqb-ctfl-syllabus-2024]

- 분명한 목표와 측정할 수 있는 종료 기준을 정한다. 참여자를 평가하는 것은 목표로 삼지 않는다.
- 주어진 목표를 이루고 작업 산출물의 종류, 참여자, 프로젝트의 요구와 맥락에 맞는 리뷰 유형을 고른다.
- 리뷰어가 개별 리뷰나 리뷰 회의에서 집중력을 잃지 않게 작은 단위로 나눠 리뷰한다.
- 이해관계자와 저자가 제품과 활동을 개선하도록 리뷰의 피드백을 준다.
- 참여자에게 리뷰를 준비할 시간을 넉넉히 준다.
- 경영진이 리뷰 프로세스를 지원한다.
- 학습과 [[process-improvement|프로세스 개선]]을 북돋도록 리뷰를 조직 문화의 일부로 만든다.
- 참여자 모두가 자기 역할을 해낼 수 있게 알맞게 교육한다.
- 회의를 원활하게 진행한다.[@istqb-ctfl-syllabus-2024]

## 리뷰 기법

체크리스트 기반 리뷰(checklist-based reviewing)는 질문이나 갖춰야 할 속성의 목록에 따라 하는 리뷰 기법이다.[@istqb-glossary-checklist-based-reviewing-2026]

테스트 분석가는 개별 리뷰에서 여러 리뷰 기법을 써서 [[v-model#테스트 기준|테스트 기준]]의 결함을 찾을 수 있다. ISTQB CTAL-TA v4.0 강의계획서에 따르면 알맞은 리뷰 기법을 고르면 리뷰의 효율과 효과를 높일 수 있다. CTAL-TA 강의계획서는 리뷰 기법을 고를 때 리뷰 목표, 프로젝트 목표, 쓸 수 있는 자원, 테스트 기준의 종류, 관련 리스크, 비즈니스 도메인, 회사 문화 같은 요인을 봐야 한다고 본다. 테스트 분석가가 흔히 쓰는 리뷰 기법으로는 다음이 있다.[@istqb-ctal-ta-syllabus-2025]

- **ad hoc 리뷰**(ad hoc reviewing): 정해진 절차 없이 비공식으로 하고, 리뷰어는 어떻게 할지 지침을 거의 받지 않는다. 준비가 거의 필요 없고 리뷰어의 기량에 크게 기댄다. 리뷰어는 테스트 기준을 읽으며 이상을 만나는 대로 기록한다. 관리하지 않으면 여러 리뷰어가 같은 이상을 거듭 보고하기 쉽다.
- **체크리스트 기반 리뷰**: 테스트 기준을 미리 정한 체크리스트에 비추어 평가한다. 체크리스트는 리뷰어에게 확인할 점을 일깨우고, 리뷰가 사람을 겨누지 않게 할 수 있다. 체크리스트는 일반적인 것일 수도, 품질 특성이나 테스트 목표, 테스트 기준의 종류에 맞춘 것일 수도 있다. 테스트 분석가는 테스트 기준의 종류, 리스크 수준, [[test-case#테스트 조건|테스트 조건]]에 맞게 체크리스트를 고친다. 체크리스트는 앞서 놓친 결함을 반영해 주기적으로 고친다. 체크리스트가 모든 것을 담지는 않으므로, 테스트 분석가는 목록에 있는 항목만 확인하지 않는다.
- **시나리오 기반 리뷰**(scenario-based reviewing): 어떤 과정이나 활동을 모의로 따라가며 이상을 찾고 테스트 기준을 다듬는다. 리뷰어는 작업 산출물의 예상 사용에 따라 dry run을 할 수 있고, 문서로 된 시나리오에 묶이지 않고 그 밖도 생각해 이상을 더 찾는다.
- **역할 기반 리뷰**(role-based reviewing): 리뷰어에게 특정 역할이나 책임을 맡긴다. 역할은 흔히 숙련·미숙련·노인·어린이 사용자 같은 최종 사용자 유형이나, 관리자·일반 사용자 같은 조직 안의 역할에 바탕을 두고, 페르소나로 나타낼 수 있다.
- **perspective-based reading**: 설계자, 테스터, 마케터, 관리자, 최종 사용자 같은 여러 관점에서 테스트 기준을 리뷰한다. 리뷰어는 리뷰하는 테스트 기준으로 자기가 거기서 끌어낼 작업 산출물을 만들어 보려 한다. 예를 들어 테스터는 요구사항 명세로 [[acceptance-testing|인수 테스트]] 초안을 만들어 보며 필요한 정보가 다 있는지 본다.[@istqb-ctal-ta-syllabus-2025]

CTAL-TA 강의계획서에 따르면 시나리오 기반 리뷰는 [[use-case|use case]]나 활동 다이어그램처럼 테스트 기준이 시나리오 꼴일 때 가장 효과적이고, 역할 기반 리뷰는 리뷰어마다 테스트 기준의 다른 측면에 집중하므로 빠짐없이 커버하면서 이상이 겹치는 것을 피하며, perspective-based reading은 개별 리뷰를 깊게 하고 리뷰어 사이에 겹치는 이상을 줄인다.[@istqb-ctal-ta-syllabus-2025]

명세의 결함은 비용과 시간이 많이 드는 후속 작업을 낳고, 인수 테스트나 운용처럼 늦은 개발 단계에서야 찾으면 특히 그렇다. ISTQB CT-AuT v2.1.1 강의계획서에 따르면 리뷰는 명세의 결함을 일찍 찾아 적은 비용으로 고치는 효과적인 수단이다. CT-AuT 강의계획서는 테스터가 테스트 분석 중에 테스트 대상의 명세가 테스트 기준으로 알맞은지 살펴야 한다고 본다. 요구사항의 품질 특성은 이때 리뷰의 초점을 잡아 준다. 리뷰를 준비하며 테스터는 품질 특성에서 리뷰 체크리스트의 항목을 끌어낼 수 있다. 품질 특성의 이름만 적은 항목은 너무 추상적이므로 항목은 그보다 구체적으로 쓰고, 리뷰에서 테스터는 아는 데까지 항목에 답한다. 예를 들어 일관성의 항목으로 "모든 요구사항에서 용어를 일관되게 쓰는가?"를 둘 수 있다.[@istqb-ct-aut-syllabus-2025]

## 리뷰 속도와 효과

Kemerer와 Paulk는 2009년 논문에서 PSP(Personal Software Process) 과정의 개인 리뷰 데이터(C 프로그램 371개, C++ 프로그램 246개)를 분석했다. 리뷰어가 개발자 자신 한 사람인 이 데이터에서, 설계 리뷰와 코드 리뷰의 속도가 권장 상한인 시간당 200 LOC(lines of code)를 넘으면 결함 제거 효과가 떨어졌다. 200 LOC 이하에서는 설계 리뷰가 결함의 약 3분의 2를, 코드 리뷰가 절반 넘게 찾았다.[@kemerer-design-code-reviews-2009]

## 여러 이름

- **동료 리뷰**(peer review): 그 산출물을 만들 역량을 갖춘 다른 사람이 하는 리뷰[@ieee-cs-sevocab-2026][@istqb-glossary-peer-review-2026]
- **경영 리뷰**(management review): ISO/IEC/IEEE 24765 용어집은 소프트웨어 획득, 공급, 개발, 운용, 유지보수 프로세스를 관리자가 하거나 관리자를 대신해 하는 체계적 평가로 정의한다.
- **데스크 체크**(desk checking): 이 용어집은 코드 목록, 테스트 결과 같은 문서를 대개 그것을 만든 사람이 눈으로 살펴 오류나 개발 표준 위반 같은 문제를 찾는 [[static-analysis|정적 분석]] 기법으로 정의한다.
- **페어 프로그래밍**(pair programming): 이 용어집은 한 개발자가 코드를 쓰는 동안 다른 개발자가 지켜보며 오류를 찾고 결과가 요구사항을 만족하는지 확인하는 관행으로 정의하고, 두 사람은 주기적으로 역할을 바꾼다고 적는다.[@ieee-cs-sevocab-2026] Kent Beck은 1999년 『Extreme Programming Explained: Embrace Change』에서 모든 소프트웨어를 두 프로그래머가 한 화면 앞에서 짝을 지어 만드는 것을 XP(Extreme Programming)의 기본으로 들었다.[@beck-extreme-programming-explained-1999]
