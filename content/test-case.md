**테스트 케이스**(test case)는 사전 조건, 입력, 기대 결과를 담은 집합이다.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-test-case-2026] [[iso-iec-ieee-29119|ISO/IEC/IEEE 29119]]-1:2022는 테스트 케이스를, 테스트 목표를 이루도록 테스트 항목의 실행을 이끄는 사전 조건, 입력, 기대 결과의 집합으로 정의한다.[@iso-iec-ieee-29119-1-obp-2022] ISTQB 용어집은 테스트 케이스를 테스트 조건을 바탕으로 만든 사전 조건, 입력, 동작(해당할 때), 기대 결과, 사후 조건의 집합으로 정의한다.[@istqb-glossary-test-case-2026]

ISO/IEC/IEEE 24765:2017은 테스트 케이스를, 특정 프로그램 경로를 실행하거나 특정 요구사항을 지키는지 검증하는 것 같은 특정 목표를 위해 만든 테스트 입력, 실행 조건, 기대 결과의 집합으로도 정의한다.[@iso-iec-ieee-24765-obp-2017]

## 구성

- **사전 조건**(precondition): 테스트를 실행하기 전에 테스트 항목과 테스트 환경이 갖춰야 할 상태.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-precondition-2026]
- **입력**(input): ISO/IEC/IEEE 29119-1:2022는 입력을 테스트 실행을 이끄는 데이터와, 필요하면 동작으로 둔다.[@iso-iec-ieee-29119-1-obp-2022]
- **기대 결과**(expected result): 정해진 조건에서 테스트 항목이 보일 것으로 예측한 관찰 가능한 동작. 명세 같은 근거에서 정한다.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-expected-result-2026]
- **사후 조건**(postcondition): 테스트 실행이 끝났을 때 테스트 항목과 테스트 환경이 있을 것으로 기대하는 상태.[@istqb-glossary-postcondition-2026]

## 테스트 조건

**테스트 조건**(test condition)은 컴포넌트나 시스템에서 테스트로 확인할 수 있는 측면이다.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-test-condition-2026] ISTQB CTFL v4.0.1 강의계획서는 테스트 조건을 테스트 분석에서 정하고, 테스트 설계에서 테스트 케이스로 다듬는 것으로 본다.[@istqb-ctfl-syllabus-2024] 두 활동은 [[test-process#테스트 활동|테스트 프로세스]]에서 다룬다. ISO/IEC/IEEE 29119 시리즈는 테스트 설계에 테스트 조건 대신 테스트 모델이라는 개념을 쓴다.[@iso-iec-ieee-29119-1-obp-2022]

## 상위 수준과 하위 수준 테스트 케이스

테스트 케이스는 구체적인 정도에 따라 둘로 나뉜다.[@istqb-ctal-ta-syllabus-2025]

- **상위 수준 테스트 케이스**(high-level test case): 추상 테스트 케이스나 논리 테스트 케이스라고도 한다. 어떤 테스트 조건을 덮는지 밝혀 테스트 대상을 살필 상황을 적는다. ISTQB CTAL-TA v4.0 강의계획서에 따르면 상위 수준 테스트 케이스는 이 때문에 관련된 테스트 조건을 모두 덮었는지 확인하는 데 알맞다. 사전 조건, 입력 데이터, 기대 출력, 사후 조건은 구체적인 값 없이 추상 수준으로만 적는다.
- **하위 수준 테스트 케이스**(low-level test case): 구체 테스트 케이스나 물리 테스트 케이스라고도 한다. 상위 수준 테스트 케이스를 자세히 다듬은 것으로, 준비할 데이터, 테스터가 할 동작(필요할 때), 구체적인 기대 결과를 적고, 구체적인 사전 조건, 입력 데이터, 기대 결과, 사후 조건을 담는다.[@istqb-ctal-ta-syllabus-2025]

대개 상위 수준 테스트 케이스를 먼저 설계하고, 그것을 바탕으로 하위 수준 테스트 케이스를 만든다. 상위 수준 테스트 케이스 하나를 하위 수준 테스트 케이스 하나 이상으로 구현할 수 있고, 구체적인 정보는 테스트 실행 중에 정하도록 상위 수준으로 남겨 두기도 한다. 하위 수준으로 옮기는 일은 특정 테스트 데이터가 필요하면 흔히 테스트 설계에서 테스트 구현으로 미룬다. 실무에서는 어떤 면은 구체적이고 어떤 면은 추상적인 혼합 테스트 케이스가 많은데, 흔히 테스트 케이스의 유지보수성과 이해 가능성 사이에서 절충한 결과다.[@istqb-ctal-ta-syllabus-2025]

이 강의계획서는 테스트 케이스의 품질 기준으로 다음을 든다.[@istqb-ctal-ta-syllabus-2025]

| 기준                                   | 내용                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 정확성(correctness)                    | 바탕이 된 테스트 조건을 정확히 검증할 수 있어야 한다.                                                                                                                                                                                                                                                                  |
| 실행 가능성(feasibility)               | 실행할 수 있어야 한다.                                                                                                                                                                                                                                                                                                 |
| 필요성(necessity)                      | 제목이나 요약에 드러나는 분명한 테스트 목표를 덮어야 한다. 중복을 피하고, 테스트하지 않을 것에는 테스트 케이스를 설계하지 않는다.                                                                                                                                                                                      |
| 이해 가능성(understandability)         | 작성자가 아닌 사람도 검토하고 고치고 실행할 수 있으므로, 관련된 모든 이해관계자가 이해할 언어와 꼴로 쓴다. 복잡한 테스트 케이스는 단순하게 하거나 나눈다.                                                                                                                                                              |
| [[traceability\|추적성]](traceability) | 최신으로 유지할 수 있도록 테스트 조건, 요구사항, 리스크로 추적할 수 있어야 한다.                                                                                                                                                                                                                                       |
| 일관성(consistency)                    | 언어, 서식, 구조가 일관되면 이해하고 유지보수하기 쉽다.                                                                                                                                                                                                                                                                |
| 정밀성(precision)                      | [[static-analysis#False positive와 false negative\|false-negative]] result와 false-positive result를 피하도록 해석이 하나뿐이어야 하고, "알맞은", "필요한 만큼" 같은 모호한 말을 피한다.                                                                                                                               |
| 완전성(completeness)                   | 필요한 테스트 데이터와, 실제 결과에 견줄 분명한 기대 결과를 비롯해 필요한 속성을 모두 갖춰야 한다.                                                                                                                                                                                                                     |
| 간결성(conciseness)                    | 크기가 [[v-model#테스트 기준\|테스트 기준]]과 테스트 조건에 맞아야 한다. [[test-coverage#기법마다 다른 커버리지 항목\|커버리지 항목]] 몇 개에 집중한 작은 테스트 케이스가 낫다. failure의 원인을 찾기 쉽고, 테스트 절차와 테스트 스위트로 유연하게 엮을 수 있으며, 실행 중 failure가 뒤의 테스트를 막지 않기 때문이다. |

테스트 케이스의 꼴과 상세 수준은 프로젝트와 제품의 맥락에 따라 다르다. 이 강의계획서는 이를 테스트 팀 안에서 합의해야 한다고 본다.[@istqb-ctal-ta-syllabus-2025]

## 테스트 절차와 스크립트

**테스트 절차**(test procedure)는 실행할 순서로 늘어놓은 테스트 케이스에, 사전 조건을 갖추는 동작과 실행 뒤의 마무리 활동을 더한 것이다.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-test-procedure-2026]

ISO/IEC/IEEE 29119-1:2022는 **테스트 스크립트**(test script)를 테스트 절차 명세(test procedure specification)와 같은 말로 두고, 하나 이상의 테스트 절차를 명세한 문서로 정의한다.[@iso-iec-ieee-29119-1-obp-2022] ISTQB 용어집은 테스트 스크립트를 테스트를 실행하는 명령의 열로 정의한다.[@istqb-glossary-test-script-2026] 테스트 구현에서 수동 테스트 스크립트와 자동 테스트 스크립트를 만든다.[@istqb-ctfl-syllabus-2024]

## 테스트 스위트

ISO/IEC/IEEE 29119-1:2022는 **테스트 스위트**(test suite)를 테스트 케이스나 테스트 절차의 집합으로 정의하고, 보통 테스트를 언제 실행하는지에 따라 묶는다고 둔다.[@iso-iec-ieee-29119-1-obp-2022] ISTQB 용어집은 테스트 스위트를 한 번의 테스트 실행에서 돌릴 테스트 스크립트나 테스트 절차의 집합으로 정의한다.[@istqb-glossary-test-suite-2026]

## 테스트 데이터와 testware

**테스트 데이터**(test data)는 테스트를 실행하는 데 필요한 데이터로, 테스트 케이스를 실행할 때의 입력 요구를 채우려고 만들거나 고른다.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-test-data-2026] ISO/IEC/IEEE 29119-1:2022는 테스트 데이터가 배열이나 flat file처럼 테스트 항목 안에 있을 수도 있고, 다른 시스템, 하드웨어 장치, 사람 운영자 같은 바깥에서 올 수도 있다고 둔다.[@iso-iec-ieee-29119-1-obp-2022]

테스트 설계 중에 테스트 실행을 위해 준비하거나 공급해야 할 테스트 데이터를 찾아 요청하고, 이때 목적, 형식, 쓰임의 맥락을 고려한다. ISTQB CTAL-TA v4.0 강의계획서는 개인 정보 같은 민감한 테스트 데이터를 보호해야 한다고 본다. **가명화**한 데이터는 개인 정보를 인위적인 식별자로 바꾼 것이고, **익명화**한 데이터는 개인을 알아볼 수 있는 정보를 없앤 것이다. 이 강의계획서는 결함을 찾고 유지보수하기 쉽도록, 하위 수준 테스트 케이스의 구체적인 테스트 데이터를 테스트 로직에 하드코딩하지 말고 따로 두어야 한다고 본다.[@istqb-ctal-ta-syllabus-2025]

**Testware**는 테스트를 계획하고 설계하고 실행하는 데 필요해서 테스트 프로세스에서 만드는 산출물이다.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-testware-2026] ISO/IEC/IEEE 29119-1:2022는 testware에 문서, 스크립트, 입력, 기대 결과, 파일, 데이터베이스, 환경, 테스트에 쓰는 추가 소프트웨어와 유틸리티가 들 수 있다고 둔다.[@iso-iec-ieee-29119-1-obp-2022]

## 판정과 테스트 오라클

테스트를 실행하면 실제 결과를 기대 결과와 견주어, 맞으면 pass, 어긋나면 fail로 판정한다.[@iso-iec-ieee-29119-1-obp-2022][@istqb-glossary-passed-2026][@istqb-glossary-failed-2026] fail의 원인 분석과 결함의 처리는 [[defect-management|결함 관리]]에서 다룬다.

ISTQB 용어집은 **테스트 오라클**(test oracle)을 기대 결과를 정하는 근거가 되는 출처로 정의한다.[@istqb-glossary-test-oracle-2026] ISO/IEC/IEEE 29119-1:2022는 테스트 오라클을 테스트의 pass와 fail을 가리는 정보의 출처로 정의한다. 오라클은 흔히 기대 결과를 끌어내는 명세이지만, 비슷한 다른 프로그램이나 시스템의 실제 결과와 견주거나 사람 전문가에게 묻는 것도 오라클이 될 수 있다고 둔다.[@iso-iec-ieee-29119-1-obp-2022]

이 표준은 주어진 테스트 입력과 상태에서 테스트가 통과했는지 실패했는지를 가리기 어려운 것을 **테스트 오라클 문제**(test oracle problem)로 정의한다.[@iso-iec-ieee-29119-1-obp-2022] ISTQB CTAL-TA v4.0 강의계획서는 테스트 기준의 품질과 완전성이나 시스템의 특성 때문에 비용에 맞는 테스트 오라클을 구할 수 없는 것을 테스트 오라클 문제라 부른다. 이 문제를 낳는 흔한 요인으로는 데이터에 얽힌 복잡도, 인공지능 기반 시스템 같은 비결정성, 확률적인 동작, 빠지거나 모호한 요구사항이 있다.[@istqb-ctal-ta-syllabus-2025]

테스트 오라클 문제의 알려진 해법으로는 다음이 있다.[@istqb-ctal-ta-syllabus-2025]

- [[back-to-back-testing|pseudo-oracle]]: 테스트 대상과 같은 명세를 채우도록 따로 개발한 시스템이다.
- [[model-based-testing|모델 기반 테스트]]: 테스트 오라클을 테스트 모델의 일부로 형식화할 수 있고, 모델에서 기대 출력을 만들고 테스트를 끌어낼 수 있게 한다.
- **property-based 테스트**: 테스트 대상에 명세된 속성으로 개별 테스트 케이스의 입력과 기대 결과 사이의 관계를 검증하고, 관계가 성립하지 않으면 그 테스트 케이스는 실패한다.
- [[metamorphic-testing|메타모픽 테스트]]
- **사람 오라클**(human oracle): 사람의 능력으로 기대 결과를 정한다.[@istqb-ctal-ta-syllabus-2025]

CTAL-TA 강의계획서에 따르면 property-based 테스트는 [[test-automation|테스트 자동화]]에 잘 맞지만 효과는 정하기 어려울 수 있는 관계에 달려 있고, 사람 오라클은 비싸고 구하기 어려울 수 있지만 [[exploratory-testing|탐색적 테스트]] 같은 일부 테스트 접근법에서는 선호된다.[@istqb-ctal-ta-syllabus-2025]

자동화한 테스트 오라클은 테스트 자동화 코드나 테스트 대상 안에 넣은 assertion으로 구현할 수 있다. **assertion**은 테스트 대상의 상태나 동작을 검증하는 실행 가능한 문장이고, 테스트 대상 안에 넣은 assertion은 대개 테스트 대상이 맡은 작업을 이어 가는 데 필요한 것만 검증한다.[@istqb-ctal-ta-syllabus-2025]

오라클이 늘 pass나 fail을 가릴 수 있는 것은 아니며, 가리지 못하면 테스트 출력을 inconclusive로 분류한다.[@ieee-swebok-v4-0a-2026]

## 테스트 케이스를 일찍 쓰기

ISTQB CTFL v4.0.1 강의계획서는 코드를 쓰기 전에 테스트 케이스를 쓰는 것과 테스터의 관점에서 명세를 [[software-review|리뷰]]하는 것을 [[v-model#테스트 설계를 앞당김|shift left]]의 좋은 관행으로 든다.[@istqb-ctfl-syllabus-2024] 테스트 설계를 개발 단계와 짝지어 앞당기는 일은 [[v-model|V 모델]]에서 다룬다.

테스트 분석에서는 테스트 기준과 테스트 대상도 평가해, 그 안의 결함을 찾고 테스트할 수 있게 쓰였는지(testability) 따진다. 테스터의 관점으로 명세를 리뷰하면 모호함, 빠진 것, 서로 맞지 않는 것 같은 결함을 흔히 찾는다.[@istqb-ctfl-syllabus-2024]

ISO/IEC 25010:2023은 **테스트 가능성**(testability)을 요구사항을 채웠는지 가리는 객관적이고 실행할 수 있는 테스트를 설계하고 수행할 수 있게 하는 제품의 능력으로 정의하고, [[software-quality-model|제품 품질 모델]]에서 유지보수성의 하위 특성으로 둔다.[@iso-iec-25010-obp-2023] ISTQB 용어집은 테스트 가능성을 컴포넌트나 시스템에 대해 테스트 조건을 세우고, 그 테스트 조건을 채웠는지 가리는 테스트를 수행할 수 있는 정도로 정의한다. 용어집은 2024년에 이 용어의 변경 이력에, ISO/IEC 25010의 정의가 바뀌어 용어집의 정의와 더는 같지 않다고 남겼다.[@istqb-glossary-testability-2026]
