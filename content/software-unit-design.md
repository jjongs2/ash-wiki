**소프트웨어 유닛 설계**는 [[software-architecture|소프트웨어 아키텍처]]를 받아 [[automotive-spice-process-reference-model#Element, component, unit|소프트웨어 유닛]]의 내부 구조와 동작을 정하는 설계로, **상세 설계**(detailed design)라고도 부른다.[@vda-automotive-spice-pam-4-1-2026][@ieee-cs-sevocab-2026] ISO/IEC/IEEE 24765 용어집은 상세 설계 단계를 시스템 설계와 소프트웨어 아키텍처를 받아 유닛마다 코딩할 수 있는 상세 로직을 만드는 단계로 정의하고, 상세 설계를 앞선 설계를 구현할 수 있을 만큼 다듬고 넓히는 것으로 정의한다.[@ieee-cs-sevocab-2026]

[[automotive-spice|ASPICE]] 4.1은 소프트웨어 유닛을, 소프트웨어 컴포넌트를 분해해 얻은 것 가운데 더 나누지 않기로 정한 소프트웨어 요소로 정의한다.[@vda-automotive-spice-pam-4-1-2026]

## 유닛의 정의

ISO/IEC/IEEE 24765 용어집은 **유닛**(unit)을 세 가지로 정의한다. 컴퓨터 소프트웨어 컴포넌트의 설계에서 명세한, 따로 시험할 수 있는 요소, 컴퓨터 프로그램에서 논리적으로 떼어 낼 수 있는 부분, 다른 컴포넌트나 요소로 더 나누지 않는 소프트웨어 요소다.[@ieee-cs-sevocab-2026] [[iso-iec-ieee-12207|ISO/IEC/IEEE 12207]]:2026은 소프트웨어 유닛을, 소프트웨어 아키텍처의 원자 수준 소프트웨어 컴포넌트로서 단독으로 시험할 수 있는 것으로 정의한다.[@iso-iec-ieee-12207-obp-2026]

ASPICE 4.1은 SWE.3(Software Detailed Design and Unit Construction) BP1의 주석에서, 유닛의 경계는 소스 코드, 코드 파일 구조, 모델 기반 구현에서 유닛이 어떻게 나타나는지와 상관없이 응용 도메인 관점의 의미로 정해지므로, 유닛이 코드 수준에서 서브루틴 하나나 여러 서브루틴의 집합으로 나타날 수 있다고 제시한다. 정보 항목 11-05(Software unit)는 유닛이 밝힐 것으로 함수 하나나 함수 집합을 든다. 검증 쪽 프로세스에서 구현된 유닛은 소스 코드 파일이나 오브젝트 파일 같은 꼴로 나타난다.[@vda-automotive-spice-pam-4-1-2026]

## 설계가 정하는 것

이 모델은 상세 설계에서 컴포넌트마다 그 유닛들의 동작, 정적 구조와 관계, 인터페이스를 명세하게 한다. 소프트웨어 상세 설계는 소프트웨어 요소의 내부 구조와 동작으로 정하고, 상세 설계가 밝힐 것으로 다음을 든다.[@vda-automotive-spice-pam-4-1-2026]

- 데이터: 데이터 구조와 변수, 입출력 데이터의 형식
- 로직: 알고리즘과 제어 흐름
- 인터페이스: 유닛이 주고받는 입력과 출력. 입출력의 유효 값 범위와 물리 단위나 측정 단위를 넣는다.[@vda-automotive-spice-pam-4-1-2026]

BP1의 주석은 응용 도메인 관점의 유효 값 범위와 물리 단위의 예로 "0..200 [m/s]", "0..3.8 [A]", "1..100 [N]"을, 측정 단위의 예로 "%"와 "‰"를 들고, 물리 단위도 측정 단위도 붙지 않는 파라미터나 반환 값의 예로 카운터를 든다. 이런 값 범위를 0..65535의 unsigned 정수 같은 프로그래밍 언어 수준의 데이터 타입에 대응시키는 일은 BP2로 넘긴다. 정보 항목 04-05(Software detailed design)는 상세 설계에 담을 수 있는 특성으로 설명 주석과 반정형 언어의 요소를 들고, 모델 기반으로 개발한 설계는 정형이나 반정형 언어로 표현할 수 있다고 예를 든다.[@vda-automotive-spice-pam-4-1-2026]

이 모델은 동적 측면으로, 컴포넌트의 동적 동작을 이루는 유닛 사이의 상호작용을 아키텍처에 맞춰 명세하게 한다.[@vda-automotive-spice-pam-4-1-2026] ISO/IEC/IEEE 24765 용어집도 상세 설계 기술(detailed design description)이 하위 컴포넌트마다 입력, 출력, 데이터 구조, 제어 로직, 알고리즘을 밝힌다고 정의한다.[@ieee-cs-sevocab-2026] 동적 동작을 기술하는 표기 가운데 다수는 주로 상세 설계에서 쓸모가 있지만, 거기에만 쓰이지는 않는다. 그 가운데 상태 다이어그램은 컴포넌트가 상태 사이를 옮겨 가며 현재 상태와 입력 이벤트에 따라 동작이 바뀌는 모습을, 시퀀스 다이어그램은 객체 사이에 오가는 메시지의 시간 순서를 보인다.[@ieee-swebok-v4-0a-2026]

상세 설계 단계는 [[software-design#설계 단계|상위 설계]]가 정한 제약 안에서 진행되며, 주요 컴포넌트의 내부 특성, 내부 모듈과 그 상호 연결, 컴포넌트가 제공하는 서비스와 프로세스, 계산 속성, 알고리즘, 데이터 접근 규칙과 데이터 구조를 명세한다. 여기에는 다음이 든다.[@ieee-swebok-v4-0a-2026]

- 주요 시스템 컴포넌트를 모듈이나 프로그램 유닛으로 나누는 일. 기성 컴포넌트와 응용 프레임워크를 쓸 기회도 여기서 찾는다.
- 모듈과 프로그램 유닛에 설계 책임을 할당하는 일
- 모듈 사이의 상호작용
- 컴포넌트, 모듈, 프로그램 유닛 사이의 범위와 가시성
- 컴포넌트의 모드와 상태, 그 사이의 전이
- 데이터와 제어의 상호 의존
- 데이터의 구성, 패키징, 구현
- 사용자 인터페이스
- 필요한 알고리즘과 데이터 구조[@ieee-swebok-v4-0a-2026]

ISO/IEC/IEEE 24765 용어집은 **SDD**(software design description)를, 분석, 계획, 구현, 의사 결정을 돕도록 만든 소프트웨어의 표현으로 정의하고, SDD가 [[software-design|소프트웨어 설계]] 정보를 전하는 매체로 쓰이며 시스템의 청사진이나 모델로 볼 수 있다고 덧붙인다.[@ieee-cs-sevocab-2026] 상세 설계에 남기는 설계 근거는 [[software-design#설계 근거|설계 근거]]에서 다룬다.

## ASPICE SWE.3

ASPICE 4.1은 유닛 설계와 코딩을 한 프로세스 SWE.3으로 둔다. 그 목적은 정적·동적 측면을 담고 아키텍처와 일관된 상세 설계를 세우고, 그 설계와 일관된 유닛을 만드는 것이다. SWE.3의 BP(base practice)는 다음과 같다.[@vda-automotive-spice-pam-4-1-2026]

| BP  | 하는 일                                                                                   |
| --- | ----------------------------------------------------------------------------------------- |
| BP1 | 상세 설계의 정적 측면 명세                                                                |
| BP2 | 상세 설계의 동적 측면 명세                                                                |
| BP3 | 소프트웨어 유닛 개발                                                                      |
| BP4 | [[traceability#일관성\|일관성]] 확보와 [[traceability#양방향 추적성\|양방향 추적성]] 수립 |
| BP5 | 합의한 상세 설계와 개발한 유닛의 전달                                                     |

코딩은 BP3이다. BP3은 유닛을 상세 설계와 일관되게, 코딩 원칙에 따라 개발하고 문서로 남기게 한다. 이 모델은 코딩 원칙의 예로 암묵적 형 변환을 쓰지 않기, 서브프로그램의 입구와 출구를 하나씩 두기, 범위 검사를 들고, 더 많은 예로 [[iso-26262|ISO 26262]]-6의 8.4.5와 표 6을 가리킨다.[@vda-automotive-spice-pam-4-1-2026]

ASPICE 3.1은 SWE.3의 목적을 컴포넌트의 평가된 상세 설계를 내고 유닛을 명세해 만드는 것으로 두었고, BP 여덟 개를 두어 마지막 BP8에서 유닛을 개발하게 했다. ASPICE 4.1은 이를 BP 다섯 개로 묶고 유닛 개발을 BP3에 둔다.[@vda-automotive-spice-pam-4-1-2026][@vda-automotive-spice-pam-3-1-2017]

## ISO 26262-6

ISO 26262-6:2018은 8절에서 소프트웨어 유닛 설계와 구현을 다룬다.[@iso-26262-6-obp-2018]
